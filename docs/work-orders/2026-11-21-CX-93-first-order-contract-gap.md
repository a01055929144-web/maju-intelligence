# CX-93 첫 주문 조건 — 선행 계약 미확정

2026-11-21, 09방. R13의 매장 ⑦ 기간 지난 단가표·③ 주문 조건 확인 중 **③ 전체 완료는 아직 아니다**.

## 읽기로 확인한 경계

- 운영 `public.store_order_eligibility(uuid,uuid,uuid)` 정의를 SELECT로 대조했다. 원본은 `docs/sql-drafts/20261117-S-2a-account-order.sql`의 동명 함수와 같다. 매장 회원을 먼저 확인하고 사업자·약관, 매출처 확인, 배송 지역/요일, 후불 방식/결제 조건, 판매 가격 유무의 blockers를 돌려준다.
- 동종업계의 **기존 설계 기준은 이미 있다**: `docs/dispatch/2026-11-16-S-store-pc.md` 2-3 ②·2-4 ⑩의 유통사 `companies.business_type` 비교다. **대표 추가 결정으로 표시명과 안정적인 분류 ID를 분리하고 한 유통사에 여러 분류를 허용하는 계약으로 확장한다.** 실제 비교는 표시 글자가 아니라 관리자 분류 ID 집합의 교집합으로 한다. 빈 분류는 관리자 확인으로 돌리고 상대 유통사 이름은 노출하지 않는다. 매장의 업종이나 별도 매장별 허용/차단 필드를 새로 만들라는 뜻이 아니다.
- `companies.business_type`은 운영 DB에 text 칼럼으로 존재하지만 안정적인 ID/다중 배정 저장 계약은 이 문서에서 아직 구현하지 않았다. 운영 공개 함수 본문에서 business_type을 참조하는 함수는 확인되지 않았고 store_order_eligibility에도 이 비교가 없다. 기존 text를 자동 분해하거나 이름만으로 분류를 확정하지 않는다. 회사 내부 거래 금지 초안은 이 규칙으로 대체하지 않는다.
- 이 RPC에는 최소 주문금액이나 장바구니/배송일 인자가 없다. 최소금액은 실제 접수 함수가 회사/권역/매장 규칙으로 결정하고 실제 주문 금액과 비교한다. 화면이 문서 가격으로 합산해서 기존 서버 판정인 것처럼 표시하면 안 된다.
- 현재 `/api/storefront`는 서명된 매장 링크에서 회사/매장을 찾고 배송 자격을 재확인한 뒤 기존 주문 RPC로 보낸다. 기존 `store_order_eligibility` RPC를 호출하는 TypeScript 화면 연결은 확인되지 않았다.
- 위 조사는 함수/스키마/소스만 읽었다. 운영 매장·번호·주문 행을 읽거나 쓰지 않았다.

## 확정된 계약과 남은 선행

1. **관리자 분류(08 소유): 마주 관리자가 분류 목록과 유통사별 배정을 이후에도 편집·설정한다.** 분류 항목은 변경하지 않는 ID와 바꿀 수 있는 표시명을 구분하고, 유통사는 분류 ID 여러 개의 집합을 가진다. 표시명 변경은 ID 변경/재사용이 아니며, 삭제·통합·폐기 시 기존 참조를 다른 의미로 재사용하지 않는다. 실제 저장/API 이름은 08 관리자·06 회사 설정의 계약으로 확정한다. 매장별 별도 승인 필드는 추가하지 않는다. 현재 고객사 `PATCH /api/customer/settings` → `updateCompanySettings`도 businessType을 저장하므로 관리자 전용 배정 변경·감사와 고객사 임의 변경 방지 정리가 선행이다. 09는 이 파일과 관리자 파일을 수정하지 않는다. 외식업 확인/매출처 확인/문서 industry는 분류를 대신하지 않는다.
2. **연결·첫 주문 공통 서버 판정:** 검증된 회원과 서버가 찾은 store_profile_id의 활성 연결만 대상으로, 대상 유통사의 확정된 분류 ID 집합과 이미 연결된 다른 유통사의 집합을 비교한다. **교집합이 하나라도 있으면 신규 연결·첫 주문을 차단**하고 같은 회사 자체는 충돌에서 제외한다. 어느 비교 대상이든 미분류/미확정/폐기 항목 등으로 권위 있는 집합을 얻지 못하거나 매장 식별이 미확정이면 관리자 확인 필요로 반환한다. 화면의 표시명 문자열, legacy business_type, 자유 입력의 쉼표 분리, 상·하위 분류 이름 유사도로 교집합을 추정하지 않는다. 분류 계층/통합이 비교 ID에 미치는 영향은 관리자 계약이 명시해야 한다.
3. **접수 시 재확인:** 연결 확인 결과나 첫 화면의 통과를 영구 승인으로 저장하지 않는다. 연결 직전과 첫 주문 접수 직전에 현재 분류/활성 연결을 서버가 재조회한다. 분류 변경 뒤 오래된 링크·토큰·브라우저 저장값으로 우회할 수 없어야 한다. 동시 연결 둘이 같은 업종으로 모두 통과하지 않도록 매장 단위의 직렬화가 필요하다. 여러 주문 진입점이 같은 검사를 거쳐야 하며 화면 버튼만 막는 구현은 완료가 아니다.
4. **최소금액과 나머지 조건:** 사업자/약관·고객사 확인·배송·후불은 기존 서버 조건을 재사용한다. 첫 진입에서는 서버가 고른 최소금액 조건을 안내하고, 실제 충족 여부는 기존 접수 서버가 실제 품목·배송일·금액으로 검사한다. 시가·세금·배송비를 화면에서 새로 계산하거나 사전 안내를 금액 충족 판정으로 표시하지 않는다. “첫 주문 한 번 자동”은 진입 안내를 반복 승인받지 않는 흐름이며, 기존 접수 재검증을 생략하는 뜻으로 해석하지 않는다.

차단 응답은 `same_industry_connection`(“이미 같은 업종 유통사와 연결된 매장입니다”) 또는 `business_type_review_required`(“유통사 업종을 관리자에게 확인해 주세요”) 같은 제한된 사유/다음 행동으로만 제안한다. 상대 유통사 이름·ID·연결 수·분류 목록을 매장에 노출하지 않는다. 이 코드는 **제안 계약**이며 아직 실제 RPC 응답이 아니다.

### 관리자 변경과 기존 연결의 영향 검토

- 배정 변경·분류 통합/폐기로 기존 연결의 교집합 결과가 바뀌면 영향 매장/연결을 **관리자 검토 대상으로 기록**한다. 기존 연결을 자동 해제·폐쇄하거나 회원을 제거하지 않는다. 기존 주문 취소·가격 재계산·원장/재고 변경도 하지 않는다.
- 표시명만 바뀌고 ID 집합이 같으면 연결 판정은 그대로다. 재검토 대상의 기록은 동일한 분류 변경 버전과 영향 연결에 대해 중복 생성되지 않아야 한다. 관리자에게만 변경 전/후 ID 집합·변경자·시각·영향 대상을 제한해 제공한다.
- 검토 기록은 신규 연결·첫 주문을 무조건 허용하는 예외 승인이 아니다. 서버는 현재 분류 집합을 재확인하고, 충돌/미확정이면 기존 토큰으로 우회하지 못하게 제한된 사유만 반환한다. 기존 거래의 반복 주문에 추가 제한을 둘지와 관리자 검토 해소 방식은 별도 계약으로 명시하고 09가 자동 차단 범위를 넓히지 않는다.
- 기존 text 값은 참고용으로만 남기고 관리자 확정 없이 다중 분류로 자동 변환하지 않는다. 분류 집합/변경 버전의 읽기, 영향 검토 기록의 보관·권한·재시도, 변경과 연결/첫 주문이 경합할 때의 일관성은 서버 선행 계약이다. 이 PR은 테이블·API·영향 기록 작업을 새로 구현하지 않는다.

**현재 막힘:** 안정적인 ID/표시명·다중 배정·관리자 전용 쓰기·영향 검토 계약과 공통 연결/첫 주문 판정 RPC가 아직 연결되지 않았다. 기존 text 분류 칼럼만으로 이 확장 계약을 구현했다고 주장하지 않는다. 08 관리자와 06 회사 설정/서버 경계의 담당 조정 후 연결한다. 이 선행 전에는 다섯 조건을 전부 통과했다고 표시하지 않는다. 09는 만료 안내만 독립적으로 검증했고 첫 주문 전체 완료를 주장하지 않는다.

후속 계약 검증표: ID 하나라도 겹치면 차단/교집합 없으면 다른 조건 확인/미분류 관리자 확인, 이름만 바꿔도 결과 불변/ID 재사용 금지, 다중 배정의 중복 ID 정리, 관리자 변경 후 기존 연결 자동 해제0·영향 검토 기록 멱등, 첫 주문 재확인·변경 경합, 타사 회원·매장 식별 위조 거절, 자기 회사 중복 오판 없음, 닫힌 연결의 범위 확정, 동시 같은 업종 연결 경합, 경쟁사 이름·ID·분류 비노출, 회사별 금액·원장 분리. 현재 PR의 만료 화면 시험 통과와 이 후속의 미검증을 구분한다.

## ⑦ 만료 화면의 현재 구현 범위

기존 공개 링크/문서와 CX-70·#1225의 문의 계약을 재사용한다. 새 `PUBLIC_DOCUMENT_ORDER_GUIDANCE_ENABLED=true`와 `FEATURE_PUBLIC_DOCUMENT_ORDER_GUIDANCE_COMPANY_IDS`의 발행 회사 허용이 모두 있어야 새 안내를 표시한다. 기본 OFF, 리드 전용 링크에는 추가하지 않는다.

가격 만료·링크 열람 가능: 흐린 목록, 가격 null 유지, 주문 불가, 새 단가표 요청 안내. 영업 키트의 직접 번호와 publicContactEnabled=true일 때만 큰 전화번호/48px 문의 링크. 미설정·조회 실패에는 기존 안내, 비공개 contact/대표 번호 fallback 없음. 링크 회수·열람 만료 시 목록·번호 모두 기존 차단을 유지한다. 기존 게시본/주문 버전과 주문 접수 코드는 바꾸지 않는다.

와이어프레임 근거: `docs/design/store-wireframe-2026-11-17/Expired.dc.html`(⑦), `Check.dc.html`(③), R13 next-wave CX-93. 차이: 만료 가격/수량은 조작 불가 상태로 유지하고, 개인 담당 번호를 임의 공개하지 않는다. ③은 위 선행 계약 미확정으로 구현 완료를 주장하지 않는다.
