## M-1 "다시 계산 필요"를 서버 기준으로 (#171의 제한 해결)

- 지금은 매입가를 저장한 브라우저에만 남는다. 다른 기기, 다른 직원, 단가표 목록 카드에는 보이지 않는다.
  - 이는 **"UI에서 상태를 숨기거나 꾸며서 해결하지 않는다"(CLAUDE.md 4절) 위반**이라 바로 고친다.
- **DB 변경 없이 서버에서 계산한다.**
  - 문서의 게시 version(`pricing_document_versions.published_at`)보다 **나중에** 그 문서에 담긴 품목의 가격이 바뀐 기록(`price_recalc_changes` / 매입가 원가 이력)이 있으면 "다시 계산 필요"로 본다.
  - 바뀐 품목 수도 함께 센다.
- 쓰는 곳: 견적서·단가표 목록 카드와 상태 열, 매입가 반영의 "영향받는 문서" 카드. 브라우저 저장은 지운다.
- 테스트(단위): 게시 → 매입가 변경 → 필요 표시 → 다시 계산 · 재게시 → 표시 사라짐.

## S-2 영업 핵심 흐름 끝까지 연결 (스프린트 중심)

**목표 흐름** — 대표가 하루 안에 끝까지 해볼 수 있어야 한다:

1. 신규 리드 / 영업 리드에서 매장을 고른다 → 연락 기록(문자 · DM · 방문)
2. 그 리드에서 **[견적서 만들기]** → 단가표를 복사해 품목 · 가격 조정(QuoteEditor) → 게시
3. **공유**: 링크 또는 카톡 문구 복사. 매장이 링크를 연다(열람 기록이 리드 / 거래처 기록에 남는다)
4. 매장이 **[이 견적으로 거래 시작]**(수락)을 누르거나, 직원이 대신 수락 처리한다
5. 수락하면 한 번에 처리한다:
   - 리드 → **거래처 전환**(이미 거래처면 연결)
   - 견적 품목 → **협의 단가**(`customer_price_agreements`, 가격 우선순위 0)
   - 그 거래처의 **매장 주문 링크**를 자동 발급할 수 있게 한다(버튼 한 번)
6. 매장이 링크로 첫 주문 → 오늘 현황 / 성과에 "견적 → 첫 주문" 전환으로 집계한다

**데이터**(계약서 2 · 4 · 6절 기준)
- `pricing_documents`(kind=quote)에 연결 칸을 추가한다: `customer_id`, `lead_id`, `status`(draft · published · sent · viewed · accepted · expired · cancelled), `accepted_at`, `accepted_by`(매장 / 직원).
  - 또는 같은 역할의 별도 테이블. 어느 쪽이 나은지 승인 표에 이유를 적는다.
- `customer_price_agreements`: 초안 `order-and-purchasing-foundation.sql`의 정의를 계약서에 맞게 따로 떼어 낸다(effective_from/until, source_quote_id → pricing_documents).
- **수락 RPC 하나**(트랜잭션 · idempotency_key): 상태 accepted + 거래처 전환/연결 + 협의 단가 생성.
  - 두 번 눌러도 결과는 하나다(계약서 I-7).
- 기존 `sales_quotes` 수락 API는 그대로 둔다. 리드 화면의 새 견적은 pricing_documents로 만든다(계약서 2절).
- 가격 결정 함수: 우선순위 0(협의 단가)을 매장 링크 가격에 반영한다(계약서 6절).

**DB 승인 표**
- `db-approval-queue.md`에 "S-2 영업 흐름" 묶음으로 올리고 **멈춘다.** Claude가 검토하고 대표가 승인한다.
- 승인 전에도 할 수 있는 것은 PG17로 먼저 만든다: 화면 · API · RPC 코드 · 테스트(플래그 `QUOTE_ACCEPTANCE` OFF).

**완료 기준**
- 위 1~6을 Playwright E2E 하나로 통과한다(테스트 회사 · 가상 매장).
- 수락이 두 번 와도 협의 단가와 거래처가 하나만 생긴다.
- 협의 단가가 링크 주문 가격에 우선 적용된다.
