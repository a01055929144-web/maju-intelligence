# MAJU 단계 완료 기준과 병렬 작업 경계

> 2026-11-07 기준. 진행률은 파일 수가 아니라 대표 회사의 고객 행동으로 판정한다. 운영 DB 쓰기·기능 활성화·배포 승인은 이 문서에 포함되지 않는다.

완료 전 단계의 코드·설계·테스트는 병렬로 준비할 수 있다. **완료 표시와 다음 단계 운영 확대는 위 순서를 지킨다.** 새 화면·테이블보다 기존 업로드 표, 문서 편집기, `/store`, TMS 코스, ERP 원장을 재사용한다.

## 현재 확인된 차단점

- A: Draft PR #333은 날짜별 원가 저장·P0 재계산·복구를 단일 DB 트랜잭션으로 묶고 PostgreSQL 17에서 검증했다. 그러나 운영 SQL 미승인, 기능 OFF, 신규 상품 생성·exact ID 매핑·09 UI 호출 미연결이므로 실제 파일 전체 경로는 아직 완료가 아니다. 1,000개 이상 조회 잘림 위험도 앱 연결 전에 확인한다.
- B: 실제 리드 전달의 원자적 기록은 Draft PR #285의 미승인 SQL에 의존한다.
- C: 기존 주문 링크 발급은 거래처 ID를 요구하지만 공개 수락에서 거래처 연결·링크 발급으로 이어지는 앱 호출이 없다. 점주 첫 개통 SQL은 별도 승인 대기다.
- D: 기존 TMS는 `store_orders.id`를 읽지 않는다. 주문 ID별 배송 완료 계약이 없다.
- E/F: 수기 전표·재고와 기초 운영 화면은 있으나 주문·배송 원천과 끝까지 연결되지 않았다.

## 충돌 방지

1. A 수정은 `purchase-cost-workspace`와 직접 테스트로 한정한다. 04의 거래처 가져오기 RPC 전환 파일과 겹치지 않는다.
2. 09는 문서·공개 주문, 03은 수락·거래처, 07은 인증, 02는 TMS를 소유한다. 생산자가 계약을 병합한 뒤 소비자가 최신 main 위에서 연결한다.
3. `lib/store.ts`, 메뉴, 백엔드 계약, 중앙 DB 승인표는 컨트롤타워만 조정한다.
4. 운영 변경은 명시 승인, PG17·CI, 적용 후 읽기 확인 순서로 진행한다. 실데이터 쓰기 검증은 별도 승인 범위에서만 한다.

## A 단계 최신 증거와 남은 검증

### 확인된 합성·자동화 증거

- Draft PR #333, head `ae8aeb2`, CI run `42378753598`: PostgreSQL 17, migration approval, 전체 build 모두 성공.
- PostgreSQL 17 합성 fixture에서 매핑 완료된 745개 상품·3,417개 원문 거래행을 한 트랜잭션으로 저장했다. 같은 품목·날짜의 반복 원문도 `source_row_number`별 receipt로 보존했다.
- 품목별 선택/보류, 과거 날짜 현재가 보호, 기준일 미확정 기존가의 기본 보호와 명시 교체, 신규 미가격(가격 0·날짜 없음), 공급처별 최신 원가를 검증했다.
- 동일 배치 멱등 재시도, 변경된 본문 재시도 거부, 중간 실패 전체 롤백, 회사 격리, `service_role` 실행 제한을 검증했다.
- 원가 저장과 P0 판매가 재계산을 같은 트랜잭션에서 실행하고, 강제 재계산 실패 시 부분 저장이 없으며 최신 배치 복구 시 원가·판매가·receipt/history가 함께 되돌아감을 검증했다.
- 3,417행 합성 저장 실행 시간은 CI PostgreSQL 17에서 2.051초였다.

### 아직 실제로 검증하지 않은 범위

- 대표 파일의 실제 분포인 188개 상이 단가 충돌과 빈 단위 1,552행을 #333 PG fixture 하나로 재현하지 않았다. SQL은 선택/보류 및 빈 단위 저장을 허용하지만, 해당 수량은 09 UI 합성 검사 또는 실제 파일 승인 테스트가 필요하다.
- 실제 파일에서 신규 상품 생성 → exact ID 매핑 → #333 호출 → 화면 재조회까지 연결된 브라우저/운영 스모크가 없다.
- 운영 DB에는 SQL을 적용하지 않았고 실데이터 쓰기·읽기·복구를 실행하지 않았다.
- 따라서 A 단계는 완료 표시할 수 없으며 운영 확대도 금지한다.
