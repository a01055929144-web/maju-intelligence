# MAJU 단계 완료 기준과 병렬 작업 경계

> 2026-11-08 현황. 아래 비율은 병합된 구현 체크이며, 단계 완료는 대표 회사의 실제 행동으로만 판정한다. 이 문서는 운영 DB 쓰기·플래그 활성화·배포 승인이 아니다.

## 현재 차단점과 승인 경계

- B: 실제 공유 준비·열람은 대표 회사의 전역 공유 플래그가 OFF라 운영에서 확인할 수 없다. 실제 메시지 발송은 별도 범위다.
- C: 점주 첫 개통 SQL은 미승인·미적용이며 기능 OFF다. #368 열람 전용 링크 SQL도 별도 운영 승인 대기다. 회원 주문 화면의 저장 중 재시도 안전성은 #383, 구성원 권한 회귀는 #385로 검증했다.
- D: #367 배송 후보 기본 제외 SQL과 #378 제품 코드는 Draft/OFF다. 02의 주문 ID 생산자 계약이 먼저 필요하다.
- E: #384는 최신 ERP 원장을 재사용하는 승인 전 SQL 초안이다. 전표 생성 단일 주문 상태와 운영 SQL 승인이 확정되기 전 실행하지 않는다.
- F: 주문→배송→매출의 원천 ID가 없어서 전환율이나 오류 큐를 추정값으로 만들지 않는다.
- **운영 DB 변경·기능 ON·실제 발송/수락/주문·배포는 이 진행률만으로 실행하지 않는다.**

## 병렬 작업 충돌 방지

1. 04는 업로드·상품·실제 파일 미리보기, 09는 문서·매장 주문 UI, 05는 전달 기록, 03은 수락·전표, 07은 인증·회원 경계, 02는 배송 생산자, 01은 지도·코스 소비자를 소유한다.
2. 06은 퍼널, 08은 관리자 오류를 담당한다. D/E 원천 ID가 생기기 전에는 합성 지표를 운영 수치로 제시하지 않는다.
3. `lib/store.ts`, 메뉴, 백엔드 계약, 중앙 DB 승인표와 이 체크리스트는 컨트롤타워가 조정한다. 같은 파일은 먼저 병합한 쪽의 최신 main을 기준으로 다시 맞춘다.
4. 운영 변경은 명시 승인 → PG17·CI → 적용 후 읽기 검증 순서다. 실데이터 쓰기는 기존 승인 범위와 최종 화면 확인을 함께 지킨다.
