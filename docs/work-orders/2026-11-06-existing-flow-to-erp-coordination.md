# 기존 흐름을 ERP까지 잇는 작업 지시와 충돌 방지표

> 2026-11-06 · 문서 전용. 기준: `main` d7ee963과 [제품 큰틀](../strategy/2026-11-06-maju-platform-blueprint.md), [백엔드 계약](../backend/00_BACKEND_CONTRACT.md). 시작할 때 최신 main과 운영 플래그·SQL 적용 상태를 다시 확인한다. 이 문서는 배포·운영 DB 변경 승인이 아니다.

## 1. 목표와 이미 있는 것

고객이 **매입가 엑셀 → 상품 확인 → 마진·판매가 → 견적서/단가표 게시 → 공유 링크 → 첫 주문 → 배송 → ERP 전표·재고·정산**을 한 데이터로 처리하게 한다. 기존 ERP를 유지하는 회사는 앞 단계만 사용해도 된다. 현재 업로드·매입 이력/정정, `product_catalog`, 가격 재계산/복구, `pricing_documents` 편집·버전·인쇄, `storefront_links`, `store_orders`, TMS 코스, 수기 전표·재고 화면이 있다. **이 기능을 다시 만들지 않는다.** 각 방은 코드와 운영 적용 상태를 확인한 뒤 빠진 연결만 고친다.

`sales_quotes`·`sales_transactions` 같은 레거시는 자동 이전·삭제하지 않는다. 판매 관리의 매입가 업로드는 가격 계산용이며 ERP 매입전표를 생성하지 않는다. 매장 응답에는 매입가·원가·마진·매입처를 넣지 않는다.

## 2. 단계와 고객 완료 기준

| 순서 | 고객 행동과 기존 재사용 | 완료 판정 | 다음 단계 조건 |
| --- | --- | --- | --- |
| A. 판매 준비 | 04: 기존 엑셀 열 맞추기·상품 연결·매입 이력/정정. 09: 기존 마진·판매가 재계산/복구 | 신규/기존 품목, 인상/인하/동일가, 단위·규격을 1개 파일로 확인하고 재업로드해도 예측 가능 | 원가와 판매가의 기준 ID·시각을 서로 확인 |
| B. 영업문서 | 09: `pricing_documents`의 sheet/quote 공통 편집기, 행사·임박 줄, 게시 버전·미리보기·인쇄 | PC/390px에서 규격·단위·과세가 읽히고 게시본 가격이 고정됨 | 문서/버전/상품 스냅샷 계약 확인 |
| C. 공유·첫 주문 | 09: 기존 링크·`/store`·장바구니·주문 이력. 03: 거래처 연결·수락·협의 단가. 07: 매장 구성원 권한 | 기존/신규 매장이 링크로 주문, 같은 요청 두 번에 주문 1건, 회사 간 비노출 | SQL·플래그 적용은 별도 승인 |
| D. 주문 운영·배송 | 09: 주문 확인·마감. 02: 기존 권역·코스·배송 완료 | 주문 ID로 접수→배정→완료를 추적, 수동 코스도 유지 | 상태·수량·권한 계약과 PG 테스트 |
| E. ERP 선택 연결 | 03: 주문→기존 매출전표·거래처원장. 04: 입고→기존 매입전표·재고 원장. 08: 품질·운영 집계 | 기능을 켠 회사에서만 확정·취소·반품 후 전표/원장/재고 합계 일치 | 운영 DB 승인, 회사별 플래그, 복구 시나리오 |
| F. 분석·확장 | 05: 영업 전환, 06: 성과, 08: 관리자 품질 | 원천 ID로 수치를 재계산 가능 | A~E 원천 정의 안정 후 |

**현재 실행은 A와 B/C의 단절 점검부터.** D~F는 앞 단계의 완료를 기다리며 읽기 조사·설계만 할 수 있다. 모든 단계는 기존 화면에서 성공한 고객 동작으로 판정한다.

## 4. 동시 작업·병합 규칙

1. **공유 파일 잠금:** `lib/store.ts`, `lib/customer-navigation.ts`, `AGENTS.md`, `docs/backend/00_BACKEND_CONTRACT.md`, `docs/work-orders/db-approval-queue.md`는 컨트롤타워가 단독 소유한다. 방은 변경 필요와 호출 지점을 먼저 보고한다. 컨트롤타워가 한 번에 한 PR로 반영하거나 소유자를 지정한다.
2. 04는 업로드/상품, 09는 가격/문서/`/store`, 03은 거래처/전표, 02는 코스, 07은 인증 경계를 소유한다. 공통 API·타입 수정은 **생산자 한 방**이 하고 소비자는 병합 후 rebase한다. 두 방이 같은 파일을 동시에 편집하지 않는다.
3. 각 방은 별도 기능 브랜치와 기존 작업트리를 사용한다. 최신 main을 확인하고 변경 파일 목록을 먼저 컨트롤타워에 알린다. 중복 발견 시 먼저 시작한 변경을 그대로 늘리지 말고, 이미 병합된 부품을 재사용한다.
4. UI는 현재 공통 표·필터·편집기·모달·상태·빈 화면을 쓴다. 삭제/보관 동작은 기존 **🗑️** 버튼·문구·권한 패턴을 확인해 맞춘다. 별도 화면/컴포넌트는 기존 것으로 고객 행동을 완료할 수 없을 때만 만든다. PC와 390px 둘 다 확인한다.
5. 한 PR은 고객 행동 하나와 그 검증만 담는다. SQL이 필요하면 **방별 승인 문서**에 초안·down·PG17·대상 건수·회사 격리·플래그 기본 OFF를 적는다. 중앙 승인표는 컨트롤타워만 갱신한다. 운영 SQL·데이터 쓰기와 돈/로그인 기능 ON은 별도 대표 승인 전 금지.
6. 병합은 의존 순서 **04 상품/매입가 → 09 가격/문서 → 03 거래처·수락 → 09 주문 → 02 배송 → ERP**를 지킨다. 독립 읽기 조사·문서 PR은 병렬 가능하다. 배포 전 전체 흐름 스모크, 실패 시 롤백.

## 5. 매 PR 체크리스트

- [ ] 최신 main·미병합 PR·운영 플래그/SQL 상태 확인. 기존 기능의 실제 경로를 재현했음
- [ ] 담당 파일과 다른 방의 변경 파일이 겹치지 않음. 공통 파일은 컨트롤타워 조정 완료
- [ ] Ponytail로 기존 부품/표/🗑️ 패턴을 먼저 찾고 가장 작은 수정 선택. 코드 PR 본문 첫 줄 `Ponytail: 사용함`
- [ ] 기존 URL·문서 버전·가격/과세·주문 이력·회사 격리·매장 원가 비노출 유지
- [ ] 빈 화면/오류/권한 안내, PC·390px 확인. 화면 변경은 Playwright 또는 CI 결과와 스크린샷 기록
- [ ] 영향 테스트, `tsc`, lint, build 통과. 돈/권한/DB는 PG17·인증 경계 검증
- [ ] 운영 DB 변경·플래그 ON·배포는 승인 상태를 명시. 미검증은 “완료”로 쓰지 않음
- [ ] PR에 고객 동작, 변경 파일, 재사용 부품, 남은 문제, UI 후속, 승인 필요 여부 기재

## 6. 작업방 보고 형식

`[방 번호] 고객 행동 / 재사용한 것 / 바꿀 파일 / 다른 방과의 접점 / PR·CI / 현재 막힘 / 다음 1건`. 컨트롤타워는 이 보고를 모아 의존 순서와 공유 파일 잠금을 갱신한다. 각 방의 과거 대화·기존 기능을 폐기하거나 대규모 재작성하지 않는다.
