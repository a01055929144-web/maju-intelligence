# CX-93 업종 중복 판정 서버 계약 초안

Ponytail: 사용함

## 범위와 선행

09 소유 서버/RPC 계약. #1240의 distributor_industry_categories 및 company_distributor_industries 안정 UUID를 재사용한다. 표시명과 companies.business_type은 판정 근거가 아니다. 같은 매장은 store_profile_id로 식별하므로 별도 매장 업종 복제 테이블은 만들지 않는다. 08 관리자/07 가입/06 회사 설정 파일은 변경하지 않는다.

SQL 초안 + down + 합성 PG17 시험만 제공한다. 실제 연결·첫 주문 변경 RPC에는 아직 연결하지 않았다. 운영 적용·기능 ON·배포 없음. UI 변경 없음(1440/390 재촬영 대상 아님).

## 호출 계약

- check_store_distributor_industry_v1(company, profile, user): eligible / same_industry_connection / business_type_review_required / store_member_unavailable만 반환. 경쟁사명·식별자·건수 반환 금지.
- assert_store_distributor_industry_v1: eligible 이외는 같은 이유 코드로 예외. 공개 브라우저 실행 권한 없음; service_role 내부 호출만 허용.
- 회사는 서명된 문서/검증된 서버 범위, 사용자는 검증된 세션, profile은 활성 회원 연결로 결정한다. 브라우저가 넘긴 세 값을 그대로 신뢰하면 안 된다. 이 함수의 service_role 실행 권한 자체는 회사 인증을 대체하지 않는다.
- 활성 profile/member/app_user 확인 → profile FOR UPDATE → 회원/사용자 FOR SHARE → 회사 ID 순 FOR SHARE → 분류 ID 순 FOR SHARE. READ COMMITTED만 허용한다. 다른 격리 수준은 cx93_read_committed_required로 실패한다.
- 신규 연결 생성/활성화 또는 첫 주문 저장과 **동일 DB 트랜잭션**에서 assertion을 실행해야 한다. HTTP 사전 확인 후 별도 쓰기, 캐시한 eligible, 승인 토큰 재사용은 금지한다. 실제 호출 RPC의 기존 잠금 순서를 먼저 대조해야 한다.
- 대상 회사와 같은 매장의 활성 연결 중 활성 회사들의 분류를 비교한다. 자신은 제외, 교집합 하나라도 있으면 차단한다. 미분류 또는 중단 분류는 관리자 검토로 보낸다. 이름 변경은 결과에 영향 없다.
- 관리자 변경은 기존 연결/주문을 자동 해제하지 않는다. #1240의 영향 preview를 관리자 검토에 활용하되 지속 검토 큐 객체는 아직 없다.

## 정확한 미완료 선행

1. 연결을 생성/재활성화하는 실제 RPC 전체의 단일 트랜잭션 호출 지점과 잠금 순서 합의. 새 회원은 검증된 회원 생성 후 활성 연결 쓰기 전 같은 거래에서 판정해야 한다.
2. 실제 주문 접수 RPC 내부의 첫 주문 정의·조회 조건·멱등 재시도 순서 합의. 기존 성공 요청 재시도가 이후 분류 변경으로 실패하지 않게, 저장된 멱등 결과 반환 경계를 보존해야 한다. 지금 이 SQL은 주문을 생성하지 않는다.
3. store_profile_id 없는 구형 계정의 검증된 profile 연결 선행. 임의 회사/매장 ID 추정 금지.
4. 런타임 통합 시 기존 isFeatureEnabled 회사별 허용 목록 체계 사용, 기본 OFF. 새 전역 우회 스위치나 중복 환경변수를 만들지 않는다. 현재 호출자 자체가 없어 운영 실행은 없다.

## 시험과 되돌리기

전용 workflow CX93 industry guard PG17은 이름이 고정된 일회용 PG17 DB만 사용한다. #1240 실제 SQL → 현재 SQL → 허용/단일·다중 교집합/미분류/회원·회사 격리/중단·이름 변경/권한 → 동일 매장 동시 연결(한 건만 저장) → 지원 안 하는 격리 수준 거절 → down 순서. 실제 고객 데이터/키 사용 없음. 시험 결과는 PR CI에 기록한다. 관리자 배정 변경이 판정 거래의 회사 잠금에서 대기한 뒤 다음 판정부터 반영되는지, 실패한 연결 거래의 rollback 뒤 대기 요청이 성공하는지 함께 확인한다.

down은 두 함수만 제거하며 연결/분류 데이터를 지우지 않는다. 실제 호출자 도입 뒤에는 호출자부터 제거해야 한다.
