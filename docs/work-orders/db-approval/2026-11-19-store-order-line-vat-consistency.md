# 매장 주문 행별 부가세 일치 — DB 승인 초안

Ponytail: 사용함

## 변경 범위

- 운영 적용 없음. SQL up/down과 일회용 PostgreSQL 17 시험만 추가한다.
- 공개 주문 함수의 OID, 권한, security 속성을 보존한 채 기존 본문을 정확히 한 번만 치환한다.
- 문서 주문은 게시 행의 `priceIncludesTax` 불리언을 주문 행 스냅샷으로 사용한다. 키가 없는 기존 게시 문서는 종전의 `false` 의미를 유지한다.
- 계정 주문의 적용 행사가는 고객이 보는 최종 고정가다. 과세 행사에 VAT를 다시 더하지 않는다.
- 행사 행은 약속가보다 우선한다. 일반 행은 기존 약속가 해석을 유지한다.

- CX-75 적용 전에는 공개 주문 함수, 적용 후에는 `cx75_*_impl`을 찾아 같은 본문만 패치한다.

## 운영 적용 선행 관계

1. #1154가 새 문서 행에 `priceIncludesTax`를 명시하고 기존 게시 버전을 재작성하지 않아야 한다.
2. main `f733862`의 CX-38b 주문→전표 스냅샷 SQL을 먼저 up하고 해당 PG17 대사를 통과한다.
3. 같은 커밋의 CX-66 부분출고 호환 SQL을 다음으로 up하고 `snapshot_ambiguous` 회귀시험을 통과한다.
4. 순서 `CX-38b → CX-66 → 06 주문 VAT SQL`을 지켜 이 주문 producer SQL을 마지막에 up하고 PG17 금액 대사를 통과한다.
   06 up은 CX-38b의 `price_includes_tax_snapshot` 열과 CX-66 부분출고 함수의 포함가 스냅샷/중복 모호성 계약 마커를 실행 시점에 확인하며 하나라도 없거나 구버전 본문이면 fail-closed로 중단한다.
5. 롤백은 반대로 `06 주문 VAT SQL → CX-66 → CX-38b` 순서로 down한다. 새 스냅샷 주문이 남아 있으면 어느 down도 진행하지 않는다.
6. 위 단계가 함께 통과하기 전에는 기능 플래그·운영 배포를 진행하지 않는다.

06방은 CX-66/CX-38 파일을 수정하지 않는다. 이 PR의 PG17 주문 대사는 producer 자체 검증이며, 전체 주문→전표→부분출고 검증은 04방 호환 시험 통과를 선행 조건으로 삼는다.

병합·기능 ON의 최종 문턱은 09방 행별 표시 수정까지 합친 단일 합성 흐름이다. 일반 과세가, 면세가, 행사 고정가, 임박 고정가를 함께 표시하고 `60 × 1.500` 및 배송비를 주문한 뒤, 주문 행 → 전표 → 부분출고의 공급가·세액·최종금액이 모두 같아야 한다. 이 종단 대사가 없으면 개별 PG17 시험이 통과해도 병합하거나 기능을 켜지 않는다.

#1157 공개 값과의 연결 기준은 새 계약의 일반 과세 `1000/priceIncludesTax=false`, 과세 행사 `1100/true`, 과세 임박 `60/true`다. 면세는 표시 설정과 무관하게 VAT 0으로 원 금액을 유지하며, 06 시험은 면세 행사 60원도 별도 행으로 검증한다.

## 검증 결과

- 2026-11-19 로컬 일회용 PostgreSQL 17에서 CI와 같은 member-order 선행 스키마, 고정 배송 SQL `220b9c1`, CX-75 회귀를 구성한 뒤 `store-order-vat-consistency.pg17.test.sql` PASS.
- 행사 1,100원 포함 고정가, 행사 비대상 일반가/별도가 fallback, 과세 임박 60원 × 1.500, 면세 계란 60원 × 1.500, 배송비 7원, 주문 합계, 멱등 재시도, 활성 스냅샷 down 거부와 정리 후 exact down을 실제 DB에서 확인했다.
- 최신 main `8b2c50a`에서 새 일회용 PostgreSQL 17 DB를 만들고 CI member-order 선행 12개 → CX-75 실제 ERP fixture/고정 배송 SQL `220b9c1` → CX-38 → CX-38b → CX-62 → CX-66 전체출고 → CX-66 부분출고/잔량취소 → CC-29b → 06 producer 순으로 실제 적용했다.
- CX-75 회귀가 단순 fixture 정리에서 `product_catalog.default_sales_price`를 제거하므로 CC-29b 직전에 이 열을 복원했다. 이 열은 운영 정의 `20261009012401_sales_quote_operations.sql`에 실제 존재하며, 운영에 없는 시험 전용 필드를 만든 것이 아니라 축약 fixture와 운영 스키마의 차이를 메운 것이다.
- 같은 DB의 `document-order-vat-journey.pg17.test.sql`에서 #1150 함수-only 합성 기준 → #1155 실제 SQL → #1157 실제 SQL 순서를 적용했다. #1150 운영 SQL 자체와 운영 행은 적용하지 않았으며, 합성 기준은 #1150 제안 함수의 고정 MD5 `41cf8da78afe5fedb6d06108614a07f0`만 재현한다.
- 일반 과세, 면세, 과세 행사, 면세 임박, 포함가 소수수량, 과세 임박의 6건 모두 저장/발행 → 주문/멱등 재시도 → draft 전표 → 부분출고/잔량취소를 통과했고 최종 표식 `DOCUMENT_ORDER_REAL_ERP_PARTIAL_PASS`를 확인했다. 주문 행·전표 행의 공급가/세액/합계, 단일 원장, 재고 이동까지 대사했다.
- up 전에 이미 활성 과세 행사가 있고 up 뒤 새 주문은 0건인 기준에서도 down은 거부되고 patch가 유지됨을 별도로 재현했다. 이는 과거 주문 보호가 아니라 down 뒤 같은 활성 행사로 생성될 미래 계정 주문의 VAT 중복을 막는 배포 롤백 문턱이다. 기존 행사를 예외 처리하면 보호를 우회하므로 guard는 완화하지 않는다.
- 활성 링크 폐기와 과세 행사 종료 뒤에도 포함가 스냅샷 행을 가진 미접수 주문이 전표 없이 남아 있으면 down을 거부한다. 해당 주문을 취소하거나 CX-38b 소비자로 전표 전환해 잔존 건을 0으로 만든 뒤에만 `06 → CX-66 → CX-38b` 역순 rollback을 허용한다.
- 전표 헤더만으로는 drain으로 인정하지 않는다. `draft`/`confirmed` 판매전표에서 대응하는 모든 포함가 주문 행의 상품·수량·단가·포함가·공급가·세액·합계 스냅샷이 실제 전표 행과 일치해야 한다. 빈 전표, 취소 전표, `snapshot=false`, 금액 불일치는 down을 계속 차단한다.
- 값이 같은 주문 행이 여러 개면 동일 값별 주문 행 수 이상으로 전표 행이 있어야 한다. 빈 단위와 `EA`는 전표 계약과 똑같이 `EA`로 정규화해 묶으며, 한 전표 행을 여러 주문 행의 증거로 재사용하지 않는다.
- 위 결과는 승인 전 SQL의 일회용 DB 검증이며 운영 적용·기능 ON·배포를 뜻하지 않는다. #1150 실제 up 적용 검증은 그 SQL의 별도 승인/실행 범위에 남는다.

## 되돌리기

- 활성 링크가 명시적 행 VAT 스냅샷을 참조하거나 활성 과세 행사가가 있으면 down은 거부한다.
- 포함가 스냅샷 행을 가진 `submitted`/`received` 주문에 완전한 `draft`/`confirmed` CX-38b 전표가 없으면 down은 거부한다. 헤더 존재만으로는 부족하며 주문을 삭제·재계산하지 말고 정상 접수로 전표 행까지 만들거나 취소해 drain한다.
- 링크 폐기, 행사 종료, 미전환 주문 0건을 확인한 뒤 exact reverse patch만 수행한다.
