# S-2 시험 데이터 정리 계획 — 실행 전

운영 프로젝트 `fcmdvveqmcgtioelzqun`의 카탈로그만 SELECT로 확인했다. 이 방은 운영 시험 행을 생성·변경·삭제하지 않았다. 실행은 컨트롤타워 담당이다.

## 확인한 기술적 제약

2026-11-02 운영 `pg_constraint`·`pg_trigger` 읽기 결과:

- 관련 `store_%`·`pricing_document%` DELETE 사용자 트리거: 0개.
- P1 `pricing_version_immutable`는 UPDATE 트리거다. 이 이유로 DELETE 불가라고 단정할 수 없다.
- `customer_price_agreements`, `customer_pricing_document_links`, 수락 요청과 발송 기록은 게시 버전을 RESTRICT로 참조한다.
- 수락 요청→발송 기록, 발송 기록→원본 문서/게시 버전, 주문 링크→수락 요청은 RESTRICT다.
- 주문→게시 버전/링크는 NO ACTION, 주문→매장 계정/구성원은 RESTRICT다.
- 주문 줄·주문 멱등 요청→주문, 링크 이벤트·주문 멱등 요청→링크는 CASCADE다.
- 구성원 이벤트→구성원, 구성원→계정은 RESTRICT이며 계정 약관 동의자·구성원 초대/내보냄 행위자에는 순환 NO ACTION 참조가 있다.

따라서 **시험 행만 식별하고 종속 관계 역순으로 지우는 것은 기술적으로 가능할 수 있다.** 감사 정책상 보존해야 하는 실제 거래와 시험 행은 구분한다. DB 제약 확인을 업무상 보존 정책 확인으로 대신하지 않는다.

## 생성 전 준비

1. fixture UUID·company_id·생성 여부를 저장소 밖 manifest에 남긴다. 새로 만든 행과 기존에 매칭된 행을 반드시 구분한다.
2. 기존 데이터가 바뀌면 해당 행의 이전 값을 저장소 밖에 백업한다. 특히 기존 협의 단가 기간/상태, 매장 정보, 리드 연결, 활성 문서 링크는 새 행 삭제만으로 복원되지 않는다.
3. 시험 대상 키와 연결된 FK를 다시 확인한다. 실제 주문·배송·전표 등 manifest 밖 행이 참조하면 자동 정리를 중단한다.
4. 테이블 전체·회사 전체 삭제, 이름 prefix만으로 삭제, 트리거/제약 비활성화는 하지 않는다. 모든 변경은 company_id와 manifest UUID를 함께 제한한다.

## 역순 정리 초안

한 트랜잭션에서 대상 건수·참조를 먼저 검증하고 예상 범위를 벗어나면 롤백한다.

1. 시험 주문의 `store_order_requests`, `store_order_lines`와 시험 링크의 `storefront_link_events`를 제거한다. 이어 시험 `store_orders`를 제거한다.
2. 시험 `storefront_links`를 제거한다. 링크가 수락 요청을 참조하므로 수락 요청보다 먼저 제거한다.
3. 시험 협의 단가·문서 매장 연결(`customer_price_agreements`, `customer_pricing_document_links`)을 제거한다. 기존 값이 변경됐으면 백업으로 복구한다.
4. 시험 `pricing_document_acceptance_requests`→`pricing_document_sends` 순서로 제거한다.
5. 계정 시험을 했다면 주문 참조가 사라진 뒤 시험 구성원 이벤트를 제거하고, 시험 계정의 약관 동의자/시험 구성원 자기 참조를 해소한 뒤 시험 구성원→시험 계정을 제거한다. 기존 계정·구성원은 제거하지 않는다.
6. 시험 게시 버전→원본 문서→시험 상품 순으로 제거한다. 행사·세트·원가 이력 등 다른 참조가 생겼다면 먼저 실제 FK 목록에 반영한다.
7. 이번 시험에서 새로 생성된 거래처·리드·import만 추가 FK 확인 후 정리한다. 기존에 매칭된 거래처·리드는 삭제하지 않고 백업된 변경 칸만 복원한다.
8. manifest의 잔여 행 0건, 기존 데이터 이전 값 일치, 전체 증감 건수를 확인한다. 실제 시험 사용자 인증 계정도 인증 공급자 정책에 맞춰 별도로 관리한다.

`pricing_public_request_audit` 등 보안 감사는 운영 보존 정책을 따른다. 시험 요청이라고 임의로 지우지 않는다. 기술적 삭제 가능성과 감사 기록 보존 여부를 분리해 보고한다.

## 격리 검증과 운영 검증의 차이

- 합성 PG17: 실제 SQL·동시 멱등·가격/회사 FK·롤백·역순 정리 검증. DB 전체를 폐기할 수 있다.
- 격리 브라우저/API 대역: 화면·인증/권한 분기·RPC 인수·재시도 검증. 실제 카카오/NTS·운영 설정·DB 커밋을 증명하지 않는다.
- 운영 시험: 실제 카카오 계정·계속 사업자 확인·배포 설정·실제 주문 연결을 검증한다. 사업자번호 매칭이 기존 거래처에 닿을 수 있으므로 생성 전 manifest·변경 행 백업과 정리 범위를 확정해야 한다. 실제 대표 매장의 첫 실사용을 보존하는 방법도 대안이다.

이 계획은 DELETE 실행문이 아니며 운영 시험/정리를 실행하지 않는다.
