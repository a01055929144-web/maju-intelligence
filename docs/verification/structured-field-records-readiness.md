# 구조화 현장 기록 적용 전 점검 보고

작성일: 2026-10-29  
상태: 운영 적용 전 · 기능 플래그 OFF · 운영 DB 쓰기 미실행

## 읽기 전용 확인 결과

- 운영 `pg_proc`에 `record_delivery_event_atomic`, `record_lead_sales_offer_atomic` 함수가 아직 없다.
- 따라서 배송 사고·견적의 입력 → 저장 → 다시 열기 운영 검증은 시작하지 않는다.
- 신규 테이블 Data API 노출 정책 변경은 2026-10-30 기존 프로젝트에도 적용된다. 현재 설계는 브라우저 직접 접근이 아니라 서버의 `service_role` RPC 호출만 허용하므로 `anon`/`authenticated` 노출을 추가하지 않는다.

## 코드 준비 상태

- `/api/customer/structured-field-records`는 로그인 세션과 회사별 플래그를 먼저 확인한다.
- 플래그 OFF에서는 요청 body를 읽거나 Supabase를 호출하지 않는다.
- 배송 사고와 리드 견적 payload를 각각 원자 RPC 서명으로 매핑하는 단위 테스트를 준비했다.
- RPC SQL 초안은 회사 소유권, 멱등키, 헤더+items 동시 저장, 예외 시 전체 롤백을 포함한다.
- 배송 기록 재요청은 같은 멱등키의 기존 note/event를 그대로 반환한다. 다른 payload로 재요청해도 기존 메모·사고·품목을 갱신하지 않는다.

## 현재 오류·불편 목록

1. **운영 적용 대기**: 화면→구조화 저장 API→RPC와 최신 기록 재열기 연결은 준비됐지만 함수가 운영에 없어 플래그를 켤 수 없다.
2. **부분 성공 UX 확인 필요**: 사진 업로드·거래처 메시지 공유는 RPC 트랜잭션 밖의 외부 작업이다. 구조화 저장 성공 후 공유 실패를 사용자에게 분리 표시하고, 저장은 중복 없이 재사용하도록 구성했지만 운영 전 테스트 데이터로 확인해야 한다.
3. **견적 대상 범위**: 현재 초안은 리드 대상 `lead_actions + sales_offers(+items)`만 다룬다. 기존 거래처 대상 견적은 `customer_notes + sales_offers(+items)` RPC가 별도로 필요하다.
4. **다중 품목 편집 UX**: DB/API는 복수 items를 지원하지만 현재 모바일 폼은 샘플 1행과 단가 1행만 직접 편집한다.

## 적용 후 제한 검증 순서

1. Claude 검토와 대표 승인 후 RPC 마이그레이션 적용 여부·권한을 SELECT로 확인한다.
2. 테스트 회사 하나만 `STRUCTURED_FIELD_RECORDS_ENABLED_COMPANY_IDS`에 추가한다.
3. 배송 사고 1건을 저장하고 동일 멱등키 재요청 시 note/event/items가 각각 1세트인지 확인한다.
   같은 키에 다른 메모·품목을 담아 재요청해도 최초 저장 내용이 유지되는지 확인한다.
   처리 상태를 `completed`로 저장하면 `resolved_at`이 채워지고, `received` 또는 `in_progress`이면 비어 있는지 확인한다.
4. 앱을 닫았다 다시 열어 원인·단계·조치·품목·수량·공급처가 동일하게 복원되는지 확인한다.
5. 견적 1건을 저장하고 동일 멱등키 재요청, 가격·유효기간·샘플 품목 복원을 확인한다.
6. 고의로 잘못된 item을 보내 전체 저장이 롤백되는지 테스트 전용 데이터로 확인한다.
7. 사진·카카오 공유 실패를 재현해 저장 성공과 공유 실패가 분리 안내되고 재시도 중복이 없는지 확인한다.
8. 결과가 확인되기 전 다른 회사로 플래그를 확대하지 않는다.

## 이번 초안 검증의 제한

- SQL은 운영에 실행하지 않았다. 로컬 `psql`은 없고 Docker Desktop 엔진도 실행 중이 아니어서 실제 PostgreSQL 실행 검증은 남아 있다.
- 로컬 또는 격리된 PostgreSQL에서 위 재요청 시나리오와 회사별 접근 권한을 검증한 뒤 SQL 승인을 요청한다.
