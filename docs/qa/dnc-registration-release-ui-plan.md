# 연락 거부 등록·해제 UI 점검 계획

운영 SQL 적용과 `LEAD_DNC_WRITE_ENABLED=true` 전환 전에는 실제 등록·해제를 실행하지 않는다. 대상 Supabase 프로젝트는 대표가 별도로 승인할 때만 `fcmdvveqmcgtioelzqun`으로 고정한다.

## 이번 기능 브랜치에서 준비한 경계

- 회사·리드 범위 GET이 플래그 상태, 해제 가능 여부, 활성 DNC의 ID·채널·마스킹 값만 반환한다.
- 활성 DNC는 회사 전체 목록을 자르지 않고 채널+정규화 값으로 직접 조회하며, 방문은 `source_lead_id`로 조회한다.
- 화면은 플래그 OFF에서 등록·해제 버튼을 비활성화하고 운영 승인 전임을 표시한다.
- 플래그 ON에서는 채널별 등록과 owner/manager 해제를 제공하며 성공 후 상태를 다시 조회한다.
- 정규화 원문과 감사 metadata는 브라우저 응답에 추가하지 않는다.

## UI 구현 계약

1. 영업 채널별로 `연락 거부 등록`을 제공하고 채널, 현재 화면 값, 사유만 서버에 보낸다.
2. 활성 연락 거부 조회는 회사·리드 범위에서 수행하고 `dncId`, 채널, 마스킹 값, 사유, 등록 시각만 반환한다. 정규화 원문은 브라우저에 반환하지 않는다.
3. 해제는 owner/manager에게만 표시하고 사유를 필수로 받는다. legacy owner는 기존 DNC 전용 재검증을 그대로 통과해야 한다.
4. 플래그가 OFF면 조회 응답의 `enabled=false`를 사용해 버튼을 비활성화하고 검토 중 안내를 표시한다.
5. 등록·해제 성공 후 리드 상태와 활성 DNC 배지를 다시 불러오며, 실패 시 성공처럼 표시하지 않는다.

## 자동 회귀 테스트 준비

- 앱과 SQL 정규화: SMS의 빠진 0, 팩스 숫자화, `mailto:`, 인스타 URL·`@`·쿼리·예약 경로, 톡톡 끝 슬래시, 방문 문자열.
- 등록: 동일 연락처를 가진 두 리드가 함께 제외되고 같은 `dncId` 영업 이력이 중복 생성되지 않음.
- 해제: 다른 활성 DNC가 있으면 복원하지 않고, 반복 등록 주기에서는 현재 주기의 실제 변경만 복원.
- 권한: member 거부, active owner/manager 허용, legacy owner 회사·이메일 재검증 실패 시 fail-closed.
- UI: 플래그 OFF 비활성, 등록 사유 전달, 해제 사유 필수, API 실패 표시, 성공 후 재조회, 정규화 원문 미노출.

## 승인 후 실사용 점검 순서

아래 절차는 대표가 **현재 적용 대상 프로젝트 `fcmdvveqmcgtioelzqun`과 DNC RPC 운영 적용을 명시적으로 승인한 뒤에만** 시작한다. 승인 전에는 SQL 실행, 플래그 변경, 등록·해제 API 호출을 모두 금지한다.

### 1. 승인 증빙과 중단 조건 고정

1. 승인 기록에 프로젝트 ID, 적용할 `docs/sql-drafts/lead-do-not-contact-rpc.sql`의 커밋 SHA와 파일 해시, 적용 시각, 실행 담당자, 검증 담당자를 남긴다.
2. 검증용 회사·리드·채널과 기존 상태를 미리 기록한다. 실제 고객 연락처 대신 검증 전용 회사의 통제된 값을 사용한다.
3. 플래그를 즉시 OFF로 되돌릴 담당자와 방법을 정하고, SQL 되돌리기는 별도 승인이 필요한 후속 조치로 분리한다.
4. 프로젝트 ID 불일치, SQL 해시 불일치, 백업 확인 실패, 실행 주체 불명확 중 하나라도 있으면 적용을 중단한다.

### 2. SQL 적용 후 플래그 OFF 검증

1. 백업과 현재 함수·권한 상태를 기록한 뒤 승인된 SQL만 적용한다.
2. `normalize_dnc_value`, `mask_dnc_value`, 등록·해제 RPC가 예상 서명으로 존재하는지 확인한다.
3. 함수가 `security invoker`인지, `anon`·`authenticated` 실행 권한이 없고 `service_role`만 실행 가능한지 확인한다.
4. 애플리케이션은 `LEAD_DNC_WRITE_ENABLED=false` 상태로 배포한다.
5. GET 응답이 `enabled=false`, 빈 `entries`, 올바른 `canRelease`만 반환하고 화면의 등록·해제 버튼이 비활성인지 확인한다.
6. 이 단계에서는 RPC와 POST·DELETE API를 호출하지 않는다.

### 3. 제한된 쓰기 검증

현재 플래그는 회사별 허용 목록이 아닌 전역 플래그다. 따라서 테스트 회사 한 곳만 여는 방식이 불가능하다. 전역 노출 위험을 대표가 다시 확인한 뒤 짧은 검증 창에서만 ON으로 전환한다.

1. 플래그 ON 직후 검증용 회사에서만 등록을 1회 실행하고, 대상 리드가 `제외`·`연락 거부 등록` 상태가 되는지 확인한다.
2. 같은 정규화 값의 동일 회사 리드만 함께 제외되고 다른 회사 데이터는 변하지 않는지 확인한다.
3. 같은 값을 다시 등록해 활성 DNC와 영업 이력이 중복 생성되지 않는지 확인한다.
4. 화면에 없는 오래된 연락처로 등록해 HTTP 409와 최신 정보 새로고침 한국어 안내가 반환되는지 확인한다.
5. 일반 member 등록, member 해제, 잘못된 legacy owner 세션이 각각 403으로 거부되는지 확인한다.
6. owner 또는 manager가 사유와 함께 해제하고, 다른 활성 DNC가 없을 때만 이번 등록 주기에서 바뀐 리드가 복원되는지 확인한다.
7. 같은 DNC를 다시 해제해 HTTP 409와 이미 해제되었다는 한국어 안내가 반환되는지 확인한다.
8. 반복 등록 → 해제 주기에서도 이전 주기의 상태나 자유 텍스트가 복원되지 않는지 확인한다.
9. 감사 이력에는 DNC ID, 채널, 마스킹 값과 행위 정보만 있고 원문 연락처·이전 자유 텍스트가 없는지 확인한다.

### 4. 완료 또는 즉시 중단

- 회사 경계 위반, 원문 연락처 노출, 권한 우회, 중복 이력, 예상 밖 리드 복원, 한국어 오류 대신 내부 오류 노출 중 하나라도 발견하면 즉시 플래그를 OFF로 되돌린다.
- 플래그 OFF 뒤 POST·DELETE가 503으로 차단되는지 재확인한다. 생성된 감사 기록은 임의 삭제하지 않는다.
- SQL 롤백이나 검증 데이터 물리 삭제는 이 검증의 자동 후속 작업이 아니며 별도 승인 후 수행한다.
- 모든 항목이 통과하면 검증 시각, 회사·리드 ID, 요청 결과, 변경 전후 수량, 감사 행 ID를 기록하고 운영 활성화 여부를 다시 승인받는다.

## 남은 오류·보완점

1. **전역 플래그**: `LEAD_DNC_WRITE_ENABLED`는 회사별 제한이 없어 한 테스트 회사만 단계적으로 활성화할 수 없다. 운영 활성화 전 회사 ID 허용 목록을 추가하는 것이 가장 안전하다.
2. **조회 실패 안내**: 등록·해제 RPC 오류는 한국어로 변환되지만 활성 DNC GET 조회의 저장소 오류는 아직 전용 한국어 안내와 재시도 UI가 없다.
3. **장애 추적성**: 알 수 없는 RPC 오류는 내부 내용을 숨기지만 사용자에게 전달할 상관관계 ID와 운영 로그 연결이 없다. 민감정보 없는 요청 ID 로깅이 필요하다.
4. **비멱등 재시도**: POST·DELETE는 네트워크 오류에 자동 재시도하지 않는다. 등록은 DB 중복 방어가 있지만, 타임아웃 뒤 실제 성공 여부를 재조회하는 UI가 없다.
5. **운영 관측**: 등록·해제 실패율, 403·409 급증, 회사 경계 거부를 감시하는 지표와 알림이 없다.
6. **실데이터 부하 검증**: 동일 값 리드가 많은 회사에서의 잠금 시간과 전파 범위는 운영 데이터로 검증하지 않았다. 승인된 검증 창에서도 통제된 소량으로 시작해야 한다.
