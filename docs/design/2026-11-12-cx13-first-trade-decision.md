# CX-13 · CC-08 첫 거래 매장 거래처 확인 — 결정 사항 (2026-11-12, Claude Code → 컨트롤타워)

지시서: [R2 CX-13·CC-08](../dispatch/2026-11-11-R2-store-signup.md), 설계 5절 "첫 주문 확인"([매장 직접 가입](2026-11-11-store-direct-signup.md)). **결정 전에는 SQL·코드를 만들지 않는다.** 아래 추천대로면 CX-13 SQL 초안 1개 + CC-08 화면이다.

## 코드로 확인한 현재 상태
| 사실 | 근거 |
| --- | --- |
| 코드로 연결하면 **항상 새 거래처**를 만든다(기존 거래처에 이름·주소로 붙이지 않음). 이름은 매장 프로필 이름, `normalized_key='profile:<프로필 id>'`, 매장 계정은 `registration_pending`(사업자번호 미확인) | `docs/sql-drafts/20261111-CX-12-store-connect-by-code.sql` (운영 적용 11/12) |
| 거래처(`normalized_customers`)·매장 주문(`store_orders`)에는 **"확인 필요" 상태가 없다.** `needs_review`는 문서 수락 요청(`pricing_document_acceptance_requests`)에만 있다(#460 보류) | 스키마 확인 |
| 거래처 **병합은 이미 있지만**(`mergeDuplicateCustomers`) **매출 이력·메모·첨부만** 옮긴다. 매장 계정·매장 주문·공개 링크·계약 단가는 옮기지 않는다 → 코드로 만든 거래처를 기존 거래처에 합치려 하면 **그대로는 안 된다**(매장 계정이 가리키는 거래처를 지울 수 없음) | `lib/store.ts` 13484행 |
| 직접 가입·코드 연결은 스위치 OFF, 실제 매장 계정 0개. 그래서 **지금은 되돌릴 데이터가 없다** | 운영 읽기 |

## 결정 1. "확인 필요"를 어디에 두나
| | A. 거래처에 | B. 주문에 | **C. 매장 계정에 (추천)** |
| --- | --- | --- | --- |
| 내용 | `normalized_customers.review_status` | `store_orders.needs_review` | `store_accounts.customer_review_status`(`needs_review`·`confirmed`, 확인한 사람·시각) |
| 장점 | 거래처 화면이 바로 보여 줌, 한 곳에서 전 화면 차단 | 주문함이 단순 | **코드·직접 가입 연결이 만드는 매장 계정 전용이라 영향 범위가 작음**(거래처 테이블·기존 링크 가입 흐름 무변경). 한 번 확인하면 이후 주문은 자동 정상 |
| 단점 | 거래처는 가장 많이 쓰는 테이블 — 기본값·백필·모든 쓰기 경로 점검 필요 | 주문마다 상태가 복제돼 **확인 뒤에도 옛 주문에 표시가 남음** | 배송·전표가 거래처 기준이라 "이 거래처의 매장 계정이 미확인인가"를 조회하는 함수 하나가 필요 |
| SQL 범위 | 열 추가 + 기본값 + 쓰기 경로 | 열 추가 + 주문 함수 수정 | 열 추가(기존 계정 = `confirmed`) + CX-12 연결 함수 한 줄 수정(새 계정 = `needs_review`) + 판정 함수 1개 |

**추천: C.** 기존 링크 가입 매장과 거래처 흐름을 건드리지 않고, 새로 생기는 연결만 표시한다.

## 결정 2. 확인 전에 무엇을 막나
| | G1 (추천) | G2 |
| --- | --- | --- |
| 주문 접수 | **받는다**(첫 거래를 막지 않음) | 막는다 |
| 주문함 [확인] | **막고 안내** "거래처 확인 후 주문 확인" (지시서 CC-08) | — |
| 배송 배정·전표 생성 | **막는다**(거래처 확인 전엔 쓰지 않음, 설계 5절) | — |
| 단점 | 유통사가 확인을 미루면 주문이 쌓임(주문함 배지로 알림) | 매장이 첫 주문을 못 해 가입 경험이 끊김 |

**추천: G1.** 막는 곳은 서버 쪽 3곳: 주문 "확인 처리" 함수, 배송 배정, 전표 생성 — 모두 위 판정 함수 하나를 부른다(화면만 막으면 우회됨).

## 결정 3. 기존 거래처 후보와 병합
| | 3-a 후보 제시 기준 | 3-b 병합 방법 |
| --- | --- | --- |
| 선택지 | ① 사업자번호 정확 일치 → ② 정규화 이름 + 주소 앞부분 일치(**제안만, 자동 병합 금지**) | ① 기존 `mergeDuplicateCustomers` 재사용 ② **새 전용 함수**: 매장 계정·주문·공개 링크·계약 단가·리드 연결을 새 거래처 → 기존 거래처로 옮기고 임시 거래처 삭제(한 트랜잭션) ③ 1차는 "확인(새 거래처로 유지)"만, 병합은 2차 |
| 문제 | 사업자번호가 있어도 같은 사업자의 **다른 지점**일 수 있음 → 자동 병합 금지는 유지 | ①은 위 표대로 **지금 구조에선 실패**. ②는 SQL 승인 + PG17 필요(옮길 테이블 목록 확정 필요). ③은 중복 거래처가 남음 |

**추천: 3-a는 ①②를 후보로만 보여 주고, 3-b는 ③으로 시작(1차) → ② 전용 병합 함수는 2차.** 이유: 1차는 "확인 필요" 표시·차단·확인 버튼만으로 첫 주문 시험(대표 C 운영 완료)을 막지 않고, 병합은 옮길 테이블 목록이 길어 별도 승인·검증이 필요하다. 시험 매장은 새 거래처로 두고 확인하면 충분하다.

## 추천안으로 만들 것
1. **CX-13 SQL 초안**(승인 대기): `store_accounts` 열 3개(상태·확인자·시각, 기존 행 = `confirmed`), CX-12 연결 함수 수정(새 계정 = `needs_review`), `store_customer_confirmed(회사, 거래처)` 판정 함수, 주문 "확인 처리"·배송 배정·전표 생성 3곳에서 판정 호출, 확인 함수 `confirm_store_customer_v1`(대표·관리자만, audit), 후보 조회(읽기 전용, 사업자번호·이름·주소), down, PG17(미확인 계정 주문 접수 O·확인 처리 X·배송·전표 X·확인 후 정상·다른 회사 격리).
2. **CC-08**: 주문함 "첫 거래 — 거래처 확인 필요" 배지 + [거래처 확인] 버튼(후보 보기·"새 거래처로 확인") + 확인 전 [확인] 대신 안내.
3. **필드 계약(CC-08이 읽는 값)**: 주문 목록 응답에 `customerReview: { status: "needs_review" | "confirmed", candidates: number }` 추가(주문 행의 매장 계정에서 계산).
