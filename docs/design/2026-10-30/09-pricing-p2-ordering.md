# 09 P2: 매장 링크·주문 설정·후결제 주문

상태: 주문 설정·매장별 링크·후결제 주문 코드 작성. [SQL 초안](../../sql-drafts/20261030-pricing-p2-store-ordering.sql)은 운영 미적용이며 별도 승인 대상이다. `PRICE_SHEETS_ENABLED`와 P2 플래그는 기본 OFF다. P0/P1 SQL 적용 확인이 선행돼야 한다.

## 주문 흐름

1. 대표·관리자가 문서 버전을 발행하고 거래처 1곳에 링크를 만든다. 범위 `전체/선택/1곳`은 링크를 일괄 만드는 UI 선택이지 모든 매장이 공유하는 토큰을 뜻하지 않는다. 링크마다 거래처 ID와 발행 버전 ID를 고정한다.
2. URL의 `#` 뒤에 256비트 서명 토큰을 둔다. `#` 부분은 웹 서버 접속 경로에 전송되지 않는다. DB에는 토큰 해시와 재생성용 공개 nonce만 저장한다. 회수·만료 후 재발급하면 기존 토큰을 재사용하지 않는다. 링크를 연 매장은 자기 거래처의 문서·주문만 볼 수 있다. 내부 원가·마진·매입처·다른 거래처 데이터는 응답에서 제외한다.
3. 매장은 KST 기준 다음 배송일을 선택하고 품목·수량을 담는다. 상품 가격은 거래처 계약 단가를 우선하고, 계약이 없으면 발행 문서의 가격 스냅샷을 쓴다. 시세 상품은 단가를 null로 주문받아 `싯가·경매가에 따라 달라질 수 있습니다`를 표시한다. 최근 출고가는 참고값이며 청구액에 더하지 않는다.
4. 후결제 주문만 허용한다. 마감·휴일·배송 요일·최소 주문 정책은 서버에서 다시 확인한다. 제출·마감 전 수정은 하나의 DB 함수에서 품목 스냅샷과 합계를 함께 바꿔야 한다. 주문 확인은 P3 출고·전표 생성과 구분한다.
5. 주문 내역은 동일 링크의 거래처 ID로만 조회한다. 재주문은 기존 주문을 새 장바구니에 복사하되 오늘의 가격·재고·마감을 다시 확인한다.

## 설정 우선순위

매장별 예외 → 배송 권역 → 회사 기본값. 요일은 KST 날짜의 0=일요일부터 6=토요일까지다. 고정 휴무·지정 날짜·요일 휴무는 주문 가능 배송일에서 제외한다. 가락시장 휴장일은 공식 일정을 사람이 가져와 확인한 날짜 행으로 저장한다. 휴무와 겹친 배송을 자동으로 다른 날짜에 옮기지 않고 다음 유효 배송일을 안내한다. 이 정책을 바꾸려면 배송 코스와도 함께 검토한다.

최소 주문금액은 가격이 확정된 품목의 부가세 포함 합계를 기준으로 한다. 정책은 `block`, `notice`, `fee`이며 `fee`면 배송비를 별도 줄로 더한다. 시세 품목이 있는 경우 합계는 확정값이 아니므로 최소 주문 조건 충족 여부를 최종 확정 전 다시 판단한다.

매장 첫 주문 정보(사업자등록증, 휴대폰 인증, 적재 위치 사진, 출입 비밀번호)는 별도 검증·저장 설계가 필요하다. 출입 비밀번호는 암호화 저장과 기사별 열람 감사가 준비되기 전까지 입력창도 열지 않는다. P2 공개 화면은 이를 필수인 양 요청하지 않는다. 주문 제출 시작 전 필수 정보와 기존 거래처 데이터의 충족 범위를 확인해야 한다.

2026-10-30 사용자 확인: 휴대폰 인증 제공사는 아직 정해지지 않았다. 인증 제공사·파일 저장과 접근 통제·출입 비밀번호 열람 감사가 준비될 때까지 `STORE_ORDERING_ENABLED`를 OFF로 유지한다. 이를 우회하는 임시 인증이나 운영 주문 제출은 허용하지 않는다.

검색 결과에서 선택한 매장과 회사 전체 매장에 링크를 발급할 수 있다. 전체 발급은 거래처 ID 순서로 50곳씩 처리하고, 중단 후 다시 시작하면 같은 회사·문서 버전·매장의 활성 링크를 재사용한다. SQL의 회사 행 잠금과 부분 UNIQUE 인덱스가 동시 중복 발급을 막는다. 첫 주문 정보와 휴대폰 인증, 원장·명세서 연결은 아직 구현 전이다. 즐겨찾기·숨긴 품목과 주문 내역 페이지 이동은 구현했다. 열람/주문 횟수와 직접 전달 기록은 볼 수 있지만 자동 발송은 없다. 이 항목들이 완성되고 실제 DB 거래 시험을 통과하기 전에는 기능 플래그를 켜지 않는다. 링크 서명 비밀값을 교체하면 기존 링크는 모두 무효가 되므로 키 교체 절차도 활성화 전에 정해야 한다.

## SQL 검토 관문

- P0/P1 스키마 적용 확인. 현재 P1 SQL은 초안이며 가격 문서 버전의 `(company_id,id)` 유니크를 P2에서 추가한다.
- 링크 회수·만료·문서 유효기간 후에도 품목만 보이고 가격·주문은 감춘다. 주문 함수는 발행 버전과 거래처 계약 단가를 DB에서 읽어 가격을 결정한다. 브라우저의 금액은 받지 않는다.
- 주문 생성·수정·품목 교체·합계는 한 트랜잭션. 동일 `idempotency_key` 재요청은 같은 결과, 다른 내용이면 충돌이다.
- P2 테이블은 전부 RLS ON, 공개 DB 역할 권한 회수, `service_role`만 접근. 공개 API는 요청 본문 속 토큰 해시로 거래처 범위를 좁힌다. 토큰 원문·전화·주소·고객 IP는 열람 이벤트에 저장하지 않는다. `STORE_LINK_SECRET`(32자 이상)과 HTTPS `STORE_PUBLIC_BASE_URL`이 없으면 기능 플래그가 켜져도 화면은 닫혀 있다.
- 최근 주문·열람 상세는 페이지 단위 조회. 다른 회사/매장 데이터 접근, 만료·회수·동시 주문, KST 경계, 시세 상품 테스트를 통과해야 플래그를 켤 수 있다.
- 발행 버전에 찍힌 행사 가격·과세구분은 이후 행사 설정을 수정해도 주문 청구 시 그대로 사용한다. 현재 행사 행은 기간·재고·매장 한도만 확인한다. 거래처 계약 단가가 있으면 계약 단가가 우선한다.

### 격리된 PG16 검증 절차

`scripts/test-pricing-p2-local.mjs`는 빈 `pricing_p2_test*` 이름의 로컬 PG16 데이터베이스에만 접속한다. P0→P1→P2 SQL 초안을 차례로 적용한 뒤 두 회사를 만들고, 교차 회사 링크 FK 거부, 공개 역할의 주문 RPC 실행 거부, 같은 요청 재시도 멱등, 마지막 행사 재고 1개를 두 요청이 동시에 주문할 때 1건만 성공하는지, 발행 가격 스냅샷과 회사별 주문 격리를 검증한다. 운영 DB에서 실행하지 않는다. 2026-10-30 별도 loopback PG16 임시 서버와 새 폐기용 DB에서 실제 실행을 완료했다. 아래 회귀도 모두 통과했으며 운영 DB 검증이나 적용을 뜻하지 않는다.

위 30일은 법정 보존 기간을 주장하지 않는 보수적인 기술 초안이다. 운영 책임자의 목적·보존 검토 전에는 수집하지 않는다. 담당 영업직원·다른 회사·다른 매장·공개 링크에는 원본 자료를 반환하지 않는다. 기사 배정은 서버 저장소에서 매장/기사/실제 KST 배송일을 확인하며 클라이언트가 전송한 assigned=true는 사용하지 않는다.

파일은 최대 10MiB(PDF 사업자등록증), 최대 5MiB(JPEG/PNG 사진)로 제한하며 MIME 선언과 파일 시그니처를 함께 확인한다. 시그니처 검사는 악성코드 검사나 안전한 이미지 재인코딩을 대체하지 않는다. 업로드는 비공개 격리 상태, 저장소의 악성코드 검사와 사진 메타데이터 제거가 완료된 뒤에만 available 상태로 전환한다. 실제 저장소/검사 어댑터가 연결되기 전에는 available 처리나 signed URL 발급 경로가 없다.

출입 정보는 별도 키 저장소의 32바이트 키로 AES-256-GCM 암호화한다. 회사/매장/레코드/키 ID를 AAD로 결합하고 링크 서명 비밀값을 재사용하지 않는다. 키가 없거나 바뀌어 해독할 수 없으면 닫힌다. 열람은 목적과 열람자 ID(개인 이름·전화 대신 내부 식별자)를 포함한 감사 기록을 먼저 영속화한 뒤 private stream 또는 복호화 결과를 반환한다. 공유 캐시·localStorage·사전 서명 URL은 사용하지 않는다. 실제 전송 경로를 연결할 때 no-store/no-referrer와 본문 로깅 제외를 필수로 적용한다.

만료 자료는 즉시 열람 차단한다. 정리 작업은 먼저 상태를 deleting으로 바꾸고 외부 객체 삭제를 요청하며, 실제 객체 삭제 확인 후 deleted로 전환한다. 실패한 삭제는 재시도 대상으로 남기며 삭제 성공으로 기록하지 않는다. DB 회사 cascade만으로 객체 저장소 삭제를 보장할 수 없으므로, 회사 탈퇴는 객체 삭제 확인을 선행하는 별도 절차가 필요하다. 감사 로그는 원문 없이 별도로 보존하며, 보존 기간·법적 보류·백업에서의 삭제는 운영 정책 확정 전 잔여 관문이다.

SQL은 비공개 메타데이터·암호문·감사 모델의 새 로컬 DB 전용 초안이다. 기존 P2 함수에 연결하지 않으며 운영 적용·bucket 생성·실제 개인정보 수집을 하지 않는다.

### P3 예약→출고 전환 규약 (문서 전용)

- 현재 P2 submitted 주문의 행사 수량은 예약으로 취급한다. received/in_delivery로 상태만 바꾸면 예약이 사라질 수 있으므로 현재 코드에서 수동 상태 전환을 운영에 사용하지 않는다.
- P3는 별도 예약 원장과 주문 수정번호, 상태 전이, 실제 재고 이동을 하나의 회사 범위 트랜잭션으로 묶어야 한다. 제출→접수는 예약을 유지하고, 취소는 1회 해제, 출고 확정은 예약을 실제 차감으로 1회 전환한다. delivered는 재차 차감하지 않는다.
- 주문/행사/재고/예약 잠금 순서를 통일하고 전환 idempotency key를 저장한다. 중복 웹훅·출고 재시도·동시 취소/수정·분할 출고·재입고/반품을 명시적으로 모델링한다. 품목·가격·과세 스냅샷을 보존하고 시세 확정은 별도 승인 이벤트로 기록한다.
- P2 예약 집계와 P3 차감을 동시에 더해 이중 차감하지 않도록 cutover 상태·대사·복구 절차를 검토한 뒤에만 연결한다. 실패 시 전표만 생기거나 예약만 풀리지 않도록 outbox/재시도와 오류 상태가 필요하다. 이번 후속은 P3 코드나 운영 테이블을 바꾸지 않는다.
