# CX-150 고객사 PC 자동 업로드 에이전트 설계 보고

Ponytail: 사용함

**상태:** 구현 전 대표 결정 대기 · 운영 DB/기능/배포 변경 없음  
**1차 대상:** 대표 회사 Windows PC + 이카운트 · 매입가와 오늘 갈 곳 파일  
**변경 불가 경계:** ERP 비밀번호는 고객사 PC 밖으로 보내지 않는다. 매입가는 매장에 노출하지 않는다. 기존 수동 업로드는 그대로 둔다.

## 결론

시범은 **Windows 작업 스케줄러 + 설치 도우미 + TypeScript/Playwright 수집기**로 시작한다. 상시 실행되는 데스크톱 셸을 만들지 않고, 실행 상태와 결과는 기존 MAJU 설정 화면에서 본다. 이미 쓰는 웹 기술과 Playwright를 재사용하므로 1인 유지보수 범위가 가장 작다.

- PC에는 ERP 계정을 Windows 자격 증명 관리자에 저장한다. 서버에는 회사별 **업로드 전용 키의 해시**만 저장한다.
- 공식 API가 필요한 파일을 제공하면 API를 우선한다. 제공하지 않는 파일만 화면 자동화로 내려받는다.
- 수집기는 원본 엑셀/CSV를 바꾸지 않고 올린다. 매입 파일은 CX-138, 배송 파일은 기존 오늘 코스 가져오기 파이프라인이 해석한다.
- 화면 변경·로그인 만료·캡차·2단계 인증은 우회하지 않는다. 자동 실행을 멈추고 수동 업로드 방법을 알린다.

## 형태 비교

| 형태 | 설치·업데이트 | 장점 | 비용·위험 | 판정 |
| --- | --- | --- | --- | --- |
| Electron + Playwright | 큰 설치 파일, 앱 자체 업데이트 필요 | TypeScript 한 언어, 로그·지금 실행 UI를 만들기 쉬움 | Chromium 중복, 메모리·다운로드 큼, 상시 앱과 자동화 브라우저를 함께 관리 | 시범에는 과함 |
| Tauri + Playwright | 작은 셸, Windows MSI/NSIS와 서명된 업데이트 지원 | 설치 크기와 상시 메모리 작음 | Rust/웹 셸/Playwright 세 층을 혼자 관리, 업데이트 서명 키도 별도 운영 | 고객사가 늘고 로컬 UI가 필요할 때 |
| 작업 스케줄러 + 설치 도우미 | 설치 시 예약 두 개 등록, 새 버전은 서명된 설치 파일로 교체 | 상시 프로세스 없음, 기존 TypeScript/Playwright 재사용, 장애 지점 최소 | 화려한 로컬 UI 없음; `지금 실행`은 설치 도우미 또는 시작 메뉴 바로가기 | **1차 추천** |

Windows 배포본은 처음부터 같은 인증서로 코드 서명한다. 미서명 앱은 SmartScreen 경고가 날 수 있고 Windows 11 Smart App Control에서는 차단될 수 있다. 인증서 가격은 발급사·조직 확인 방식에 따라 달라지므로 구현 승인 시 2개 발급사 견적을 받는다. Tauri로 전환하면 업데이트 패키지 자체 서명도 필수이며, 개인키를 잃으면 기존 설치본에 업데이트를 배포할 수 없으므로 CI 비밀 저장소와 별도 복구 보관이 필요하다.

## PC 안의 흐름

1. 관리자가 MAJU에서 1회용 설치 코드를 발급한다. 코드는 10분 뒤 만료되고 설치 완료 즉시 폐기한다.
2. 설치 도우미가 회사별 업로드 키를 받아 Windows 자격 증명 관리자에 저장한다. ERP 아이디·비밀번호도 같은 PC의 별도 자격 증명으로 저장한다.
3. 작업 스케줄러가 `05:30 오늘 갈 곳`, `06:00 매입가` 작업을 일반 사용자 권한으로 실행한다. 겹친 실행은 로컬 잠금 하나로 건너뛴다.
4. 수집기는 이카운트 공식 API 사용 가능 여부를 먼저 확인하고, 불가한 종류만 브라우저로 로그인해 원본 파일을 내려받는다.
5. 파일의 SHA-256을 계산해 업로드 시작을 요청하고, 서버가 준 서명 URL로 원본을 직접 올린 뒤 완료를 알린다.
6. 서버가 기존 가져오기 파이프라인에 작업을 넘긴다. PC는 성공·실패 코드와 행 수만 받아 로컬 로그에 남긴다.
7. 성공한 임시 파일은 즉시 지운다. 실패 파일은 관리자만 읽을 수 있는 폴더에 최대 7일 보관하고 다음 성공 또는 만료 시 지운다.

로컬 로그에는 실행 시각, 수집기 버전, 파일 종류, 파일 해시 앞 8자리, 행 수, 결과 코드만 쓴다. ERP 아이디·비밀번호, 업로드 키, 파일 내용, 거래처명은 쓰지 않는다. 자동화 중 화면 캡처와 네트워크 본문 기록은 기본 금지한다.

## 서버 계약

`POST /api/agent/uploads/start`

- 인증: `Authorization: Bearer <회사별 업로드 키>`; 로그인 쿠키는 받지 않는다.
- 입력: `kind`(`purchase_cost` 또는 `today_route`), 파일명, 크기, SHA-256, 수집기/어댑터 버전.
- 검사: 키 해시·회사·허용 종류·만료/회수, 확장자, MIME, 크기, 회사별 속도 제한.
- 같은 `company + kind + SHA-256`의 성공 건은 새 쓰기 없이 기존 결과를 반환한다.
- 4.5MB 이하는 기존 API 업로드, 초과는 기존 서명 업로드 방식을 재사용한다. 새 저장 방식을 만들지 않는다.

`POST /api/agent/uploads/{id}/complete`

- 저장 객체의 실제 크기·해시를 다시 확인한 뒤에만 `queued`로 바꾼다.
- 매입가는 CX-138과 같은 열 인식·단위 정규화·품목 매칭을 호출한다. 에이전트 전용 가격 계산은 만들지 않는다.
- 오늘 갈 곳은 기존 수동 파일 가져오기와 같은 칸 맞춤/코스 생성 경계를 호출한다.
- 응답은 `accepted | duplicate | needs_review | failed`와 행 수·매칭 수·보류 수·안전한 오류 코드만 제공한다.

업로드 키는 읽기, 파일 내려받기, 결과 목록 조회, 가격·코스 수정 권한이 없다. 결과 조회와 키 발급·회수는 로그인한 대표/관리자만 기존 회사 권한으로 한다.

## DB 초안 목록

구현 승인 뒤 SQL 초안·down·PG17을 별도 PR로 만든다. 이번 문서에서는 적용하지 않는다.

1. `agent_upload_keys`
   - `id, company_id, name, secret_hash, allowed_kinds[], expires_at, revoked_at, last_used_at, created_by, created_at`
   - 원문 키 저장 금지. 같은 회사에 활성 키 최대 2개, 기본 만료 90일.
2. `agent_upload_runs`
   - `id, company_id, key_id, kind, source_system, source_sha256, object_path, file_size, collector_version, adapter_version, status, row_count, matched_count, held_count, error_code, started_at, completed_at`
   - `(company_id, kind, source_sha256)` 성공 건 중복 방지. 오류 본문·ERP 계정 저장 금지.

두 표 모두 RLS를 켜고 앱 역할 직접 접근은 막는다. `service_role` 함수만 쓰고 회사 고정, 키 발급·회수는 대표/관리자 감사 로그를 남긴다. 원본 파일 보관 기간은 시범 30일로 제안하며, 만료 삭제 작업과 법적 보관 필요 여부는 구현 승인 전에 대표가 결정한다.

## 실패와 복구

- 로그인 실패는 1회 재시도만 한다. 연속 3회면 예약 실행을 중지해 계정 잠김을 피한다.
- 캡차·2단계 인증·약관 재동의·예상하지 못한 화면은 `manual_action_required`로 중지한다.
- 선택자나 내려받은 열이 바뀌면 어댑터 버전 불일치로 처리하며, 이전 파일을 성공으로 표시하지 않는다.
- 업로드 중 네트워크가 끊기면 같은 해시로 재시도한다. 서버 중복 키가 이중 반영을 막는다.
- 서버 해석이 `needs_review`이면 현재 가격과 오늘 코스를 자동 확정하지 않고 기존 수동 화면으로 연결한다.
- 최근 결과 화면에는 마지막 성공, 다음 예약, 연속 실패 수, 원본 행/매칭/보류, `지금 다시 실행` 안내를 표시한다.

## 이카운트 확인 결과와 착수 조건

이카운트 공개 안내는 외부 연동에 OAPI를 사용할 수 있다고 설명하지만, 제공 API는 제품 안의 `API인증키발급 > API매뉴얼`에 있는 일부 메뉴로 한정되고 매뉴얼 밖 API 추가 제공은 보장하지 않는다. 공개 약관은 고객 데이터의 엑셀 백업 권리는 설명하지만 화면 자동 접속 허용 여부를 명시하지 않는다. 따라서 **자동 로그인이 허용된다고 추정하지 않는다.**

시범 착수 전 대표 회사 계정에서 다음을 확인한다.

1. API 매뉴얼에 매입 현황과 출고·배송 목록 조회/내려받기가 각각 있는지 캡처 없이 항목명·응답 필드만 기록한다.
2. 없는 종류는 이카운트 고객센터에 “고객사 PC의 조회 전용 하위 계정으로 정해진 시간에 로그인해 엑셀을 내려받는 자동화” 허용 여부를 서면 문의한다.
3. 조회·엑셀 다운로드만 가능한 전용 하위 계정을 만든다. 입력·삭제·사용자 관리 권한은 주지 않는다.
4. ERP 샘플 파일 각 1개와 수동 내려받기 경로를 받는다. 실제 거래 데이터는 저장소·PR에 올리지 않는다.

## 승인 뒤 구현 순서

1. 이카운트 OAPI/약관 확인과 샘플 파일 확보.
2. 업로드 키·이력 SQL 초안/down/PG17 및 키 발급·회수 API.
3. 원본 업로드 입구와 CX-138/오늘 코스 기존 파이프라인 연결. 기능은 대표 회사 allowlist에서 기본 OFF.
4. Windows 수집기 한 종류(`purchase_cost`)와 수동 `지금 실행`만 시범.
5. 7일 동안 수동 업로드 결과와 행 수·해시·매칭/보류가 같은지 비교한 뒤 예약 실행.
6. `today_route` 추가. 고객사 2곳 이상에서 로컬 상태 UI 요구가 확인될 때만 Tauri 셸을 검토.

## 대표 결정이 필요한 네 가지

1. 시범 형태를 **작업 스케줄러 + 설치 도우미**로 확정할지.
2. 원본 파일 서버 보관 기간을 30일로 할지.
3. 코드 서명 인증서 견적을 받은 뒤 발급할지(미서명 배포는 하지 않음).
4. 이카운트에 화면 자동화 허용을 서면 문의하고, 답변 전에는 OAPI로 가능한 종류만 만들지.
