## 결론과 충돌 경계

현재 `/store#<token>`은 거래처에 발급한 서명 링크로 주문하는 화면이다. 카카오 점주·관리자·직원 공동 계정 화면은 아직 아니다. 같은 링크를 여러 기기에서 열 수 있으나 사람별 역할·주문 작성자 식별·구성원 제거에 따른 접근 차단은 제공하지 않는다. 이 상태를 ‘역할별 공동 사용 완료’로 표시하면 안 된다.

03 PR #255의 매장 자체 원가 계약과 07 PR #258의 구성원 가입 SQL 초안·세션 경계를 재사용한다. 새로운 원가 테이블/RPC나 별도 로그인 체계를 설계하지 않는다. 이번 변경은 이 문서 한 개로, 03/07 파일과 충돌하지 않는다. 후속 구현에서 07의 인증·03의 API 작업이 필요하면 먼저 소유자에게 연결 요청한다.

운영 상태는 이번에 조회하지 않았다. ‘초안/미연결’은 이 기준 커밋의 소스·승인표 상태다. 판매가 등락 SQL의 운영 적용 기록(#264)은 원가 SQL/매장 카카오 SQL의 적용 승인을 뜻하지 않는다. 기존 OFF 유지 지시도 변경하지 않는다.

## 역할표 — 현 상태와 후속 정책을 구분

현재 공개 링크에서는 아래 매장 역할을 판별하지 않는다. 주문 역할표는 후속 연결 제안이며, 원가 권한은 #255 기존 계약이다. 사용자 ID·회사·매장·역할은 body/query가 아니라 검증된 매장 세션과 활성 멤버 조회로 결정한다.

| 행위 | 점주 owner | 관리자 manager | 직원 staff | 현재/후속 경계 |
|---|---|---|---|---|
| 허용된 견적·단가표·행사·임박 보기/주문 | 허용안 | 허용안 | 허용안 | 현재는 유효 링크 권한뿐. 회원별 필터·주문 감사는 미구현 |
| 주문 내역·재주문·마감 전 수정 | 매장 범위 허용안 | 매장 범위 허용안 | 매장 범위 허용안 | 현재 link_id/revision 경계 유지. 타인 주문 수정 정책은 서버 계약 확정 후 연결 |
| 매장 자체 원가·이력 조회 | 허용 | 허용 | 허용 | #255: 활성 매장 멤버만. 링크만 있으면 거부 |
| 매장 원가 엑셀 업로드·정정 | 허용 | 허용 | 거부 | #255: API+기존 `save_store_cost`의 owner/manager 이중 검사 |
| 직원 초대 | 허용 | 허용 | 거부 | #258 초안 재사용. 관리자 초대는 owner만, owner 개통/이전은 별도 경계 |
| 콘텐츠 초안 작성·저장·공유 범위 | 정책 확정 전 미노출 | 정책 확정 전 미노출 | 정책 확정 전 미노출 | 주문/원가 권한을 자동 전용하지 않는다. 외부 자동 게시 없음 |

구성원 제거·role 변경은 다음 요청에서 반영되어야 한다. 현재 bearer 링크는 구성원 제거만으로 폐기되지 않으므로 회원 전용 기능의 권한 우회로로 사용하면 안 된다. 기존 공개 주문 유지/회원 주문 전환 정책은 컨트롤타워에서 결정하고, 그 전까지 기존 주문 API를 조용히 로그인 필수로 바꾸지 않는다.

## 단계별 설계와 재사용

### 1. 주문과 공동 사용

기존 홈/주문/내역/내 정보 구성과 주문 폼을 유지한다. 카카오 연결은 07 세션 이후에만 추가하고, 서버가 확인한 매장과 역할을 표시한다. 여러 매장 소속이면 검증된 소속 목록에서 선택하고 대상 변경 시 장바구니·내역·요청 상태를 섞지 않는다. 견적/단가표/행사/임박은 게시 문서 접근 범위 안에서 표시한다. 새 통합 문서함이 필요하면 03 문서 읽기 API 소유자와 범위·페이지 계약부터 합의한다.

기존 `place_store_order`를 재사용할 수 있는지 주문 소유자가 회원 경계·actor 감사·타인 주문 수정 정책을 먼저 확정한다. 09가 새로운 주문 RPC를 만들거나 공개 token만으로 회원 주문을 인증하지 않는다. 여러 기기의 새 주문은 서로 다른 멱등키로 별개 주문이 될 수 있으므로 ‘같은 장바구니 한 번 주문’으로 오인시키지 않는다. 같은 주문 revision 충돌은 기존 재조회 안내로 처리한다.

### 2. 매장 원가관리

07 전용 세션 → 활성 멤버 helper → 03 `/api/store/costs` 계약 → 09 화면 순서다. #255의 `store_cost_items`/`store_cost_revisions`와 `save_store_cost`를 그대로 재사용하며 추가 DB·원가 RPC를 작성하지 않는다.

| 흐름 | 재사용/입출력 | 안전 조건 |
|---|---|---|
| 조회·이력 | 계약의 GET 기간·상품 검색, itemId history | 회사+매장 범위 고정. 페이징/응답 DTO/오류 코드 상세는 03과 연결 전에 확정 |
| 업로드 | 파일 → 열 맞추기 → 행 미리보기/검증 → 확인 → POST | `fileName`, `fileBytesBase64`, rows. 서버 SHA-256, 원본 행 번호 유지, 10MB 제한; 전체 파일 실패/부분 성공 응답·재시도 기준은 03 계약 보완 필요 |
| 정정 | 기존 행 선택 → 폼 → PATCH | itemId/expectedRevision/row. 409 또는 충돌 응답 시 최신값 확인 후 명시 재시도; 조용한 덮어쓰기 금지 |
| 입력 항목 | 적용일·품목명·규격·단위·원화 원가 | 03 최종 계약의 다섯 항목만. 공급처·수량·유통사 매입가·마진 필드를 임의 추가하지 않는다 |

고객사 기존 폼 경험을 재사용한다: [ExcelHeaderMappingPreview](../../components/excel-mapping-preview.tsx)의 열 매핑·필수 열 안내, [ImportRowEditor](../../components/import-row-editor.tsx)의 미리보기·수정/원복, 기존 `Button`/`Badge`/표·입력 부품을 우선 사용한다. [CustomerItemsImportDrawer](../../components/customer-items-import-drawer.tsx)는 업로드→매핑→미리보기→저장 흐름의 참고이며 고객사 API/상품 참조 조회를 그대로 가져오지 않는다. [CompanyProfileForm](../../components/company-profile-form.tsx) 역시 고객사 인증·첨부 API를 포함하므로 매장 세션 폼으로 통째로 재사용하지 않는다. 공용 표시 부품의 변경이 필요하면 그 소유자와 먼저 범위를 조율한다.

기존 11/5 작업지시의 공급처·수량 등 넓은 원가 필드와 매입가 방향 제안은 최신 #255 API 계약·#263 판매가 방향으로 구체화/정정됐다. 그 이전 제안을 근거로 필드를 늘리거나 유통사 가격 이력을 연결하지 않는다.

### 3. 콘텐츠 초안

주문·원가관리 연결 후의 별도 단계다. 최초 범위는 사용자가 입력한 매장 소개/상품 정보로 초안 작성·수동 편집·미리보기·복사/내보내기까지의 설계다. 저장 필요 여부와 역할·공유 범위·입력 출처를 먼저 확정한다. 원가·개인정보·카카오 토큰·비공개 문서 내용을 자동으로 초안에 넣지 않는다. 블로그·인스타·유튜브 자동 게시, 외부 OAuth/업로드, 게시 예약·백그라운드 전송은 구현하지 않는다.

## 후속 순서와 완료 판정

1. 07: 승인된 가입/초대 경계와 매장 전용 세션을 연결하고 M1/M2를 검증한다. 운영 적용 여부는 소유자가 별도 확인한다.
2. 주문 소유자+09: 회원 주문의 신원·actor 감사·타인 주문 수정 정책을 확정하고 기존 bearer 주문과의 전환 경계를 검증한다. UI 버튼 숨김만으로 권한을 구현하지 않는다.
3. 03: #255 repository/API와 조회 페이징·응답·업로드 부분 실패·충돌 계약을 완성한다. 09는 계약을 받아 기존 폼 부품으로 원가 탭을 연결하고 C1~C4를 검증한다.
4. 09: 여러 게시 문서 탐색 필요 여부를 확인하되 문서 읽기 API·중앙 메뉴를 직접 확장하지 않는다. PC/390px O1~O6을 실행한다.
5. 주문·원가 단계의 합격 증거 이후 콘텐츠 초안의 최소 수동 흐름을 별도 확정한다. 자동 게시 구현은 계속 제외한다.
