# 주문 링크·매장 화면·MAJU 관리자 확장 검토 (2026-11-06)

## 결정

MAJU는 하나의 모놀리스에서 유통사 운영 화면, 매장 화면, 플랫폼 관리자 화면을 제공한다. 매장 화면의 **공통 구성·기능 사용 여부·외부 정보 품질**은 MAJU 관리자가 관리한다. 특정 유통사의 **상품·판매가·마진 규칙·발행 문서·주문 조건·매장 링크**는 그 유통사 대표/관리자가 관리한다. 매장의 자체 매입 원가·비용은 매장 구성원만 관리한다. 이 세 범위를 하나의 관리자 수정 권한으로 합치지 않는다.

| 주체 | 관리할 것 | 볼 수 없는 것 |
| --- | --- | --- |
| MAJU 관리자 | 매장 공통 화면 구성, 기능 플래그, 외부 API 수집 상태, 출처가 있는 시장 참고 데이터, 고객사별 연동 상태 | 다른 회사의 원가·마진·계약 단가 원문을 일반 화면에서 일괄 열람하거나 수정하는 기능 |
| 유통사 대표/관리자 | 자기 회사 상품과 매입가, 마진·판매가, 문서 발행, 링크 발급·회수, 주문 설정과 접수 | 매장이 따로 업로드한 매장 자체 원가·비용 |
| 매장 점주/관리자/직원 | 해당 유통사에 보낸 주문과 허용된 문서; 매장 자체 원가는 별도 카카오 구성원 권한으로 접근 | 유통사 매입가·마진·매입처, 다른 매장의 데이터 |

## 기존 기능과 연결

1. **매입가 → 마진 → 문서 → 링크.** 현재 `pricing_documents`는 편집본과 게시 버전을 나누며, `storefront_links`는 게시 버전을 가리킨다. 매입가를 다시 올려도 기존 게시 버전의 상품·가격은 바꾸지 않는다. 재계산 필요 건수를 보여준 뒤 유통사가 새 버전을 검토·발행하고, 대상 링크를 새 버전으로 재발급하거나 교체하도록 한다. 유통사가 보낸 이전 버전과 기존 주문의 가격 스냅샷은 유지한다. 링크 교체는 기존 링크의 주문 내역 조회·회수 정책을 검증한 뒤 설계한다.
2. **매장 화면.** 현재 `/store`에는 홈·주문·내역·내 정보 탭과 판매가 등락 표시가 있다. 원가 등락이나 유통사 매입가를 공개하지 않는다. 고객사가 제공하는 상품·판매가·배송/마감 조건을 보여주고, MAJU 관리자가 화면 템플릿과 정보 영역만 관리한다. 모바일 390px과 PC에서 같은 주문 정책을 사용한다.
3. **매장 자체 원가.** 매장용 원가 업로드는 기존 `store-cost-api-contract.md`대로 `store_account_id` 소유로 구현한다. 공개 링크만으로 열지 않으며, 활성 카카오 매장 구성원 세션이 필요하다. 점주/관리자는 업로드·정정, 직원은 조회 권한부터 시작한다. 유통사 원가와 별도 저장·조회한다.
4. **시장 모니터링.** MAJU 관리자는 품목별 관측 가격을 `품목·규격·단위·지역·채널(도매/소매 등)·관측일·출처`와 함께 관리한다. 이를 **시장 참고값**으로 명시한다. 유통사의 판매가나 매장 주문 단가에 자동 반영하지 않으며, 유통사가 채택하기 전에는 가격 규칙의 입력으로 쓰지 않는다. 채널과 규격이 다른 가격을 같은 값으로 비교하지 않는다.

## 자동 영업 구상 반영 범위

`auto_sales_design.html`의 다섯 기능을 하나의 자동화 작업으로 묶지 않는다.

| 첨부 구상 | 현재 처리 방향 |
| --- | --- |
| 단가가 높은 매장 자동 발굴 | 매장 자체 원가는 해당 매장 계정의 비공개 데이터다. 유통사 리드 생성·전달이나 매장별 절감액 공개에는 사용하지 않는다. 매장이 명시적으로 견적을 요청하는 별도 흐름을 설계할 때만 공유 범위를 다시 결정한다. KAMIS 가격과 규격·단위·지역·관측일이 맞는 경우에도 차이는 참고값이며, 임의의 15% 기준으로 거래 판단을 확정하지 않는다. |
| 매장 신뢰 스코어·미수 위험 | 기존 **영업 리드 점수**와 금융 신용·미수 위험은 다른 개념이다. 로그인 빈도나 상권 지표로 외상 가능 여부를 자동 판정하지 않는다. 필요한 경우 실제 자사 거래·수금 이력과 설명 가능한 정책을 별도 승인받아 검토한다. |
| 유통사 여러 곳 견적 비교·수락 | 현재는 유통사가 자기 매장에 보내는 단가표·견적서와 매장별 링크가 정본이다. 여러 유통사의 제안을 한 매장에서 비교하는 마켓플레이스는 별도 참여 동의·회사 간 정보 격리·가격 노출 정책이 필요한 후속 단계다. |
| D+3/D+7 팔로업·이탈 감지 | 수락·첫 주문·재주문 시각 및 매장별 실제 주문 간격을 먼저 정확하게 기록한다. 주문 간격이 늘어난 매장은 담당자용 **확인 필요** 카드로 제안할 수 있다. 자동 카카오 발송이나 확정된 “이탈 위험” 판정은 하지 않는다. |
| 월간 영업 성과 | 자기 회사의 리드→문서 발송→열람→수락→첫 주문→재주문 퍼널과 주문액은 기존 정본으로 집계한다. 다른 회사의 단가·매장 자체 원가는 비교 지표에 넣지 않는다. 표본이 충분하고 공개 정책이 승인된 집계만 별도 검토한다. |

## 외부 데이터 적용 기준

- **AirKorea:** 측정소·시각·PM2.5/PM10 원본 값을 제공하는 공식 API 후보. “대기질 → 주문 증가/감소”는 별도 실측 전 예측 규칙으로 만들지 않는다. 첫 단계는 매장 위치 인근 대기질 참고 정보뿐이다.
- **한국관광공사 행사:** 행사 조회가 공식 API 범위에 있다. 행사 장소·기간과 고객사 배송 권역을 연결해 운영자 참고 일정으로 보여줄 수 있다. 마라톤·도로 통제까지 빠짐없이 제공한다고 가정하지 않는다.
- **소진공 상가(상권)정보:** 공식 상가 API의 상호·주소·업종·좌표를 기준으로 인근 동업종 점포 수는 계산할 수 있다. 개폐업률·배달 수요·매출 전망은 이 API 한 개의 직접 제공값으로 확정하지 않는다. 갱신 시각·누락률을 측정하고 별도 공식 데이터가 필요한 항목을 분리한다.
- 모든 외부 값에는 출처·관측일·갱신일·비교 조건을 표시한다. 제공 조건과 호출 한도는 연동 직전에 다시 확인하고, 운영 키를 문서·로그·브라우저에 넣지 않는다. 첫 버전은 읽기 전용 관리자 카드, 이후 실제 유용성이 확인되면 유통사·매장 노출 범위를 결정한다.

## 우선순위와 완료 기준

1. **주문 링크 갱신 흐름 (P1):** 재계산 필요 → 새 문서 버전 미리보기 → 발행 → 영향을 받는 매장 링크 목록 → 명시적 갱신·재발급. 이전 발행본과 주문 금액은 불변. 같은 회사 대표/관리자만 실행. 갱신 실패는 매장별로 표시한다.
2. **매장 화면 관리 (P1):** MAJU 관리자는 공통 블록 노출과 콘텐츠 운영 상태, 유통사는 자기 회사 주문 조건과 문서/상품 공개 범위를 관리한다. 매장 정보 제공자와 마지막 갱신 시각을 표시한다. 전역 변경이 개별 유통사 가격을 덮지 않도록 한다.
3. **매장 자체 원가관리 (P2):** 매장 카카오 세션·구성원 권한·원가 저장 승인 상태를 확인한 뒤 엑셀 열 맞추기 → 미리보기 → 저장 → 원가 이력. 링크 토큰 단독 접근 거부, 다른 매장·다른 회사 차단, 원본 파일 접근 통제와 정정 이력 검증.
4. **시장 참고 가격 (P2):** KAMIS/aT 등 공식 자료로 단위·규격이 일치하는 품목만 참고 비교. MAJU 관리자 검수·출처 표시·오래된 값 숨김. 실제 거래 가격이나 자동 판매가로 혼동시키지 않는다.
5. **상권·환경·행사 참고 정보 (P3):** 관리자 전용 소규모 표본으로 API 품질·지연·갱신 빈도를 측정한 뒤 매장/유통사 화면 노출 여부를 결정한다. 예측·알림·자동 발주는 측정 근거가 생긴 뒤 별도 설계한다.

운영 DB 변경, 외부 API 키 등록, 자동 알림, 대량 수집, 결제·수수료 활성화는 이 문서에 포함되지 않는다. 코드 착수 전 관련 `docs/pages/*.md`의 Allowed Files와 백엔드 계약서 2·5·6절을 기준으로 소유 경계를 확정한다.
