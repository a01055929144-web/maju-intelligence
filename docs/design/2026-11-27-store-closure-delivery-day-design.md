# 매장 휴무일 → 배송 요일 설계 보고서

상태: 설계 확정안 · 코드/운영 DB 변경 없음  
근거: R19 C3, `2026-11-25-store-holiday-delivery-days-backlog.md`의 대표 결정

## 결론

매장 휴무는 기존 배송 요일 설정을 덮어쓰지 않고 **배송 가능일을 계산할 때 차감**한다.

```text
기본 배송 요일 = 매장 예외가 있으면 매장 예외, 없으면 권역 규칙
배송 가능일 = 기본 배송 요일
             - 고객사·권역 휴무
             - 매장 주간 휴무
             - 매장 날짜 휴무
             - 마감이 지난 날짜
```

- 매주 휴무는 화면에 보이는 유효 배송 요일에서도 즉시 빠진다.
- 날짜 휴무는 해당 날짜만 막고, 요일 설정 자체는 바꾸지 않는다.
- `store_order_customer_rules.delivery_weekdays` 원본은 보존한다. 휴무 해제 때 복원본을 관리할 필요가 없다.
- 기존 주문은 자동 취소하지 않는다. 휴무와 겹치면 `확인 필요`로 표시하고 고객사가 배송일을 바꾼다.
- 배송 코스는 주문 기준이다. 겹친 주문은 코스에서 빼지 않고 `확인 필요`로 남긴다.

## 현재 규칙과 재사용 범위

| 현재 값/함수 | 역할 | 이번 설계 |
|---|---|---|
| `store_order_territory_rules.delivery_weekdays` | 권역 배송 요일 | 그대로 사용 |
| `store_order_customer_rules.delivery_weekdays` | 매장별 예외 요일 | 그대로 사용, 휴무로 덮어쓰지 않음 |
| `store_order_holidays` | 고객사·권역 휴무 | 그대로 사용 |
| `getStoreDeliveryEligibility` | 주소·권역·기본 요일 확인 | 유효 요일 조회가 같은 계산을 쓰도록 연결 |
| `deliveryDayState` | 요일·휴무·마감·14일 범위 판정 | 최종 날짜 판정의 단일 진입점으로 유지 |
| 주문 RPC | 제출 직전 날짜 재검증 | 같은 휴무 자료를 DB에서 다시 검증 |

회사 기본 배송 요일은 현재 일부 조회 화면의 최후 대체값이지만 주문 RPC는 매장 예외 → 권역 규칙을 사용한다. 구현 전에 이 차이를 한 규칙으로 맞춰야 하며, 회사 기본값을 새 우선순위로 추가하지 않는다.

## 저장 모델

기존 `store_order_holidays`를 확장해 `customer_id`를 선택 값으로 추가한다. 새 표는 만들지 않는다.

- `customer_id IS NULL`: 지금과 같은 회사·권역 휴무.
- `customer_id IS NOT NULL`: 해당 매장 휴무. 이때 `territory_id`는 저장하지 않고 매장의 현재 권역을 계산 시 조회한다.
- 종류는 기존 `weekly`, `fixed`, `date`를 재사용한다. 첫 구현 범위는 `weekly`, 다음 구현에서 `date`를 연다. `fixed`는 고객사 휴무에만 유지한다.
- 작성자는 점주/매장 관리자 또는 고객사 담당자이며, 작성 주체와 시각을 감사 정보로 남긴다.
- 같은 회사·매장·종류·요일/날짜의 중복 저장을 막는다.

매장 영업시간 자유문자(`normalized_customers.business_hours`)는 계산 자료로 쓰지 않는다.

## 계산 기준

1. 한국 날짜(`YYYY-MM-DD`, Asia/Seoul)만 사용한다.
2. 기본 요일은 `매장 예외 ?? 권역 규칙`이다. 값이 없으면 지금처럼 `weekdays_unconfigured`로 주문을 막는다.
3. 매장 주간 휴무 요일을 기본 요일에서 뺀 값이 유효 배송 요일이다.
4. 선택 날짜가 고객사·권역 휴무 또는 매장 날짜 휴무와 일치하면 `holiday`로 막는다.
5. 이후 기존 마감과 14일 범위를 적용한다.
6. 모든 요일이 빠지면 조용히 빈 달력을 보여주지 않고 `매장 휴무로 배송 가능한 요일이 없습니다`를 표시한다.

예: 권역 배송이 월·수·금이고 매장이 매주 수요일 휴무면 화면 배송 요일은 월·금, 수요일 날짜는 선택할 수 없다. 12월 31일만 쉬는 경우 요일 표시는 그대로이고 12월 31일만 막힌다.

## 저장·변경 흐름

1. 점주가 매장 앱의 `영업일 설정`에서 주간 휴무 또는 날짜 휴무를 저장한다.
2. 저장 직후 승인 대기 없이 반영한다.
3. 고객사 담당자에게 매장명·변경 전후·적용일을 알린다.
4. 변경 뒤 이미 접수된 주문 중 배송일이 새 휴무와 겹치면 `확인 필요`로 표시한다. 주문 상태와 금액은 바꾸지 않는다.
5. 고객사 담당자가 배송일을 바꾸면 기존 주문 변경 규칙과 마감을 다시 검증한다.

권한은 해당 매장의 점주·매장 관리자와 해당 고객사의 허용된 담당자만 가진다. 요청의 회사/매장 ID를 신뢰하지 않고 로그인 관계에서 서버가 결정한다.

## 변경 영향

| 영역 | 필요한 변경 | 바꾸지 않는 것 |
|---|---|---|
| DB | `store_order_holidays.customer_id`와 중복 방지·권한·감사 정보 | 기존 회사·권역 휴무 행 |
| 공통 계산 | 유효 요일과 매장 날짜 휴무를 정책에 합성 | 가격·최소 주문·배송비 계산 |
| 매장 앱 | 영업일 설정, 달력의 휴무 사유 | 주문 품목·합계 화면 |
| 주문 서버 | 제출 직전 동일 규칙 재검증 | 기존 주문 자동 취소 |
| 고객사 화면 | 거래처 상세의 휴무, 충돌 주문 `확인 필요` | 주문 금액·발행 문서 |
| 배송 코스 | 충돌 주문 배지, 주문 없는 휴무 매장 제외 | 이미 있는 주문의 코스 강제 삭제 |
| 알림 | 휴무 저장/해제 알림 | 고객사 승인 단계 |

단가표 하단·공개 화면·매장 홈의 배송 요일도 같은 유효 요일을 읽어야 한다. 각 화면에서 별도로 요일을 빼지 않는다.

## 구현 순서와 완료 조건

1. **매주 휴무**: 저장 확장 SQL 초안/down/PG17 + 공통 계산 + 주문 서버 재검증.
2. **날짜 휴무**: 공통 달력 재사용 + 날짜 휴무 저장/해제.
3. **운영 연결**: 고객사 알림 + 기존 주문 충돌 표시 + 코스 배지.

각 단계는 별도 PR로 진행한다. 1단계 완료 조건은 다음과 같다.

- 권역 월·수·금 / 매장 수 휴무 → 월·금만 표시·선택·제출 가능.
- 휴무 해제 → 원래 월·수·금으로 즉시 복귀.
- 모든 요일 휴무 → 명시적 안내와 주문 차단.
- 휴무 저장과 주문 제출이 동시에 일어나도 제출 서버가 최신 휴무를 다시 읽어 차단.
- 다른 매장과 기존 고객사·권역 휴무에 영향 없음.
