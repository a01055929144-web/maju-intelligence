# 공공데이터 데이터셋별 수집 예산 분리 설계 (2026-11-22)

상태: **설계만 완료**. 코드·DB·운영 설정·정기 실행 시각은 변경하지 않았다. Owner Domain은 리드 수집이다. 선행 수정은 [CX-118](../dispatch/2026-11-18-CX-118-gov-general-restaurants.md)이며, 이 문서는 그 재시도·지역 회전 로직을 다시 만들지 않는다.

## 확인된 문제

| 11/22 읽기 결과 | 실제 경계 |
|---|---|
| 일반음식점 첫 지역 20행 요청은 약 16.7초에 성공해 새 행 13건을 가져왔다. 이어진 단독 지역 요청은 20초 시간 초과였고 나머지 18지역은 이월됐다. | 한 실행의 수집 예산 40초, 뒤처리 예약 10초, 외부 요청 동시성 2. **한 실행에서 19지역을 모두 끝낼 수는 없다.** |
| 휴게음식점·카페의 100행 요청 두 건은 각각 20초 시간 초과였다. 재시도할 예산이 남지 않았다. | 현재 `recommend-refresh`는 휴게음식점·카페와 빵집을 한 번의 `syncAllCompaniesGovRestaurantLeads(["rest_cafes", "bakeries"])` 호출에 넣어 **같은 40초 마감과 요청 슬롯 2개를 공유한다.** |

`gov-sync`의 일반음식점 15분 호출과 `recommend-refresh`의 휴게음식점·빵집 일일 호출은 서로 다른 HTTP 실행이다. 각 실행 안에서는 `lib/store.ts`가 데이터셋·회사 작업을 함께 시작하고 같은 `deadlineAt`과 `createGovRequestLimiter(2)`를 공유한다. 따라서 한 데이터셋의 느린 요청이 다른 데이터셋의 첫 시도까지 이월시킬 수 있다. 11/22 결과만으로 외부 API 자체의 장애나 신규 행 0건을 단정하지 않는다.

## 제안: 한 HTTP 실행에서 데이터셋 하나만 수집

기존 `/api/cron/gov-sync`의 15분 호출 한 번을 한 데이터셋에 배정한다. 순서는 **일반음식점 → 휴게음식점·카페 → 일반음식점 → 빵집**으로 반복한다. 일반음식점은 영업 파일럿 우선순위 때문에 시간당 두 번, 다른 두 종류는 각 한 번의 기회를 받는다. 데이터셋 선택은 실행 시각의 15분 슬롯으로 결정하고 요청 쿼리나 브라우저 입력으로 받지 않는다. 누락된 실행이 있어도 다음 네 슬롯 안에 다시 기회가 온다.

선택된 데이터셋만 기존 `syncAllCompaniesGovRestaurantLeads([dataset])` 경로에 넣는다. **40초 수집 + 10초 뒤처리 예약, 함수 최대 60초, 요청당 20초, 동시성 2는 유지**한다. CX-118의 지역별 `attempts`, `timeoutCounts`, 보류 지역 이어받기와 일반음식점 첫 20행 규칙을 그대로 쓴다. 선택되지 않은 데이터셋에는 성공·실패 수집 행을 새로 기록하지 않는다.

기능은 기본 OFF이고 먼저 합성 회사로 검증한다. 전환 대상 회사의 휴게음식점·빵집은 `recommend-refresh`, 일반음식점은 `business-status`의 중복 수집에서 제외한다. 두 일일 경로의 점수 재계산·연락처 보강·사업자 상태 확인 등 나머지 작업은 유지한다. 공개 API 응답 필드가 사용 중이면 빈 결과 대신 “이 실행에서는 수집 대상 아님”을 명시한다.

현재 15분 `gov-sync`는 **모든 회사**를 한 번에 처리한다. 따라서 대표 회사만 새 회전 방식으로 바꾸면 다른 회사의 15분 일반음식점 수집도 줄어든다. 회사 허용 목록이 없는 상태에서 전체 회전을 바로 켜지 않는다. 실제 코드 작업은 회사별 기존 수집 주기를 보존하는 분리 호출을 먼저 마련하거나, 영향받는 회사 모두의 전환 승인을 받은 뒤에만 ON한다. 이 선행 조건을 충족할 수 없으면 기본 OFF를 유지한다.

15분 워크플로 파일, Vercel 정기 실행 시각, 인증 비밀값, 20초·40초·60초 상한은 바꾸지 않는다. 데이터셋마다 **동시에 40초를 주는 방식**은 외부 요청 동시성 2와 함수 60초 한도를 깨므로 사용하지 않는다.

## 구현 경계와 확인

| 단계 | 변경 파일 후보 | 완료 확인 |
|---|---|---|
| 슬롯 선택 순수 함수 | `lib/gov-area-fanout.ts`와 해당 단위 시험 | 네 연속 슬롯의 순서, 실행 한 번 지연·누락, 자정 경계에서 선택이 결정적이다. |
| 회사별 한 종류 실행 | `lib/store.ts`, `app/api/cron/gov-sync/route.ts` | 전환 대상의 선택된 종류만 기존 40초 예산을 사용한다. 다른 종류의 `lead_sync_runs`는 쓰지 않는다. 기존 회사의 15분 일반음식점 주기는 줄이지 않는다. |
| 중복 수집 제거 | `app/api/cron/recommend-refresh/route.ts`, `app/api/cron/business-status/route.ts` | 전환 대상의 일일 수집만 제외하고 추천·연락처·사업자 상태 작업은 유지한다. |
| 합성 시간 시험 | 가짜 시계·가짜 외부 API | 일반음식점 20초 지연 뒤 다음 슬롯의 카페가 자기 예산을 갖고 시작한다. 카페 두 요청이 20초 시간 초과여도 다음 빵집 슬롯이 이월되지 않는다. 기존 CX-118의 시간 초과 횟수·20행·지역 회전 시험은 유지한다. |

배포 뒤에는 데이터셋마다 `scannedPages`, `pendingAreaCount`, 지역별 `attempts(pageSize, ms, result)`, 마지막 성공 시각을 **서로 분리해** 본다. 일반음식점에서 한 실행에 18지역이 이월되는 것은 40초 상한 때문에 가능하며, 다음 슬롯들에서 보류 지역이 실제로 줄어드는지가 완료 기준이다. 카페가 다시 20초 시간 초과라면 CX-118의 작은 페이지·단독 실행으로 이어지는지 확인한다.

## 적용 전 확인할 위험

1. 15분 호출이 크게 지연되면 시각 슬롯을 건너뛸 수 있다. 네 슬롯 내 재기회가 있는지 가짜 시계로 확인하고, 실제 지연이 반복되면 기존 `lead_sync_runs`의 마지막 시도 시각을 이용한 우선순위 보완을 별건으로 결정한다.
2. 같은 슬롯 재시도는 같은 데이터셋을 다시 읽을 수 있다. 기존 원본 키 중복 제거·upsert 동작을 합성 시험으로 확인한다. 시간 슬롯만으로 DB 중복 방지를 주장하지 않는다.
3. 이 설계는 **서로 다른 데이터셋의 예산 경쟁**을 없앤다. 한 지역 자체가 계속 20초 넘는 문제, 회사 여러 곳의 같은 종류 작업 경쟁, 외부 API 장애는 CX-118 기록과 별도 원인 분석이 필요하다.
4. `createGovRequestLimiter(2)`는 **한 함수 실행 안에서만** 요청 2개를 제한한다. 서로 다른 cron HTTP 실행이 겹치면 전역 2개를 보장하지 못한다. 겹침을 막는 운영 경계나 DB 잠금이 검증되기 전에는 여러 종류를 별도 함수로 동시에 호출하지 않는다.

운영 DB 적용·기능 ON·배포는 이 문서에 포함되지 않는다.
