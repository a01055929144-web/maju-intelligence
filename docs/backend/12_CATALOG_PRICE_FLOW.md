근거: 운영 DB 읽기 조사(11/18 13:20) — `self_order_price`, `store_member_order_catalog`, `store_order_eligibility`, `save_purchase_cost_date_batch_v2`.

## 1. 용어 (화면 · 문서 · 지시서 모두 이 말만 쓴다)

| 용어 | 뜻 | 내부 이름 |
|---|---|---|
| **매입 이력** | 올린 파일의 원본 거래 행 전부. 같은 상품·적용일에 서로 다른 단가가 있어도 각각 보존하며 이력 저장 자체는 현재가를 고르지 않음 | `purchase_receipt_lines`, `supplier_product_cost_history` |
| **현재 매입가** | 판매가 계산에 쓰는 매입가(상품마다 1개). 적용 가능한 날짜 중 가장 늦은 날짜의 원본 후보에서 사용자가 고른 한 행으로 결정 | `product_catalog.purchase_price(_date)` |
| **기본가** | 현재 매입가 × 회사 기본 마진(분류 · 품목 마진 포함) | `pricing_p0_effective` |
| **카탈로그** | 기본가에 분류별 %를 다르게 준 가격 묶음. 매장마다 1개 지정 | `margin_templates`, `normalized_customers.margin_template_id` |
| **기본 카탈로그** | = 기본가 = **전체 상품**. 카탈로그를 지정받지 않은 모든 매장의 가격. 새 매장은 항상 여기서 시작 | `margin_template_id is null` |
| **단가표 · 견적서** | 고객사가 골라 보낸 문서. 게시한 순간 가격이 문서에 고정 | `pricing_document_versions` |
| **약속가** | 보낸 단가표 · 견적서의 가격. 유효기간까지 유지 | 게시본 `content.lines[].price` |
| **유효기간 · 연장** | 약속가가 지켜지는 마지막 날. 연장 = **고객사가 고름**: ⓐ 약속가 그대로 기간만 늘림 ⓑ 최신 가격으로 다시 계산해 새로 게시(둘 다 같은 링크) | `content.validUntil` |
| **매장 가격** | 매장이 주문할 때 실제 적용되는 가격(아래 3절 순서로 하나) | `self_order_price` |
| **가격 공개 매장** | 가입 후 전체 상품 **가격까지** 보는 매장 = **고객사가 "외식업 확인"을 누른 매장** | 신설(CX-122) |
| **거래처** | 매출처 + 매입처를 함께 부르는 말. 등록 화면 · 규칙은 하나 | `normalized_customers` · `product_suppliers` |
| **개업 준비 거래처** | 사업자번호가 아직 없는 거래처. 나중에 번호를 받으면 확인 후 정상 전환 | 신설 상태(CX-126) |
| **주문 가능 매장** | 가격 공개 + 고객사 확인 + 배송 권역 + 결제 조건 | `store_order_eligibility` |

금지어: "등급가"(→ 카탈로그 가격), "판매가 탭"(→ 기본 카탈로그), "반영"(→ 현재 매입가 변경 / 이력만 저장 중 하나로 정확히).

## 2. 전체 플로우

```
[고객사] 매입 파일 올림 ─▶ 원본 행 전부 매입 이력 저장(같은 상품·날짜·다른 단가도 각각 보존)
                            └▶ 현재 매입가 변경을 고른 경우: 상품별 가장 늦은 유효 적용일의 후보 중 원본 한 행 선택
                                 ├▶ 선택·검증 완료 → 현재 매입가 변경 → 기본가 · 카탈로그 재계산
                                 └▶ 선택 보류 / 단위·환산 미확인 → 이력만 저장, 현재가·판매가 그대로
                                   │
            문서 목록: "다시 계산 필요 N품목" (보낸 단가표 · 견적서는 그대로 = 약속가)
                                   │
[고객사] 단가표 · 견적서 보냄(링크 · A4) ─▶ [매장] 가입 없이 문서만 보기(약속가)
                                   │
[매장] 카카오 가입 + 매장 정보 ─┬─ 사업자 있음 ─▶ 전체 상품 이름만 · "고객사 확인 후 가격 공개"
                                │      └ [고객사] 외식업 확인 누름 ─▶ 전체 상품 + 가격(기본 카탈로그)
                                └─ 개업 준비 ─▶ 고객사 대표번호 전화
                                       └ [고객사] 매출처 관리에서 "개업 준비 매출처" 등록 ─▶ 매장 초대 링크 ─▶ 가입 · 연결
                                   │
[고객사] 매출처 확인(매출처 관리에서 생성 · 연결) ─▶ 배송 권역 · 결제 조건 ─▶ 주문 가능
                                   │
[매장] 주문하기 ─▶ 매장 가격(3절) 그 순간 값으로 주문 줄에 고정
```

### 2-1. 매입가 적용일과 저장 경계 (11/21 대표 결정)

- `가장 늦은 날짜`는 **엑셀 행의 적용일** 중 현재까지 유효한 가장 최근 날짜다. 파일 업로드일이나 저장 버튼을 누른 날이 아니다. 미래 적용일의 행은 이력에 보존하되 그 날짜 전에는 현재가로 선반영하지 않는다.
- 같은 상품코드에 여러 매입가가 나와도 원본 행은 모두 이력으로 남긴다. 현재 매입가는 해당 날짜의 후보 가운데 **사용자가 명시적으로 고른 한 행**으로 정한다. 고르지 못하면 현재가 변경만 보류한다.
- 신규 상품 등록으로 임시 상품 ID가 실제 ID로 바뀌어도 선택한 원본 행이 유지돼야 한다. 상품 연결 완료와 매입 이력 저장 완료는 별개이며, 저장 실패 뒤 같은 요청을 다시 시도해도 상품·이력이 중복 생성되면 안 된다.
- **구현 상태:** 위 선택·재시도 수정은 [#1220](https://github.com/a01055929144-web/maju-intelligence/pull/1220) Draft에서 검증 중이다. CI 통과만으로 운영 실파일 저장 완료를 뜻하지 않는다. 병합·배포·실사용 저장을 각각 확인한다.

## 3. 매장 가격 결정 순서 (대표 결정 ①)

1. **유효기간 안의 약속가** — 그 매장이 받은 단가표 · 견적서 중 가장 최근 게시본, 해당 품목 · 단위가 있을 때.
2. 그 외 → **매장에 지정된 카탈로그 가격**.
3. 지정 없음 → **기본가(기본 카탈로그)**.
- 유효기간이 지나면 약속가는 자동으로 빠지고 2 · 3의 **최신 가격**(현재 매입가 기준)이 적용된다.
- **연장**(대표 결정 11/18 13:38) — 연장 창에서 고객사가 고른다:
  - ⓐ **약속가 그대로 연장**: 가격은 그대로, 유효기간만 늘린 새 게시본. 매입가가 올라 이익이 낮아진 품목 수 · 최저 이익률을 함께 보여 줌(경고만, 막지 않음).
  - ⓑ **최신 가격으로 연장**: 연장 시점 최신 가격으로 다시 계산 → 바뀐 품목 미리보기(전/후 · 차이) → 새 게시본.
  - 둘 다 같은 링크 · 기록(누가 · 언제 · 어느 쪽)을 남긴다. 기본 선택은 없음(반드시 고름).
  - **연장 전 편집**(11/18 13:44): ⓐ · ⓑ 어느 쪽이든 게시 전에 품목 **추가 · 수정 · 삭제**, 단가 직접 수정, 순서 · 보이기/숨기기, 유효기간을 바꿀 수 있다. 기존 문서 편집기를 그대로 쓴다(새 편집기 금지).
    - 추가한 품목은 최신 가격(매장 가격 순서 2 · 3)으로 채우고 직접 고칠 수 있다.
    - 직접 고친 단가는 "직접 수정" 표시 · 원래 계산가와 차이 · 이익률을 함께 보여 준다(이익률 기준 아래면 경고, 막지 않음).
    - 게시 전 요약: 그대로 N · 가격 바뀜 N · 추가 N · 삭제 N. 게시하면 새 게시본 = 새 약속가.
- 시가 품목(`order_pricing_mode='market'`) · 행사가 · 품목 마감은 기존 규칙 그대로.
- 이 순서는 **서버 함수 하나**에만 둔다(화면 계산 금지).

## 4. 가격 공개 판정 (대표 결정 11/18 13:38: 고객사가 직접 "외식업 확인"을 누른 매장만)

| 판정 | 조건 | 보이는 것 |
|---|---|---|
| **가격 공개** | 고객사 직원(권한 있는 사람)이 매장 정보에서 **"외식업 확인"**을 누름 | 전체 상품 + 매장 가격 |
| **확인 전** | 가입했지만 아직 안 누름 | 전체 상품 이름 · 규격 · 분류만. 가격 칸 "고객사 확인 후 공개" |
| **개업 준비** | 사업자 없음 | 고객사 대표번호 전화 버튼(기존) → 7절 |
- 자동 공개는 없다. 대신 고객사 화면에 **참고 표시**만: 고객사가 보낸 링크로 가입함 · 국세청 계속사업자 · 영업신고(일반 · 휴게음식점 · 제과점) 일치 여부.
- 확인 · 취소는 기록(누가 · 언제 · 메모). 취소하면 다음 화면부터 가격 숨김(이미 들어온 주문은 그대로).
- 고객사 "새 매장 확인" 목록에 확인 전 매장 수를 보여 준다(놓치지 않게).

## 7. 거래처(매출처 · 매입처) 공통 등록 · 개업 준비 (대표 결정 11/18 13:38)

**지금**: 매출처 빠른 등록은 사업자번호 없이 저장은 되지만 "개업 준비" 상태 · 개업 예정일 · 나중에 번호 보완 흐름이 없다. 매장이 스스로 가입하는 개업 준비 경로(`activate_preopening_store_owner_v1`, 플래그 OFF)만 매출처를 자동으로 만든다. 매입처(`product_suppliers`)는 주소 · 사업자 상태 · 사업자 형태 · 계산서 이메일 · 사업자등록증 칸이 없어 매출처와 다르다.

**바뀔 것**: 매출처 · 매입처는 **같은 등록 화면 · 같은 도메인 규칙**(customer 도메인의 거래처 공통 모델), 저장만 각자 테이블.

| 항목 | 규칙 |
|---|---|
| 상태 | `사업자 확인됨` / `개업 준비` / `휴업` / `폐업` (국세청 확인 결과 · 수동) |
| 개업 준비 필수 | 상호(예정) · 대표자 · 연락처 · 주소(카카오 검색 공통 컴포넌트) · 개업 예정일(선택) · 메모 |
| 사업자 있음 필수 | 위 + 사업자번호(국세청 확인) · 사업자 형태(개인/법인) · 과세 구분 · 계산서 이메일 |
| 중복 막기 | 저장 전에 연락처 · 사업자번호 · 주소+상호로 기존 매출처 · 매입처 · 리드를 먼저 보여 주고 "이 거래처 맞음"이면 연결(새로 만들지 않음) |
| 번호 보완 | 개업 준비 거래처에 "사업자번호 받기" 버튼 → 국세청 확인 → `사업자 확인됨` 전환 · 이력. 개업 예정일 지나도 번호 없으면 목록에 표시 |
| 매장 연결(매출처만) | 개업 준비 매출처 상세 → **매장 초대 링크 보내기** → 점주 카카오 가입 시 이 매출처에 연결(`registration_pending` 계정). 가격 공개는 4절(외식업 확인) |
| 리드 연결 | 영업 리드에서 만든 경우 리드 → 매출처 전환 기록 유지(기존 리드-거래처 연속성 규칙) |
| 문서 · 전표 | 개업 준비 거래처는 견적 · 단가표 · 주문 가능, **세금계산서는 사업자 확인 후**(그 전엔 거래명세서만) |

**DB(초안)**: 두 테이블에 같은 의미의 칸을 맞춘다 — `business_status` 허용값에 `registration_pending`, `expected_opening_date date null`, (매입처) `address · address_detail · business_status · business_status_checked_at · business_entity_type · tax_invoice_email · business_license_file_url`. 기존 행은 값 그대로(번호 있으면 기존 상태 유지).
