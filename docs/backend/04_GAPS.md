# 계약과 현재 코드의 차이

기준: [백엔드 계약서](00_BACKEND_CONTRACT.md). `01_SCHEMA.md`의 “적용 기록”은 저장소 위치이며 운영 적용 증거가 아니다. 실제 적용은 별도 읽기 조회로 확인한다.

| 규칙 | 현재 차이 | 다음 작업 |
|---|---|---|
| I-1 | 모든 기존 테이블의 복합 FK·RLS를 자동 문서만으로 증명할 수 없다 | PG17 전체 스키마에서 외부키·RLS 검사 |
| I-2 | 전표 원장은 `partner_ledger_entries`를 쓰지만 예치금 유형이 없다 | D 단계에서 deposit 유형 추가, 불변 검사 |
| I-3 | 전표 기반 `inventory_document_positions`는 있으나 주문 예약은 계산 뷰가 없다 | 재고 원장 단계에서 주문 `closed` 뷰 추가 |
| I-4 | P0/P1/P2가 각기 가격을 계산하며 계약 6절 `resolve_price` 단일 함수가 없다 | 가격 함수 통합 후 모든 소비자 연결 |
| I-5 | 확정 전표 줄 스냅샷은 있으나 새 기준가와 독립성 통합 검증이 없다 | PG17 회귀 시나리오 추가 |
| I-6 | 예치금 원장·행 잠금이 없다 | D 나머지 단계 |
| I-7 | 일부 주문·전표·가져오기 멱등 처리가 있으나 네 흐름의 단일 계약 검사는 없다 | 각 RPC에 멱등 키 일치 테스트 |
| I-8 | `purchase_orders` 정식 테이블·매입전표 1:1 제약이 없다 | 발주 단계 |
| I-9 | 공개 링크 토큰 확인은 있으나 회사별 플래그 경계는 U-2 PR #158 대기 | 운영 DB 승인 뒤 대표 회사만 활성화 |
| I-10 | 신규 migration 승인 줄 CI 검사는 PR #161에 있음 | CI 통과·병합 확인 후 적용 |
| I-11 | `product_base_prices`는 승인 전 초안이다 | 기준 단가 단계에서 날짜별 유일성 PG 검사 |
| I-12 | 중앙값 규칙은 구매가 제안과 실중량에만 적용; 통합 순수 함수가 없다 | 가격 단계에서 홀짝·기록 없음 테스트 |
| 상태 | `store_orders`에 `closed`가 없다 | 매장 링크 이후 마감 단계 |
| 이전 | `sales_transactions`와 `sales_quotes`는 별도 레거시 정본 | 자동 변환 금지, 이전 계획만 수립 |

보류: `ledger_entries`, `product_purchase_units`, `company_unit_policies`를 새로 만들지 않는다. 2% 수금 방식과 참고 단가 칸 이름은 확정 전까지 구현하지 않는다.
