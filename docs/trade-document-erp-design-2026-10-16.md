# 전표 기반 ERP 문서·조회 설계

> 설계 전용 문서입니다. 구현하거나 운영 DB에 적용하지 않습니다. SQL 초안은 `docs/sql-drafts/trade-document-foundation.sql`입니다.

## 1. 결정

매출·매입을 별도 원장으로 중복 저장하지 않고 `trade_documents`와 `trade_document_lines`를 단일 거래 원천으로 사용한다. 거래명세서, 거래처·매입처 원장, 세금계산서 대상 집계와 운영 조회는 모두 확정 전표에서 파생한다.

- `document_type`: `sale` 또는 `purchase`
- `transaction_type`: `normal` 또는 `return`
- `status`: `draft`, `confirmed`, `cancelled`
- 전표일자는 KST 업무일인 `trade_date`로 저장한다.
- 확정 전표의 거래 내용과 라인은 수정하지 않는다. 정정은 취소 사유를 남기고 새 전표로 재발행한다.
- 반품은 금액을 음수로 직접 입력하지 않고 `transaction_type='return'`으로 구분하여 집계 시 부호를 반전한다.

공통 전표 모델은 검색·문서 발행·원장 집계 코드를 한 번만 유지할 수 있다는 장점이 있다. 매출·매입 전용 테이블보다 타입 제약이 필요하지만, 정확히 한 거래 상대만 연결하는 CHECK와 복합 FK로 이를 통제한다.

## 2. 데이터 모델

### trade_documents

- 테넌트: `company_id`
- 상대방: 매출은 `customer_id`, 매입은 `supplier_id`만 설정
- 문서번호: 회사·연도·구분별 자동 채번, 예: `S-2026-000001`, `P-2026-000001`; 발급 후 불변
- 출처: `quote`, `order`, `manual`, `upload`와 출처 키. 같은 출처의 중복 생성을 막는 멱등 키 포함
- 합계: 공급가액·부가세·총액. 확정 RPC가 라인 합계에서 계산하고 고정
- 이력: 확정·취소 담당자와 시각, 취소 사유, 원본/재발행 전표 연결

### trade_document_lines

- 회사 마스터 상품 `product_catalog_id` 연결, 매입 전표는 `supplier_product_id`도 선택 연결
- 품목코드·명·규격·판매 단위·과세구분을 스냅샷으로 저장
- 수량, 단가, 공급가액, 부가세, 합계를 원 단위로 저장
- 계산: `공급가액 = round(수량 × 단가)`, 과세 라인은 `부가세 = round(공급가액 × 10%)`, 면세는 0, 문서 합계는 라인 합산
- 계약 단가는 매출 초안 생성 시 기본값으로만 불러오며, 전표 라인에는 당시 가격을 고정한다.

### trade_payments

- `partner_type`: `customer` 또는 `supplier`
- 매출처 입금은 `receipt`, 매입처 지급은 `payment`
- 금액·일자·수단(`cash`, `bank`, `card`)과 멱등 키 저장
- 수정·삭제하지 않는다. 정정은 원 지급을 참조하는 반대 전표를 추가한다.
- 잔액은 확정 전표 합계에서 입금·지급을 차감해 계산하며 별도 잔액 컬럼을 두지 않는다.

### trade_document_issues

거래명세서 발행 시 발행번호, 전표 스냅샷 JSON, 내용 해시, 발행자·시각을 보관한다. 이후 원본 정보가 바뀌어도 발행본은 동일하다. 공개 토큰·이미지 발송은 1차 범위에 포함하지 않는다.

## 3. 무결성·권한

- 모든 회사 데이터 참조는 `(company_id, id)` 복합 FK로 같은 회사만 허용한다.
- 신규 테이블은 RLS를 활성화하고 `anon`, `authenticated` 권한을 회수한다. 앱 서버의 검증된 `service_role` 경로만 사용한다.
- API는 기존 세션의 `manage_sales` 권한과 `company_id`를 함께 검증한다.
- 확정 전표는 핵심 필드와 라인 변경을 DB 트리거로 차단한다. 취소는 금액을 바꾸지 않고 상태·사유만 기록한다.
- 원가·마진·매입처 정보는 공개 문서와 향후 매장 화면 응답에서 제외한다.
- 번호 채번과 확정은 RPC로 처리하여 동시 요청과 부분 저장을 방지한다.

## 4. 기존 데이터

`sales_transactions`는 과거 업로드 데이터로 그대로 유지하며 자동 전표 변환하지 않는다.

- 운영 조회에서는 `source='legacy_sales_transaction'`로 표시한 UNION 조회를 제공할 수 있다.
- 레거시 데이터는 매출 통계에만 합산하고, 미수금 원장·거래명세서·세금계산서 발행 근거에는 자동 포함하지 않는다.
- 사용자가 특정 기간을 검증해 전표로 이관하는 기능은 별도 승인 후 설계한다.

## 5. 조회와 성능

공통 필터는 기간, KST 요일, 거래처, 매입처, 상품, 담당자, 권역, 과세구분, 상태다. 기본 집계는 일·주·월·요일·거래처·매입처·상품별 공급가액·부가세·합계다.

- 전표: `(company_id, trade_date desc, id)`, 상대방+일자, 상태+일자 인덱스
- 라인: `(company_id, document_id, line_no)`, 상품+전표 인덱스
- 지급: 회사+상대방+지급일 인덱스
- 목록은 offset 대신 `(trade_date, id)` 커서 페이지네이션 사용
- 수십만 라인까지는 인덱스 기반 실시간 집계로 시작하고, 측정 후 월별 집계 뷰를 추가한다.

세금계산서는 확정 매출 전표를 월·거래처별로 묶어 과세 공급가액·부가세와 면세 공급가액을 분리한 발행 대상 목록까지만 만든다. 전자발행은 향후 대행사 어댑터로 연결한다.

## 6. 화면 위치

`운영 관리` 하위에 다음 화면을 둔다. 기존 라우트와 메뉴 재편 원칙은 유지한다.

- 매출 전표: 목록, 작성, 확정, 반품, 취소·재발행
- 매입 전표: 목록, 작성, 확정, 반품, 취소·재발행
- 전표 상세: 거래명세서 A4 인쇄
- 매출처 상세: 거래처원장(전표·입금·기초/기말 잔액)
- 매입처 상세: 매입처원장(전표·지급·기초/기말 잔액)
- 거래 조회: 기간·요일·상대방·상품별 검색과 합계
- 세금 문서: 월별 발행 대상 집계(후속 단계)

## 7. 문서 생성 흐름

1. 견적·향후 주문·수기 입력에서 전표 초안을 만든다.
2. 계약 단가와 상품 스냅샷을 확인하고 라인을 저장한다.
3. 확정 RPC가 라인 합계를 재검증하고 문서번호를 발급한다.
4. 확정 전표가 거래처·매입처 원장에 즉시 반영된다.
5. 거래명세서 발행 시 발행 스냅샷과 해시를 저장하고 A4 인쇄/PDF를 생성한다.
6. 오기재는 기존 전표를 취소하고 새 전표로 재발행하여 연결 이력을 남긴다.

## 8. 1차 구현 범위

1. 매출·매입·반품 전표 초안 작성, 확정, 취소 후 재발행
2. 확정 전표 기반 거래명세서 A4 인쇄/PDF
3. 입금·지급 등록과 매출처·매입처 원장 조회
4. 기간·요일·상대방·상품별 기본 검색·합계

온라인 명세서 공개 링크, 카카오톡 이미지 발송, 카드 자동 차감, 전자세금계산서 연동, 저장된 조회, 대규모 집계 최적화는 1차에서 제외한다.

## 9. 구현 순서와 승인 지점

1. 스키마·RLS·트리거·RPC SQL 검토 및 운영 적용 승인
2. 전표 도메인 계산과 서버 API
3. 전표 작성·확정·취소 화면
4. 입금·지급과 원장 조회
5. 거래명세서 발행·인쇄

각 단계에서 기존 `sales_transactions`를 변경하거나 자동 이관하지 않는다.
