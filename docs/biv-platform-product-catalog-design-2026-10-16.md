# BIV 플랫폼 표준 품목 계층 설계 (2026-10-16)

> 전략 설계 문서입니다. 이 문서와 연결된 SQL은 검토용 초안이며 아직 구현하거나 운영 DB에 실행하지 않습니다.

## 1. 목표와 경계

BIV 플랫폼 표준 품목은 여러 유통사의 이름·코드·단위가 다른 상품을 같은 실물 품목으로 식별하기 위한 **플랫폼 내부 식별 계층**이다. 유통사는 계속 자기 `product_catalog`와 `supplier_products`를 사용하며 화면의 품목명·코드를 바꾸지 않는다.

- 플랫폼 식별: `platform_products`
- 회사 판매 품목: `product_catalog`
- 회사 매입처 원본 상품: `supplier_products`
- 연결: `company_product_platform_links`
- 가격 원칙: 플랫폼 품목은 동일성만 제공한다. 견적·계약단가·추천 가격은 항상 요청 회사가 소유한 원가와 계약단가로 계산한다.
- 원가 공유 원칙: 원본 단가는 플랫폼 운영자만 볼 수 있다. 회사에는 동의한 **다른 회사 3곳 이상**의 익명 집계만 보여준다.

플랫폼 품목을 연결했다는 이유로 다른 회사의 `supplier_products`, 공급처, 거래처 가격, 계약 단가를 조회하거나 계산 원천으로 사용할 수 없다.

## 2. 데이터 모델

### 2.1 플랫폼 품목

`platform_products`

- `id`, 변경 불가 플랫폼 코드 `platform_product_code`
- 표시명과 `normalized_name`
- `brand_id`, 원산지, 규격 값·단위, 표준 비교 단위
- 과세 구분, 분류, 용도 태그
- `barcodes text[]`: 관리 편의를 위한 배열. 중복 바코드는 DB 트리거가 막는다.
- `status`: `active | inactive | merged`; 병합 시 `merged_into_product_id` 필수
- 생성·수정 플랫폼 관리자 스냅샷

`platform_brand_dictionary`

- 정규 브랜드명, 표시명, 별칭 배열, 활성 여부
- 정규 브랜드명은 플랫폼 전체에서 유일하다.

`platform_product_aliases`

- 회사 원본을 바꾸지 않고 플랫폼이 기억하는 정규화 별칭
- 이름·브랜드·원산지·규격·단위 시그니처와 근거, 확정 여부
- 동일한 이름만으로 실물 품목을 단정하지 않도록 전체 시그니처 단위로 유일성을 둔다.

### 2.2 회사 품목 연결

`company_product_platform_links`

- 한 행은 회사 판매 품목 또는 매입처 상품 중 정확히 하나를 플랫폼 품목에 연결한다.
- `source_type`: `product_catalog | supplier_product`
- `status`: `candidate | auto | confirmed | rejected`
- 점수, 후보 순위, 이름·브랜드·원산지·규격·단위·바코드 일치 여부, 매칭 엔진 버전
- 플랫폼 표준 단위로 환산하는 `source_to_platform_ratio`와 확정 여부
- 확정 주체: `company_user | platform_admin`, 확정자 스냅샷과 시각. 회사 확정자는 `(company_id, company_members.id)` 복합 FK로 같은 회사만 허용하고, 쿠키 기반 플랫폼 관리자는 member ID 없이 관리자 스냅샷을 기록한다.
- 회사 품목 FK는 모두 `(company_id, id)` 복합 FK다. 다른 회사 품목 ID를 연결할 수 없다.
- 같은 원본에 `auto/confirmed` 활성 연결은 하나만 허용한다. 후보는 최대 3개이며 재채점할 때 기존 확정 연결은 보존한다.

현재 `supplier_product_matches`의 파서, `scoreProductMatch`, 확정 보존 원칙을 재사용하되, 첫 단계에서는 플랫폼 후보를 별도 테이블에 기록한다. 회사 내부 매핑과 플랫폼 매핑은 목적이 다르므로 기존 테이블을 덮어쓰지 않는다.

### 2.3 데이터 이용 동의

`company_platform_data_consents`는 현재 상태를, `company_platform_data_consent_events`는 변경 이력을 보관한다.

- 목적은 우선 `cost_benchmarking` 하나로 시작한다.
- 현재 동의 버전, 상태, 동의자 `company_members.id`, 이름, 동의·철회 시각을 저장한다.
- 동의 이벤트는 append-only이며 UPDATE/DELETE 트리거로 변경을 막는다.
- 동의 철회 즉시 신규 집계에서 제외한다. 이미 생성된 집계 스냅샷은 다음 재계산에서 제거하며 회사 API는 현재 동의 상태도 재확인한다.
- 정책 버전이 올라가면 이전 동의를 자동 승계하지 않는다. 새 버전 동의 전까지 제외한다.

## 3. 가격 정규화와 익명 집계

### 3.1 집계 입력 조건

다음 조건을 모두 만족한 원가만 사용한다.

1. 회사가 현재 정책 버전의 `cost_benchmarking`에 동의했다.
2. 플랫폼 링크가 `confirmed`이고 회사 품목·공급상품이 활성이다.
3. `supplier_products.cost_confirmed=true`, `latest_cost >= 0`이다.
4. 단위가 같거나 `source_to_platform_ratio`가 사람이 확정됐다.
5. 가격 시점이 허용된 최신 기간 안에 있다.

표준 단위 원가는 `매입 원가 / source_to_platform_ratio`로 계산한다. 한 회사에 같은 플랫폼 품목의 공급상품이 여러 개이면 먼저 그 회사 안에서 최신 확정 원가의 중앙값 하나로 축약한다. 이로써 공급처나 행이 많은 회사가 집계를 과도하게 지배하지 않는다.

### 3.2 최소 출처 수 적용 위치

최소 출처 수 기본값은 **요청 회사를 제외한 서로 다른 회사 3곳**이다. 다음 두 경계에서 중복 적용한다.

1. DB 집계 함수/스냅샷 생성: `HAVING count(distinct company_id) >= 3`
2. 회사용 API 응답 직전: 현재 동의와 `source_company_count >= 3`을 다시 확인

회사 응답에는 중앙값, 25/75 분위, 회사 자체 원가 대비 차이율, 출처 수 구간(`3-5`, `6-10`, `11+`)만 포함한다. 개별 단가, 최저·최고 단가, 회사명, 공급처명, 정확한 출처 수는 노출하지 않는다. 3곳 미만이면 값 대신 `비교 데이터 부족`만 반환한다.

`get_company_market_benchmark`는 `service_role`만 실행할 수 있는 `SECURITY INVOKER` 함수다. `anon/authenticated`에는 테이블·뷰·함수 권한을 모두 회수한다. 애플리케이션은 로그인 세션의 회사 ID를 서버에서 확정하고 다른 회사 ID를 요청 파라미터로 신뢰하지 않는다.

## 4. 권한 모델

현재 플랫폼 관리자 인증은 Supabase Auth 역할이 아니라 `requireAdminSession()`의 서명 쿠키다. 따라서 DB가 JWT만으로 BIV 관리자를 식별할 수 없다.

- 플랫폼 원본 테이블: RLS 활성화, `anon/authenticated` 권한 없음, 공개 정책 없음
- 서버: `service_role`로만 접근
- 플랫폼 관리자 API: 반드시 `requireAdminSession()`을 먼저 통과하고 `super_admin/operator`별 쓰기 권한을 검사
- 회사 API: 회사 세션의 `companyId`를 서버가 고정하고 모든 회사 원본 쿼리에 `company_id` 조건 적용
- 회사는 플랫폼 품목의 공개 가능한 설명과 자기 연결만 조회한다. 다른 회사 링크와 원가는 반환하지 않는다.
- 향후 DB 수준 역할 분리를 더 강화하려면 플랫폼 관리자 전용 백엔드 자격증명을 별도 프로젝트/DB 역할로 분리한다. 현재 service role 키를 브라우저에 제공하는 방식은 어떤 경우에도 허용하지 않는다.

초기 권한표는 다음과 같다.

| 작업 | `super_admin` | `catalog_operator` | 회사 관리자 |
|---|---:|---:|---:|
| 플랫폼 품목·브랜드 생성/수정/비활성 | 허용 | 허용 | 불가 |
| 플랫폼 품목 병합 | 허용 | 승인 요청만 | 불가 |
| 연결 큐·일괄 확정·신규 승격 | 허용 | 허용 | 자기 회사 후보 확정만 |
| 데이터 이용 동의 현황 조회 | 허용 | 불가 | 자기 회사만 |
| 민감정보 감사 로그 조회 | 허용 | 불가 | 불가 |
| 원본 회사 원가·거래처 단가 조회 | 허용, 사유·감사 필수 | 불가 | 불가 |
| 역제안·수수료 진행 관리 | 허용 | 불가 | 불가 |
| 익명 시장 집계 | 운영 확인 가능 | 불가 | 자기 회사 컨텍스트에서만 |

`service_role`은 RLS를 우회하므로 이것만으로 플랫폼 관리자임을 뜻하지 않는다. 모든 신규 서버 함수는 `admin`용과 `company`용 모듈을 분리하고, 범용 `supabaseRequest`로 원본 플랫폼 가격을 임의 조회하지 못하도록 코드 리뷰·인증 경계 검사 대상에 추가한다.

### 기존 관리자 계정의 역할 기본값

현재 로그인 구현은 단일 `ADMIN_EMAIL`이 성공하면 항상 `super_admin` 세션을 발급한다. SQL은 환경변수를 읽을 수 없으므로 관리자 이메일을 마이그레이션에 하드코딩하지 않는다.

1. 배포 후 `platform_admin_roles`가 비어 있을 때만 서버가 현재 `ADMIN_EMAIL`과 일치하는 첫 정상 로그인에 `super_admin` 부트스트랩을 허용한다.
2. 첫 행 이후 자동 기본값은 없다. 새 운영자는 기존 `super_admin`이 역할을 명시 등록한다.
3. 역할 행이 비활성·누락되면 기존 관리자 쿠키가 있어도 플랫폼 메뉴는 fail-closed로 거부한다.
4. 기존 `AdminSession.role`은 호환용이고 플랫폼 기능의 최종 권한은 매 요청마다 활성 `platform_admin_roles`를 조회한다. 역할 변경 즉시 기존 쿠키 권한도 축소된다.

### 운영자 원본 가격 접근 감사

`platform_data_access_audit_logs`는 원본 가격 조회마다 기록한다.

- 관리자 이메일·이름·역할, 목적, 플랫폼 품목, 필터, 결과 행 수, 요청 ID, IP 해시, 시각
- 원본 가격 자체는 로그 metadata에 넣지 않는다.
- 감사 로그는 append-only 트리거로 UPDATE/DELETE를 차단한다.
- `/admin`의 품목별 회사 단가 분포와 역제안 후보 API는 **조회 성공 전에 감사 로그 기록 성공을 요구**한다. 감사 기록 실패 시 원본 조회도 실패 처리한다.

## 5. 화면 설계

### `/admin` 메뉴 구조

기존 메뉴는 유지하고 다음 세 그룹을 추가한다.

| 그룹 | 메뉴 | 경로 | 주요 역할 |
|---|---|---|---|
| 플랫폼 상품 | 표준 품목 | `/admin/platform-products` | 마스터·브랜드·별칭 |
| 플랫폼 상품 | 회사 품목 연결 | `/admin/platform-products/links` | 미연결 큐·후보·일괄 확정 |
| 데이터 거버넌스 | 이용 동의 | `/admin/platform-data/consents` | 회사별 동의 현황 |
| 데이터 거버넌스 | 민감정보 감사 | `/admin/platform-data/audit` | 원가·거래처 단가 조회 이력 |
| 시장 운영 | 회사 간 단가 비교 | `/admin/platform-pricing/benchmarks` | 품목별 회사 원가 분포 |
| 시장 운영 | 역제안 관리 | `/admin/platform-pricing/proposals` | 후보·제안·수락·수수료 |

권한 없는 메뉴는 숨기되 page/API에서도 다시 역할을 확인한다. 직접 URL 접근은 403으로 거부한다.

### `/admin/platform-products`

- 플랫폼 표준 품목 목록·생성·수정·비활성·병합
- 바코드, 브랜드 사전, 별칭 관리
- 병합 전 연결 회사 수와 영향을 확인하고 대상 품목으로 링크를 이동하는 별도 확인 단계
- 목록 필드: 플랫폼 코드, 품목명, 브랜드, 원산지, 규격·단위, 과세, 분류, 용도, 바코드, 연결 회사/상품 수, 상태, 최종 수정자·시각
- 삭제 대신 비활성만 제공하며 연결된 품목은 비활성 사유를 필수로 받는다.

### `/admin/platform-products/links`

- 미연결 회사 품목·매입처 상품 큐
- 회사·공급처 원본 이름은 운영자에게만 표시
- 기존 매칭 점수와 항목별 일치, 후보 3개, 플랫폼 신규 품목 생성
- 회사 확정과 플랫폼 운영자 확정을 구분해 기록
- 필터: 회사, 원본 종류, 공급처, 점수, 수집일, 후보 없음
- 일괄 작업: 동일 후보 확정, 거절, 재채점. 신규 승격은 유사 품목·바코드 충돌을 먼저 확인한다.

### `/admin/platform-data/consents`

- 회사명, 상태, 정책 버전, 동의자, 동의·철회 시각, 현재 집계 포함 여부
- 미동의·철회·구버전 동의는 `집계 제외`로 표시한다.
- 운영자는 회사 동의를 임의 변경하지 않고 이벤트를 조회한다.

### `/admin/platform-data/audit`

- 운영자, 역할, 대상 회사, 데이터 종류, 화면, 접근 목적, 요청 ID, 결과 행 수, 시각
- 원가·거래처 단가 자체는 감사 metadata에 저장하지 않는다.
- 조회·다운로드 모두 `super_admin` 전용이며 다운로드도 새 감사 이벤트를 남긴다.

### `/admin/platform-pricing/benchmarks`

- 동의 회사만 포함한 표준 단위 원가 분포
- 회사별 원본 값은 운영자 전용이며 열 때마다 접근 사유를 받고 감사 로그 기록
- 역제안 후보: 해당 회사 원가가 자신을 제외한 동의 회사 3곳 이상 중앙값보다 설정 비율 이상 높을 때 표시
- 수수료 제안과 계약 체결은 별도 도메인으로 두고, 이 단계에서는 후보만 제공
- 필드: 플랫폼 품목, 회사, 표준 단위 원가, 최근 관측일, 타사 중앙값·분위수, 차이율. 원본 회사별 표는 `super_admin`만 조회한다.

### `/admin/platform-pricing/proposals`

- 후보 회사·품목, 회사 원가, 비교 중앙값, 차이율, 월 예상 수량, 예상 절감액
- 상태: `candidate | proposed | accepted | rejected | commission_confirmed`
- 제안일·응답일, 담당 운영자, 메모, 수수료율·확정 수수료
- 상태 변경은 이벤트 원장에 append-only로 남기고 후보 생성 당시 기준값을 스냅샷으로 보존한다.

### 회사 상품·견적 화면

- 회사가 플랫폼 연결을 확정하거나 거절할 수 있는 후보 UI
- 시장 비교는 익명 집계만 노출
- 견적 자동화·업종 단가표·대체품 추천은 플랫폼 ID로 후보군을 찾되, 최종 가격은 해당 회사의 `supplier_products` 확정 원가·`customer_price_agreements`만 사용

## 6. 서버 경계와 테스트

필수 회귀·보안 테스트:

1. 회사 A 세션으로 회사 B의 공급상품·공급처·계약단가·플랫폼 링크를 조회하면 404/403이다.
2. 요청 body/query의 `companyId`를 B로 바꿔도 서버는 A 세션 범위만 사용한다.
3. `anon/authenticated`로 신규 테이블 SELECT와 집계 RPC 호출이 거부된다.
4. 동의 회사가 2곳이면 집계가 반환되지 않고, 타사 3곳부터 집계만 반환된다.
5. 미동의·철회·구버전 동의 회사는 분모와 값에서 제외된다.
6. 한 회사에 공급상품이 여러 개여도 출처 회사 수는 1이며 회사별 대표값 하나만 반영된다.
7. 환산 미확정 상품은 비교에서 제외된다.
8. 플랫폼 관리자의 원본 가격 조회는 감사 로그 없이 성공할 수 없다.
9. 플랫폼 품목이 같아도 회사 A 견적이 회사 B 원가나 계약단가를 사용하지 않는다.
10. 병합 품목은 활성 대상 ID로만 조회되고 순환 병합이 거부된다.
11. `catalog_operator`는 품목·연결 API를 사용할 수 있지만 동의·감사·원가 비교·역제안 API와 직접 URL 접근은 403이다.
12. 비활성 또는 역할 행이 없는 기존 관리자 세션은 플랫폼 메뉴 API를 사용할 수 없다.
13. 민감 원가 조회는 먼저 생성된 감사 로그 ID·요청 ID와 함께 실행되며, 감사 INSERT 실패 시 원본 조회도 실행하지 않는다.
14. 역제안 후보는 미동의 회사 원가를 사용하지 않고 타사 출처가 3곳 미만이면 생성되지 않는다.

## 7. 단계별 구현 순서

1. **동의·감사 기반**: 운영 정책 버전 확정, 동의 화면, 동의/감사 테이블과 서버 관리자 게이트
2. **플랫폼 품목 원장**: 품목·브랜드·별칭, 바코드 중복 방지, 관리자 CRUD
3. **연결 엔진**: 기존 파서·점수 재사용, 연결 dry-run, 미연결 큐, 회사/운영자 확정
4. **회사 기능 연결**: 견적·업종 템플릿·대체품 추천의 식별만 플랫폼 ID로 전환; 가격 원천 회사 경계 테스트
5. **익명 시장 비교**: 동의한 타사 3곳 이상 집계, 회사 API 이중 임계치 확인, 캐시/스냅샷
6. **운영자 가격 분포·역제안 후보**: 원본 조회 감사 강제, 중앙값 차이 후보, 수수료 모델은 별도 승인

각 단계는 별도 마이그레이션과 승인으로 진행한다. 기존 회사 품목의 자동 연결, 기존 가격 데이터의 일괄 집계, 운영자 화면 구현은 해당 단계 승인 전 수행하지 않는다.

어드민 콘솔 구현 순서:

1. 표준 품목·연결 큐·`platform_admin_roles`
2. 데이터 이용 동의·민감정보 접근 감사
3. 회사 간 단가 비교·역제안 진행 관리

- 기존 `product_catalog`, `supplier_products`, 가격 이력의 값이나 이름·코드는 변경하지 않는다.
