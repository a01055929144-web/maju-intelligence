# ARC-04 상품·매입처 적재·매핑 점검 (2026-11-01)

> 상태: 코드·저장소 SQL 확인 완료, 운영 DB 미확인. 운영 DB 변경·기능 플래그 변경·배포를 승인하지 않는다.
> 기준: `main` `fb7175e` 및 미병합 작업지시서 PR #106.

## 1. 범위와 소유권

| 대상 | 쓰기 소유자 | 이번 점검의 판정 |
| --- | --- | --- |
| `product_suppliers` | 거래처·매입처 | 매입처 프로필과 회사 범위 ID의 원장이다. 상품 업로드는 이름 기준으로 기존 매입처를 찾아 연결한다. |
| `supplier_products` | 상품 | 파일의 원문 상품, 파싱 결과, 최신 원가와 관측일을 보존한다. |
| `supplier_product_matches` | 상품 | 공급 상품과 `product_catalog`의 후보·자동·확정 연결 및 매입→판매 환산 확인 상태를 보존한다. |
| `product_catalog` | 상품 | 회사의 판매 마스터 상품이다. 견적·가격·재고는 이 ID를 소비하지만 직접 소유하지 않는다. |
| `product_unit_conversions` | 상품 | 판매 상품의 기본 단위 환산 원장이다. 재고는 확인된 환산만 소비한다. |
| `product_catalog_imports` 및 원가/가격 관측 | 상품 | 파일 매핑 스냅샷, 처리 결과와 원가 관측의 감사 경로다. |
| `normalized_customers` | 거래처(ARC-03) | ARC-04가 쓰지 않는다. 업로드의 구매처 문자열은 관측 증거로만 남기고 거래처 연결은 별도 계약으로 넘긴다. |

PR #106은 `product_catalog`를 상품 소유로 정리하지만, 현재 `docs/02_DOMAIN_MAP.md`는 quote 소유로 기록한다. 작업지시서가 아직 병합되지 않았고 ARC-01의 소유권 표 갱신 범위와 겹치므로 이 PR에서 도메인 맵을 수정하지 않는다.

## 2. 확인된 저장 흐름

1. `/api/product-catalog/imports`가 서명된 세션에서 `company_id`와 `manage_sales` 권한을 결정한다.
2. 파일 미리보기는 상품명·원가 열을 요구하고, 공급처 상품코드 → 바코드 → 이름·규격·단위 지문 순서로 공급 상품을 식별한다.
3. 저장은 `product_suppliers` → `product_catalog_imports(processing)` → `supplier_products` → 원가 이력 → 가격 관측 → 매핑 후보 → `completed` 순으로 실행된다.
4. 표준 상품 생성은 선택한 `supplier_products`로 `product_catalog`를 만들고 `supplier_product_matches.confirmed`를 별도 저장한다.
5. 환산 비율은 활성 자동/확정 매핑에만 기록하며, `conversion_confirmed=true`가 된 뒤에만 환산 원가 계산에 사용된다.
6. 재고 SQL은 확정 매핑과 확인된 환산을 소비하며, 미확정 연결은 재고 이동에서 제외하도록 설계돼 있다.

## 3. 위험과 판정

### P0 — 파일 저장이 하나의 트랜잭션이 아니다

상품, 원가 이력, 가격 관측, 후보 매핑을 여러 REST 요청으로 순차 저장한다. 중간 요청이 실패하면 업로드 이력은 `failed`가 되지만 앞 단계의 행은 남는다. 재시도 시 대부분의 행은 유일키 upsert로 합쳐지지만 다음 상태는 원자적으로 보장되지 않는다.

- `supplier_products.latest_cost`만 갱신되고 해당 원가 이력이 없을 수 있다.
- 기존 후보를 삭제한 뒤 새 후보 저장이 실패하면 후보가 비어 있을 수 있다.
- 상품·원가·관측은 저장됐지만 이력 상태는 `failed`일 수 있다.

해결 경계는 파일 1건을 서버 함수/RPC 한 번으로 넘겨 짧은 DB 트랜잭션 안에서 검증·upsert·이력 상태 변경을 함께 수행하는 것이다. 운영 SQL은 별도 초안, 로컬 시나리오, 명시적 승인 전에는 적용하지 않는다.

### P0 — 표준 상품 생성과 확정 매핑이 부분 저장될 수 있다

`product_catalog` 생성 후 `supplier_product_matches` 저장이 실패하면 판매 마스터만 남는다. 상품 코드도 행마다 `next_product_code` RPC를 호출하므로 대량 선택에서 느리고, 코드 발급 후 실제 상품 저장 실패 시 번호가 건너뛸 수 있다. 상품 생성·코드 발급·확정 매핑은 하나의 상품 소유 진입점에서 원자 처리해야 한다.

### P1 — 대량 선택의 URL 길이 위험

기존 구현은 최대 수천 개 UUID를 한 번의 `in.(...)` 필터에 넣었다. 프록시·플랫폼의 URL 제한에 따라 조회 또는 후보 삭제가 본문 저장 전에 실패할 수 있다. 이번 PR은 조회·삭제 필터를 100개씩 나눠 이 위험만 작게 줄인다. 쓰기 트랜잭션 문제는 해결하지 않는다.

### P1 — 원가 확정과 환산 확정은 서로 다른 상태다

`cost_confirmed=true`만으로 판매 단위 원가를 확정할 수 없다. 활성 매핑과 `conversion_confirmed=true`, 양수 환산비가 모두 있어야 가격 자동화와 재고가 소비할 수 있다. `parsed_pack_quantity`는 제안값이며 사람 확인 전에는 확정 환산으로 승격하지 않는다.

### P1 — 기본 매입처 선택 경로가 업로드 흐름과 분리돼 있다

`product_supplier_defaults`와 재고의 `preferred_supplier_product_id`가 모두 존재한다. 어느 쪽이 최종 기본 매입처 원장인지 운영 스키마와 화면 동작을 확인하기 전에는 동기화하거나 자동 선택하지 않는다. ARC-04에서 하나의 쓰기 원천을 정한 뒤 ARC-08이 읽도록 해야 한다.

## 4. ARC-03 거래처 이관 경계

- ARC-04는 파일의 `buyer_name`/`buyer_code`를 `product_price_observations`에 원문 증거로 저장할 수 있다.
- ARC-04는 이름 유사도만으로 `normalized_customers`를 생성·수정하거나 `customer_id`를 확정하지 않는다.
- ARC-03이 거래처 ID를 확정하면 회사 범위 `(company_id, customer_id)` 계약으로 관측 연결을 요청한다.
- 같은 사업자번호를 가진 매입처와 매출처도 자동 병합하지 않는다. 필요하면 별도 상대방 연결 계약을 사용한다.
- 거래처 원장 업로드, 중복 병합, 원본 활동 보존은 ARC-03 소유이며 이번 변경 파일에 포함하지 않는다.

## 5. 후속 구현 게이트

1. 운영 DB에서 관련 테이블·복합 FK·유일 인덱스·RLS와 적용 마이그레이션을 읽기 전용으로 확인한다.
2. 파일 단위 멱등 키를 정의하고 동시 재시도 테스트를 추가한다.
3. 파일 저장 RPC와 표준 상품 생성 RPC를 별도 SQL 초안으로 작성한다. 오류 시 전체 rollback을 검증한다.
4. 5,000상품/100,000관측 상한에서 실행 시간, 요청 크기, 잠금 범위를 측정한다.
5. 실패 뒤 재시도 시 상품·원가 이력·관측·후보·이력 집계가 한 번만 남는지 확인한다.
6. 미확정 원가·매핑·환산이 가격 자동화와 재고에 들어가지 않는 계약 테스트를 통과한다.
