# 08 WO-8 관리자·고객·청구 구현 계획

## 상태와 범위

- 기준: PR #43의 정책·SQL 초안이 리뷰되고 CI를 통과했지만 운영 DB에는 적용되지 않았다.
- 이 문서는 관리자 요금제 CRUD, 고객 구독 화면, 결제 크론의 의존성과 승인 순서를 정리한다.
- 이 PR은 문서만 추가한다. 코드, SQL 실행, 환경변수, `vercel.json`, 기존 Toss 경로를 변경하지 않는다.
- 금액, 라이브 키, 실결제, 세금계산서 절차는 대표 승인 전까지 확정하지 않는다.

## 절대 경계

1. 운영 SQL 적용 전에는 `plans`, `subscription_monthly_usage`, 새 구독·결제 칼럼을 런타임에서 읽거나 쓰지 않는다.
2. 기존 `/settings/billing`, `/api/billing/status`, `/api/billing/callback`, `/api/billing/subscription`과 `lib/toss-payments.ts` 흐름을 변경하지 않는다.
3. 신규 기능은 `WO8_BILLING_V2_ENABLED=false`를 기본값으로 두고, OFF일 때 기존 `plan_amount_won` 화면과 청구 동작으로 완전히 돌아가야 한다.
4. 운영 DB의 결제·구독 행을 수동 수정하거나 재생성하지 않는다.
5. 청구월 중복 방지는 UI가 아니라 DB 제약, 청구 주기 키, Toss 요청 멱등성을 함께 사용한다.
6. 고객 데이터는 삭제하지 않는다. 결제 유예 종료 후에도 읽기 전용으로만 제한한다.

## 의존성 목록

### 데이터와 Supabase

- PR #43 SQL 초안: `plans`, `subscriptions.plan_code/scheduled_plan_code/trial_ends_at/grace_until/retry_attempt/next_retry_at`, `subscription_monthly_usage`, 결제 주기 키와 복합 FK.
- 적용 전 dry-run:
  - `subscription_payments.company_id`와 연결 구독의 회사 불일치 0건.
  - 기존 구독의 같은 청구월 성공 결제 중복 0건.
  - 기존 요금이 0원인 회사, 카드 미등록, 일시중지, 해지 회사 목록 확인.
- 적용 후 검증:
  - `pg_constraint`의 실제 컬럼 조합과 부분 unique index 확인.
  - `plans`와 사용량 테이블 RLS 활성화, `PUBLIC/anon/authenticated` 권한 없음, `service_role`만 접근.
  - Data API 노출 설정과 무관하게 브라우저가 새 테이블을 직접 조회하지 않음.
- 집계 원천: 영업 지역 안 `business_permit_leads` 중 임시 영업·제외 상태를 뺀 월 신규 매장, 활성 직원 수.
- 월 경계: Asia/Seoul 기준 매월 1일 00:00. 저장 키는 `YYYY-MM-01`.

### 인증과 권한

- 관리자 CRUD: 기존 `getAdminSession` 경계와 `admin_audit_logs`를 사용한다.
- 고객 화면: 기존 customer session의 `manage_billing` capability를 유지한다.
- 관리자 미리보기는 조회만 허용한다. 카드 등록·변경, 해지 확인은 고객 본인 세션에서만 실행한다.
- 브라우저에는 Toss secret, billing key, service role key를 직렬화하지 않는다.

### Toss Payments

- 기존 카드 등록과 callback 경로는 그대로 둔다.
- 환경별 `NEXT_PUBLIC_TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`는 값이 아니라 설정 여부와 테스트/라이브 구분만 대표가 확인한다.
- 청구 주기 키는 `subscription_id + KST 청구월`로 고정하고 재시도마다 바꾸지 않는다.
- Toss가 지원하는 멱등 요청 헤더·동일 orderId 재호출 응답을 테스트 환경에서 확인한 뒤 구현한다.
- 결제 성공 후 DB 기록 실패를 대비해 “먼저 DB 청구권 획득 → Toss 호출 → 결과 확정” 상태 머신 또는 원자적 RPC가 필요하다.

### Vercel 크론

- 새 청구 경로는 Node.js Route Handler와 `CRON_SECRET` 인증을 사용한다.
- `vercel.json` 일정 추가는 G4 승인 후 컨트롤타워가 담당한다. 이 계획 PR에서는 수정하지 않는다.
- 기존 `business-status` 크론에서 청구를 제거하는 시점은 전용 크론이 운영 검증된 뒤다. 같은 기간 두 경로를 동시에 활성화하지 않는다.
- 한 번의 실행은 만기 구독을 제한된 batch로 claim하고, deadline 전에 다음 실행 커서를 남긴다.
- 함수 메모리에 lock·재시도 상태를 두지 않는다. 모든 claim과 결과는 DB에 저장한다.
- 실행 로그에는 키·billingKey·카드번호·원문 오류를 남기지 않는다. 회사 ID, 청구월, attempt, 안전한 오류 코드만 기록한다.

### 알림·세무·운영

- 화면 알림과 이메일 발송 채널, 발신 주소, 수신 대상은 대표 승인 후 확정한다.
- 청구 3일 전, 체험 종료 전, 실패 1·3·5일, 유예 종료 알림은 동일 이벤트의 중복 발송 방지 키가 필요하다.
- 카드 영수증 URL은 기존 결제 이력에서 제공하되 세금계산서와 동일한 문서로 표현하지 않는다.
- 세금계산서 발행 주체·과세 유형·발행 시점을 세무 전문가 검토 후 확정한다.

## 단계별 구현

### 1단계 — 스키마 승인과 읽기 기반

Owner Domain: `billing`. Related Domain: `lead`, `organization`.

- PR #43 SQL을 최종 migration으로 승격하되 대표가 Supabase SQL Editor에서 직접 적용한다.
- 적용 전·후 검증 쿼리와 롤백 가능한 인덱스/제약 목록을 별도 체크리스트로 남긴다.
- `WO8_BILLING_V2_ENABLED=false` 플래그를 추가한다.
- repository는 플래그 OFF이면 새 테이블에 요청을 보내지 않고 기존 `plan_amount_won`만 반환한다.
- 완료 조건: 운영 스키마 확인, 권한 확인, 기존 결제 화면과 청구 결과가 적용 전과 동일.

### 2단계 — 관리자 요금제 CRUD

- 대상: `/admin/billing`, `/api/admin/billing`의 기존 인증 경계를 확장한다.
- 별도 Use Case:
  - 활성 요금제 목록 조회.
  - 코드 생성 후 코드 변경 금지, 이름·상한·금액·직원 상한·활성 여부 수정.
  - 고객사 현재 요금제와 다음 청구일 예약 요금제 지정.
- 금액은 0 이상 정수만, 월 리드/직원 상한은 0 이상 또는 무제한만 허용한다.
- 사용 중 요금제는 삭제하지 않고 비활성화한다.
- 모든 변경에 변경 전·후 값, 수행자, 회사, 이유를 감사 로그로 남긴다. secret은 기록하지 않는다.
- 대표 승인 전에는 저장 버튼 대신 “상품·금액 승인 대기” 상태를 표시한다.
- 완료 조건: 관리자 권한 401/403, 입력 검증, 감사 로그, 동시 수정 충돌, 모바일·768·1920px 회귀 테스트.

### 3단계 — 월 사용량과 추천

- KST 월별 신규 리드를 회사별로 집계한다. 최근 3개월 평균은 완료된 월을 우선하며 현재 월은 별도 표시한다.
- 집계는 멱등 upsert이며 `(company_id, usage_month)` 1행만 유지한다.
- 추천은 가장 작은 활성 상한 요금제를 반환한다. 초과 사용은 숨김·추가 청구·즉시 제한 없이 다음 달 변경 권장만 표시한다.
- 원천 행과 집계 숫자를 비교하는 회사별 샘플 검증을 수행한다.
- 완료 조건: KST 월 경계, 제외/임시 영업 제외, 재실행 동일 결과, 3개월 미만 신규 회사 처리 테스트.

### 4단계 — 고객 구독 화면

- 기존 `/settings/billing`과 카드 등록 callback은 유지한다.
- 추가 표시: 현재 요금제, 이번 달 사용량/상한, 최근 3개월 평균, 추천 요금제, 다음 청구일, 예약 변경, 체험 종료, 유예 상태.
- 요금제 변경은 `scheduled_plan_code`만 저장하고 즉시 금액이나 현재 요금제를 바꾸지 않는다.
- 해지는 데이터 삭제가 아니라 다음 결제 중단과 사용 종료일 안내로 처리한다.
- 결제 이력의 영수증은 기존 receipt URL만 열고 민감 카드정보는 마스킹한다.
- 완료 조건: owner/manager capability, 관리자 미리보기 쓰기 차단, callback 회귀, 카드 미등록·체험·실패·유예·해지 상태 테스트.

### 5단계 — 전용 청구 크론

- 새 경로 예시: `/api/cron/subscription-billing`. 실제 이름과 일정은 G4에서 확정한다.
- 처리 순서:
  1. `CRON_SECRET` 검증.
  2. KST 기준 만기·재시도 대상 batch claim.
  3. DB에서 청구 주기 키의 선행 성공·진행 중 상태 확인.
  4. 동일 결제 주기 키/orderId로 Toss 호출.
  5. 성공 또는 실패 결과와 안전한 오류 코드를 원자적으로 확정.
  6. 성공 시 예약 요금제 적용과 다음 청구일 계산, 실패 시 1·3·5일 재시도와 7일 유예 계산.
- 네트워크 timeout은 무조건 실패 재청구하지 않는다. Toss 조회 API로 orderId 상태를 확인한 뒤 재개한다.
- 한 회사 오류가 전체 batch를 중단하지 않되, 오류를 삼키지 않고 결과 집계에 포함한다.
- dry-run은 대상과 예정 금액만 계산하며 Toss와 DB를 변경하지 않는다.
- 완료 조건: 동시 실행 2개, timeout 후 재개, 동일 월 중복 호출, 월말·윤년·KST 경계, 부분 실패, 300초 deadline 전 중단 테스트.

### 6단계 — 제한 롤아웃

- 테스트 키와 전용 테스트 회사로 카드 등록→청구→영수증→실패→재시도→유예를 확인한다.
- 라이브 키는 대표가 Vercel에서 직접 설정하고 값은 코드·로그·문서에 남기지 않는다.
- 시범사 1곳은 첫 청구 전 금액·청구일·고지 수신을 대표가 확인한다.
- 첫 운영 청구 후 Toss 대시보드, DB 성공 행, 관리자 화면, 고객 영수증을 대조한다.
- 이상 시 크론만 중지하고 기존 카드·구독·결제 이력은 보존한다.

## PR 분할과 충돌 회피

1. `08-WO-8-schema`: 최종 migration과 검증 체크리스트. 운영 실행은 별도 승인.
2. `08-WO-8-admin`: 관리자 CRUD·감사 로그. 메뉴 수정 없음.
3. `08-WO-8-usage`: 월 사용량 집계·추천 repository와 테스트.
4. `08-WO-8-customer`: 기존 고객 결제 화면 확장. 기존 callback 변경 금지.
5. `08-WO-8-cron`: 전용 route·상태 머신·dry-run. `vercel.json`은 컨트롤타워 별도 변경.

각 PR은 직전 단계가 main에 병합된 뒤 최신 main에서 시작한다. 12:00 병합 묶음에는 이 문서 PR만 포함하며 PR #43과 파일이 겹치지 않는다.

## 검증 매트릭스

- Unit: 요금제 추천, 금액 정수 검증, KST 월 경계, 월말/윤년, 예약 변경, 재시도일, 유예 종료.
