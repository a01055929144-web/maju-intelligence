# MAJU 모듈형 모놀리스 정리 작업지시서 (2026-11-01)

> 상태: 설계·작업 순서 제안. 이 문서는 코드 이동, 운영 DB 변경, 기능 플래그 활성화 또는 배포를 승인하지 않는다.
> 기준: 2026-11-01 `main` (`fb7175e`). 구현 시에는 그날의 코드·운영 스키마·승인 상태를 다시 확인한다.

## 1. 목표와 범위

MAJU는 **하나의 Next.js 배포와 공유 DB**를 유지하는 모듈형 모놀리스다. 고객사 데이터는 회사 범위로 격리하고, 플랫폼 운영자 데이터는 별도 권한 경계에 둔다. 영업관리, 견적·단가표, 주문관리, ERP, TMS를 별도 서비스로 쪼개지 않는다. 각 업무의 규칙과 쓰기 경로에는 한 모듈을 소유자로 정하고, 화면은 여러 업무의 읽기 결과를 조합할 수 있다.

이번 정리는 전면 재작성이나 메뉴 개편이 아니다. 실제로 쓰는 흐름을 끊지 않으면서 소유권·데이터 원천·모듈 간 계약을 확정하고, 이후 수정하는 경로부터 점진적으로 옮긴다. 기존 URL, 보류 기능, 승인되지 않은 SQL, 레거시 업로드 데이터는 유지한다.

## 2. 현재 확인된 구조와 먼저 해결할 문서 충돌

- `domains/`에는 lead, product, pricing, quote, purchasing, erp, delivery, organization 등이 있으나 `application/`과 `lib/store.ts`에 기능이 섞여 있다. `lib/store.ts`는 약 1.4만 줄, `components/sales-route-map-workspace.tsx`는 약 1.1만 줄이다. 큰 파일이라는 이유만으로 통째로 분리하지 않는다.
- `docs/02_DOMAIN_MAP.md`는 `product_catalog`를 quote 소유로 기재하지만 현재 상품관리와 매입처 매핑은 product/purchasing 책임이다. 해당 문서의 파일 규모와 함수 목록도 최신 코드와 대조해야 한다.
- `docs/business-document-erp-design-2026-10-16.md`의 확정 전표 불변 설명과 이후 ERP 1-B v2의 수정·이동 방식은 충돌한다. 운영 적용본과 현재 RPC를 확인해 한 규칙으로 고친다.
- `docs/order-and-purchasing-direction-2026-10-15.md`의 매장 인증·가격 우선순위는 `docs/pages/09_ORDER_PRICING_WIREFRAMES.md`의 최신 링크 주문·견적가/단가표 규칙과 다르다. 최신 사용자 결정을 먼저 대조하되 운영 동작을 문서만 보고 바꾸지 않는다.
- 재고 문서는 ERP RPC 직접 호출을 설명하지만 이후 적용 지시는 전표 상태/수정 트리거가 재고 차액을 기록하는 방식이다. 실제 운영 함수·트리거를 읽기 전용으로 확인한다.

**정리 원칙:** 문서, 저장소 SQL, 운영 DB, 실제 API 동작을 각각 `확인됨 / 초안 / 보류 / 충돌`로 표시한다. 확인되지 않은 항목을 완료로 적지 않는다.

## 3. 업무 모듈과 데이터 소유권

| 모듈 | 책임 | 쓰기의 원천 | 다른 모듈에 제공하는 것 |
| --- | --- | --- | --- |
| 회사·권한 | 회사, 직원, 역할, 세션, 회사 범위 | `companies`, `company_members` | 확인된 회사·사용자·권한 문맥 |
| 영업관리 | 신규/영업 리드, 연락·방문·후속, 거래처 전환 | `business_permit_leads`, `lead_actions`; 거래처 기본정보는 customer | 전환된 `customer_id`, 영업 활동 요약 |
| 거래처·매입처 | 매출처 기본정보와 매입처 기본정보 | `normalized_customers`, `product_suppliers` | 회사 범위 상대방 ID와 표시 정보 |

| 매입·재고 | 매입처 발주·입고, 기본 단위 재고 이동·실사 | 매입 업무 기록, `inventory_movements` | 확인된 입고, 현재고·가용재고 |
| 전표·정산 | 매출/매입/반품 전표, 원장, 입금·지급·선입금 | `business_documents`와 라인, `partner_ledger_entries`, 결제 기록 | 명세서·잔액·세무/통계의 확정 금액 |
| TMS | 권역·호차·기사·배송일, 코스·완료·운행 위치 | 배송 일정·날짜 예외·코스·완료 기록 | 배송 계획과 실제 납품 결과 |
| 통계·관리자 | 위 모듈의 읽기 모델, 회사 운영 진단 | 원천 문서가 아닌 집계·스냅샷만 | 지표와 감사 가능한 조회 |

`product_catalog`는 회사 마스터 상품이고 플랫폼 표준 품목은 별도 운영자 모듈이다. 회사 간 원가 비교·역제안은 기존 보류 결정을 유지한다. 리드와 거래처는 한 객체로 강제 병합하지 않고 현재 `matched_customer_id` 연결을 기준으로 한다.

## 4. 모듈 간 규칙

1. `app/`은 인증·입력 검증·응답 변환, `application/`은 업무 흐름, `domains/`는 순수 규칙, `lib/`의 인프라는 DB·외부 API를 맡는다. `domains/`는 Next.js·React·Supabase를 import하지 않는다.
2. 하나의 업무 쓰기에는 소유 모듈의 진입점 하나를 둔다. 다른 모듈은 내부 테이블을 직접 수정하지 않고 그 진입점을 호출한다. 같은 트랜잭션이 필요한 전표·원장·재고는 검증된 DB RPC/트리거 경계에서 원자 처리한다. 이벤트 버스나 별도 서비스는 도입하지 않는다.
3. 모든 회사 데이터 조회·쓰기는 서명된 세션의 `company_id`를 서버에서 결정하고 `(company_id, id)` 복합 참조를 검증한다. 공개 매장 링크는 별도 제한된 조회 모델만 사용하고 매입가·마진·공급처·기사 개인 위치를 반환하지 않는다.
4. 금액은 원 단위 정수, 수량은 단위가 명시된 소수, 업무 날짜는 Asia/Seoul이다. 견적·주문·전표 품목명/단위/세금/가격은 결정 당시 스냅샷을 남긴다. 계산식은 한 도메인 함수와 DB 검증 결과가 일치해야 한다.
5. 보고서와 명세서는 확정 전표·원장에서 파생한다. 기존 `sales_transactions`는 레거시 수입 자료로 분리 표시하며 자동으로 미수금이나 세금계산서에 합치지 않는다.
6. 차량은 운행 자산이다. 거래처 노출 권한은 담당 직원·그날 기사인 호차와 권역 규칙으로 결정하고 차량 교체는 권한·코스를 바꾸지 않는다.

## 6. 모든 작업지시의 완료 조건

1. Owner/Related 모듈, 변경 파일·테이블·API와 유지할 기존 동작을 먼저 적는다.
2. UI부터 DB를 직접 호출하는 새 경로를 만들지 않는다. 업무 규칙·use case·인프라·UI 순서로 검증한다.
3. 회사 격리·역할·공개 응답 비노출·멱등/트랜잭션·KST·금액/수량 경계를 해당 흐름에서 확인한다.
4. 수정 범위의 테스트, 타입 검사, lint, production build, 인증 경계를 통과한다. 화면 변경이면 PC/모바일 핵심 폭을 확인한다.
5. 운영 SQL과 기존 데이터 변경은 별도 초안·검토·명시적 승인 뒤에만 한다. SQL이 미적용이면 관련 기능은 OFF로 유지한다.
6. PR에는 전후 동작, 실패·롤백 방법, 남은 초안/보류 항목을 적는다. 완료 확인 전에는 다음 단계의 플래그를 켜지 않는다.

## 7. 이번 정리에서 하지 않는 것

- 서비스 분리, 별도 메시지 버스, 전체 스키마 재설계, 모든 파일 일괄 이동.
- 보류 중인 회사 간 원가 비교·역제안·AI 영업·대량 발송 활성화.
- 사용자 승인 없는 운영 SQL·백필·결제·문자 인증 적용.
- 운영 중인 링크와 기존 데이터의 무단 삭제·재키잉.
