# WO-1 전체 매장 DB — 수집 전환 전 설계·실측 보고

## 승인 경계

- SQL 초안: `docs/sql-drafts/wo-1-shared-business-places.sql`
- 운영 적용 전 대표 승인 필요. 이 문서 작성 시점에는 운영 DB 변경과 코드 배포를 하지 않았다.
- 테이블 생성은 2026-10-26 운영 적용 완료. 수집 전환은 아직 승인 전이다.
- 적용 후 구현 순서: 전체 매장 DB upsert → 회사별 영업 지역·업종 집합 조회 → 기존 `ingestPermitLeadRows` 호출 → 기존 회사별 전국 API 반복 호출 제거.

## 수집·보존 정책(2026-10-26 확정)

- 최초 적재는 `is_active=true`인 영업 중 매장만 저장한다. 과거 폐업 이력은 넣지 않는다.
- 기존 매장의 원천 상태가 폐업으로 바뀌면 `is_active=false`, `close_date`를 기록하고 연결된 회사 리드는
  `폐업 확인 필요`로만 표시한다. 자동 제외하지 않는다.
- 비활성 매장은 회사 리드 생성·목록·지도·홈 집계의 모든 조회에서 제외한다. 폐업 전환 90일 뒤 배치 삭제한다.
- `raw_payload`는 항상 빈 객체로 두며 원문 전체를 저장하지 않는다. 감사에 꼭 필요한 값도 구조화 컬럼
  (`source_record_key`, `permit_status`, `source_modified_at`, `close_date`)으로만 저장한다.
- 매일 원천의 `source_modified_at`이 달라진 레코드만 upsert한다. 변경 없는 행의 `updated_at`도 갱신하지 않는다.
- 회사가 영업 지역을 저장하면 `(administrative_area, dataset_type, open_date)` 색인으로 활성 매장을 즉시 조회해
  회사 리드를 생성한다. 새 회사도 다음 크론을 기다리지 않고 설정 저장 직후 같은 fan-out을 실행한다.

## 예상 행 수·용량과 요금제

- 운영 프로젝트는 Supabase Free이며 현재 DB는 `104 MB`다. Free 데이터베이스 할당량 `500 MB` 대비 약 `20.8%`다.
- 현재 코드에서 실제 확인된 원본 전체 건수는 일반음식점 약 `229만`, 서울 일반음식점 `536,435`건이다.
  휴게음식점·제과점·집단급식소·위탁급식은 운영 키가 로컬에 없어 이번 보고에서 실측하지 못했다.
- 최초 적재는 영업 중만이므로 위 원본 총계가 곧 적재량은 아니다. 다만 일반음식점만 행당 약 0.7~1.0KB
  (구조화 행과 5개 인덱스, raw payload 제외)로 잡아도 100만 행당 약 0.7~1.0GB다. 전국 5종 전체 적재는
  Free 500MB를 초과할 가능성이 높다.
- 따라서 Free 유지 시 1차 범위는 고객사 영업 지역이 존재하는 시·도만 적재한다. 저장 전 API 응답을 스트리밍 필터해
  비대상 시·도와 폐업 이력을 DB에 쓰지 않는다. 데이터셋별 `totalCount / 영업 중 / 대상 시·도`를 첫 드라이런에서
  측정하고, 예상 DB가 400MB(할당량 80%)를 넘으면 적재를 중단한다.
- 현재 104MB 기준 안전 가용 예산은 약 296MB(400MB 상한까지)이며, 0.85KB/행 가정 시 약 34만 행이다.

## 호출량 변화

- 실제 운영 회사: 2개.
- 현재 일반음식점 스캔은 회사마다 최대 150페이지이므로 예정 호출량은 `2 × (최대 150 + 첫 페이지)` ≈ 최대 302회/일이다.
- 공용 원장 전환 후 5개 데이터셋을 각각 한 번 스캔하면 `5 × (최대 150 + 첫 페이지)` ≈ 최대 755회/일이며,
  회사가 늘어도 증가하지 않는다. 기존 방식으로 5개 데이터셋을 두 회사에 적용하면 최대 1,510회/일이다.
- 개발계정 공식 한도 10,000회/일 대비 공용 원장 예상 상한은 약 7.6%. 실제 호출 수는 시간 예산으로 더 낮을 수 있어
  `lead_sync_runs`에 dataset별 fetched/scannedPages/error를 남긴다.

## 안전·격리

- `shared_business_places`(화면·문서명: 전체 매장 DB)는 company_id가 없고 service_role만 접근한다. `anon/authenticated/public` 권한을 회수하고 RLS를 켠다.
- 회사별 담당자·상태·메모·`lead_actions`·직원 입력 연락처·사용자 칸은 공용 원장에 저장하지 않는다.
- 회사 리드는 `(company_id, shared_place_id)`로만 연결하고 기존 canonical/폐업/대상업종/영업지역 규칙은
  `ingestPermitLeadRows`에서 계속 적용한다.
- 동일 장소의 영업자 변경을 자동 병합하지 않도록 fingerprint는 조회용 비고유 인덱스만 둔다.
- 국세청 상태조회 확대는 기존 주 1회 흐름에 사업자번호 있는 리드를 추가하되, 폐업 결과는
  `폐업 확인 필요`만 기록하고 자동 제외하지 않는다.

## 외부 이용 조건 확인

- 공공데이터포털의 행정안전부 일반음식점 페이지는 REST/JSON+XML, 일간 갱신, 이용허락범위 제한 없음,
  개발계정 10,000회/일을 명시한다.
- 행정안전부 계열 데이터는 출처 표시를 제품·문서 하단에 유지한다.
- 카카오 로컬 결과는 공용 원장의 원천 레코드로 재배포하지 않고, 회사별 리드의 주소 정리·좌표 보강에만 사용한다.
  카카오 다수 고객 제공·장기 저장 범위는 구현 전 약관 재확인이 필요하다.
