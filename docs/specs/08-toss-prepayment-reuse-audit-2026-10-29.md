# 09 P4 매장 선결제 대비 Toss 연동 재사용 조사

- 작성일: 2026-10-29
- 기준 커밋: `f0385c3`
- 담당 범위: 08 플랫폼 관리자 조사 메모
- 상태: 설계 입력용. 결제 코드, 요금제, SQL, 운영 설정은 변경하지 않는다.

## 1. 결론

기존 구독 자동결제 연동의 공통 HTTP 래퍼와 결제 식별자 모델 일부는 재사용할 수 있다. 다만 현재 구현은 `billingKey` 기반 월 자동청구에 맞춰져 있으며, 09 P4 매장 선결제에 필요한 일반결제 상태 동기화, 웹훅 검증, 취소·환불, 테스트/라이브 키의 강제 분리는 구현되어 있지 않다.

따라서 P4에서 `lib/toss-payments.ts`를 그대로 확장하기 전에 아래 경계를 먼저 분리해야 한다.

1. 공통 전송 계층: Basic 인증, JSON 처리, 타임아웃, 오류 정규화
2. 구독 결제 어댑터: 빌링키 발급·청구·삭제
3. 선결제 어댑터: 승인 조회·취소·환불
4. 웹훅 어댑터: 원문 본문 서명 검증, 중복 방지, 결제 조회 교차 확인
5. 환경 설정: 용도별 MID/키 세트와 테스트·라이브 환경 검증

## 2. 현재 재사용 가능한 부분

| 항목 | 현재 위치 | 재사용 판단 | 주의사항 |
| --- | --- | --- | --- |

| 요청 타임아웃·오류 응답 정규화 | `tossRequest()` | 재사용 가능 | 결제 승인, 조회, 취소별 타임아웃과 재시도 정책은 분리해야 한다. |

`app/api/billing/callback/route.ts`는 카드 등록 위젯의 브라우저 리다이렉트 콜백이다. Toss 서버가 보내는 웹훅이 아니므로 웹훅 수신·서명 검증 경로로 재사용하면 안 된다.

## 3. 웹훅 서명 검증 보완점

현재 저장소에는 Toss 웹훅 엔드포인트와 `tosspayments-webhook-signature` 검증 코드가 없다. P4 구현 전 다음 요구사항을 충족해야 한다.

1. `request.json()`보다 먼저 원문 본문을 읽고 보존한다.
2. `{원문 본문}:{tosspayments-webhook-transmission-time}`를 Toss 개발자센터에서 발급한 웹훅 보안 키로 HMAC SHA-256 처리한다.
3. `tosspayments-webhook-signature`의 모든 `v1:` 값을 파싱하고 Base64 디코딩한 뒤 하나라도 일치하는지 상수 시간 비교한다. 키 교체 중 복수 서명이 올 수 있다.
4. 서명 실패 요청은 상태 변경 없이 거부한다. 본문이나 서명, 보안 키를 로그에 남기지 않는다.
5. `tosspayments-webhook-transmission-id`는 전송마다 새 값이므로 **중복 처리 키로 쓰지 않는다**. 본문에 `eventId`가 있으면 이를 사용하고, 없는 결제 상태 웹훅은 결제 조회 결과와 내부 상태 전이의 멱등성으로 중복을 막는다. 전송 ID는 전달 진단용으로만 제한해 보관한다. [Toss 웹훅 이벤트](https://docs.tosspayments.com/reference/using-api/webhook-events)
6. 원문, 서명 검증 결과, 업무 중복 판정에 필요한 식별자와 후속 처리 작업을 **내구성 있게 기록한 뒤에만** 10초 안에 `200`을 반환한다. 메모리 큐에만 넣고 먼저 `200`을 보내면 프로세스 종료 시 이벤트가 유실된다. 내구성 있는 수신에 실패하면 성공 응답을 보내지 않아 Toss의 최대 7회 재전송을 이용한다.
7. 서명 성공만으로 결제를 확정하지 않는다. 결제 조회 API로 `paymentKey`, `orderId`, `totalAmount`, `mId`, `status`를 내부 주문과 교차 확인한 뒤 상태를 전이한다.
8. 수신 시간 허용 범위와 오래된 요청 거부 기준은 구현 명세에서 확정한다. 전송 ID는 재전송 멱등키가 아니라 전달 추적용이라는 경계를 유지한다.

`PAYMENT_STATUS_CHANGED`에는 재시도 간 유지되는 `eventId`가 없다. 업무 중복 판정은 `paymentKey`와 조회된 `status`, 취소 건의 `transactionKey`, 내부에서 허용한 단방향 상태 전이를 기준으로 한다. 전송 ID별 수신 로그는 운영 진단용으로 남길 수 있지만 결제·배송을 다시 확정하는 근거로 사용하지 않는다.

권장 이벤트 후보는 `PAYMENT_STATUS_CHANGED`다. `CANCEL_STATUS_CHANGED`는 비동기 해외 간편결제 취소 전용이며 국내 결제 취소에는 오지 않는다. 국내 취소는 취소 API 응답과 결제 조회로 반영한다. 실제 등록 이벤트는 P4 결제수단과 상태 머신 확정 후 최소 범위로 선택한다. [Toss 웹훅 이벤트](https://docs.tosspayments.com/reference/using-api/webhook-events)

## 4. 취소·환불 보완점

현재 `updateSubscriptionStatus(..., "canceled")`는 다음 자동청구를 중단할 뿐 이미 승인된 결제를 환불하지 않는다. `deleteBillingKey()`도 결제 취소 API가 아니다. P4 환불에 이 둘을 사용하면 안 된다.

선결제 환불은 서버에서 `POST /v1/payments/{paymentKey}/cancel`을 호출하는 별도 유스케이스가 필요하다.

- 필수: `cancelReason`
- 부분 취소: `cancelAmount`
- 중복 방지: 충분히 무작위한 `Idempotency-Key`
- 사전 검증: 회사 범위, 주문 소유권, 환불 권한, 현재 승인액, 기존 취소 합계, `isPartialCancelable`
- 성공 기록: `transactionKey`, `cancelAmount`, `cancelReason`, `cancelStatus`, `canceledAt`, 남은 환불 가능액
- 사후 동기화: API 응답과 결제 조회를 동일 상태 머신으로 수렴. 비동기 해외 간편결제를 지원할 때만 `CANCEL_STATUS_CHANGED`를 추가

환불 명령을 만들 때 멱등키를 먼저 영속화하고 같은 명령의 모든 네트워크 재시도에 동일한 값을 사용한다. Toss 멱등키의 유효기간은 최초 요청일로부터 15일이므로 최소 그 기간 동안 키와 결과를 재사용하고, 내부 감사 기록은 별도 보존 정책을 따른다. 시간초과되더라도 새 멱등키로 즉시 재요청하지 않고 같은 키로 결과를 재확인하며, 필요하면 결제 조회로 실제 취소 상태를 확인한다.

국내 결제에서 취소 API의 `cancelStatus=DONE`은 Toss의 취소 거래가 성공했다는 뜻이지 구매자 계좌·카드에 환급 표시까지 끝났다는 뜻은 아니다. 카드 매입 후 또는 부분 취소는 영업일 기준 3~4일, 가상계좌는 통상 영업일 기준 2일이 걸릴 수 있다. 따라서 내부 상태와 고객 문구를 `취소 처리 완료`와 `환급 반영 예상`으로 구분하고, 즉시 입금 완료로 표시하지 않는다. 부분 취소·면세·가상계좌 환불계좌는 P4 결제수단 범위가 확정된 뒤 별도 정책으로 제한한다. [Toss 결제 취소 가이드](https://docs.tosspayments.com/guides/v2/cancel-payment)

승인·취소의 `paymentKey`와 각 취소의 `transactionKey`는 대소문자를 구분해 원문 그대로 저장한다. 부분 취소는 한 결제에 여러 `transactionKey`가 생길 수 있으므로 `paymentKey`만으로 취소 원장을 덮어쓰지 않는다.

## 5. 테스트 키와 라이브 키 분리

현재 설정은 `NEXT_PUBLIC_TOSS_CLIENT_KEY`와 `TOSS_SECRET_KEY` 한 쌍이며, 값이 존재하는지만 확인한다. 다음 위험이 남아 있다.

- 테스트 클라이언트 키와 라이브 시크릿 키를 섞어도 애플리케이션이 시작 단계에서 감지하지 못한다.
- 구독 자동결제 MID와 선결제 MID가 다를 경우 한 쌍의 환경변수로 용도를 구분할 수 없다.
- 서버 전용 조회·환불도 현재 `isTossPaymentsConfigured()` 때문에 클라이언트 키 존재 여부에 종속된다.

P4 구현 시 권장 원칙:

1. 개발·미리보기 환경에는 테스트 키만, 운영 환경에는 라이브 키만 주입한다.
2. 클라이언트 키와 시크릿 키가 같은 환경·같은 MID 세트인지 배포 전 검증한다.
3. 구독과 선결제가 다른 MID라면 환경변수 이름과 설정 객체도 용도별로 분리한다.
4. 서버 준비 상태와 브라우저 SDK 준비 상태를 별도로 판단한다. 조회·환불·웹훅 검증은 공개 클라이언트 키에 의존하지 않는다.
5. 시크릿 키와 웹훅 보안 키는 서버 전용 시크릿 저장소에 두고 `NEXT_PUBLIC_` 변수, 응답 본문, 로그, PR, 문서에 넣지 않는다.
6. 키 접두사와 배포 환경이 맞지 않으면 결제를 비활성화하고 배포 검증을 실패시킨다. 실제 키 문자열은 오류 메시지에 포함하지 않는다.
7. 키 회전 시 결제 승인·조회·취소·웹훅을 모두 점검한 뒤 기존 키를 폐기한다.

키 검증은 `test`/`live` 환경 등급과 설정한 MID·용도를 확인하되, 알려진 접두사 목록에 없다는 이유만으로 신규 키 종류를 거부하지 않는다. Toss는 새 키 종류에 새 접두사를 추가할 수 있다고 명시한다. Preview 배포에는 라이브 시크릿과 라이브 웹훅 보안 키를 주입하지 않고, 테스트와 라이브 웹훅 URL·MID·수신 원장을 분리한다. [Toss 요청·응답 식별자 원칙](https://docs.tosspayments.com/reference/using-api/req-res)

환경변수의 구체적인 이름과 MID 구성은 Toss 계약 범위가 확정된 뒤 결정한다. 이 메모에서는 운영 설정을 추가하거나 변경하지 않는다.

## 6-1. 주문 링크와 선결제의 추가 경계 (2026-10-30 검토)

09번 주문 기능은 매장별 링크로 접근한다. 첫 주문의 휴대폰 인증 제공사가 아직 정해지지 않았으므로, 주문 링크가 유효하다는 사실만으로 선결제를 열거나 환불 권한을 부여하지 않는다. `STORE_ORDERING_ENABLED`와 선결제 기능은 인증·SQL·운영 검증 전까지 OFF다.

- 결제 요청 전에 **서버가 계산한** 주문번호, 회사·매장 ID, 확정 품목·수량·세금·총액을 저장한다. 성공 리다이렉트의 `orderId`와 `amount`는 이 저장값과 비교한 뒤에만 승인 API로 보낸다. URL의 금액을 주문 원장에 그대로 반영하지 않는다. [Toss 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)
- 결제 승인·웹훅·취소는 같은 회사의 주문과 결제 시도를 식별해야 한다. 링크 재발급·만료 후에도 이미 시작된 결제의 조회·환불 기록은 보존하되, 만료 링크로 새 결제 시도를 만들지 않는다.
- 성공 리다이렉트는 결제 완료의 단일 근거가 아니다. 승인 응답 또는 검증된 웹훅 뒤의 결제 조회로 최종 상태를 확인한다. 브라우저가 닫혀도 미확정 결제 시도가 남도록 하고, 지연·순서 역전 웹훅은 현재 상태보다 과거 상태로 주문을 되돌리지 않는다.
- 웹훅 수신 성공과 내부 주문 반영 성공을 구분한다. 후속 처리 실패 건을 재처리 대기열에 남기고, `eventId`가 있으면 그 값으로, 없으면 `orderId`·`paymentKey`와 조회된 결제 상태의 전이로 중복 없이 재시도한다. 전송 ID는 멱등키가 아니다. 관리자에게 대기·불일치 건수만 보여 주며 키·카드 정보·웹훅 원문은 노출하지 않는다.
- 주문 금액과 승인·취소 누적액을 일 단위로 대조하는 운영 절차를 정의한다. 결제 API 호출이 시간초과되면 새 주문·새 멱등키를 만들기 전에 기존 주문번호로 조회한다. 환불 중 또는 결과 미확정 상태에서 중복 배송 확정도 막아야 한다.
- P4 결제수단이 확정되면 카드/계좌 등 수단별 승인·취소 가능 시점, 부분 취소, 세금/면세 금액, 환불 계좌 필요 여부를 별도 상태표로 검증한다. 결제수단 정보는 PG 응답의 업무에 필요한 최소값만 보관하고 카드 원문·인증값을 저장하지 않는다.

이 항목은 구현·운영 적용 승인이 아니다. 첫 주문 본인 확인 수단과 결제수단 정책이 결정된 뒤 09번 주문 상태 머신과 함께 다시 검토한다.

## 6-2. 대사와 재처리 운영 경계 (2026-10-30 추가 검토)

웹훅은 실시간 상태 반영 수단이지 최종 대사 원장이 아니다. 일 단위 거래 대사에서 Toss 거래 조회 결과의 승인·취소 거래와 내부 주문·결제·환불 원장을 비교한다.

- 승인·취소 각각의 `transactionKey`, `paymentKey`, `orderId`, MID, 통화, 금액, 상태, 발생 시각을 비교한다. 결제 조회의 현재 상태만 비교하면 여러 차례의 부분 취소 중 한 건을 놓칠 수 있다.
- 대사 구간은 KST 영업일과 PG 조회 기준 시간을 명시하고, 경계 시각의 지연 거래를 다음 실행에서 다시 포함하는 겹침 구간을 둔다.
- 불일치는 `PG에만 존재`, `내부에만 존재`, `금액 불일치`, `상태 불일치`, `처리 대기`로 분류한다. 자동으로 재승인·재취소하지 않고 조회·검증 후 권한 있는 운영자가 조치한다.
- 승인·취소 API 시간초과 건과 웹훅 후속 처리 실패 건은 별도 재처리 대기열에서 같은 주문·명령·멱등키로 복구한다. 재처리 횟수, 마지막 오류, 다음 시도 시각을 남기고 무한 재시도를 막는다.
- 대사 결과에는 키, 인증 헤더, 카드번호 원문, 웹훅 원문을 노출하지 않는다. 운영 화면에는 건수, 내부 주문번호, 마스킹된 결제 식별자, 금액, 상태, 마지막 확인 시각만 제공한다.
- 환급 소요 기간이 지난 미해결 취소는 자동 성공 처리하지 않고 PG 조회·관리자 확인 대상으로 올린다.
