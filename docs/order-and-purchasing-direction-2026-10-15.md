# 주문·매입·정산 확장 방향 (2026-10-15)

> 설계 전용 문서입니다. 아래 SQL은 승인 전 실행하지 않습니다.

## 1. 도메인 경계

- **partner**: 매입처는 `product_suppliers`, 매출처는 `normalized_customers`가 원장이다. 같은 사업자번호를 가진 두 원장은 `business_partner_links`로 선택 연결할 수 있으나 자동 병합하지 않는다.
- **product**: `product_catalog`는 고객에게 판매하는 표준 품목·판매 단위, `supplier_products`는 매입처의 원본 품목·매입 단위다. 두 단위 사이에는 확정 환산비율이 필요하다.
- **pricing**: 확정 공급 원가 → 판매 기준가 → 거래처별 계약 단가 → 브랜드 우대가 순서다. 매장이 보는 가격의 단일 출처는 유효한 `customer_price_agreements`다.
- **quote**: 견적 품목은 이름·단위·가격·과세구분을 스냅샷으로 보관한다. 견적 수락 시 계약 단가 후보를 생성하고 운영자가 적용일을 확인한다.
- **order**: 매장 주문은 계약 단가와 품목명 스냅샷, 희망 납품일을 보존한다.
- **purchasing**: 주문 수요를 기본 공급처별로 집계해 발주하고 입고를 기록한다.
- **delivery**: 확정 납품일을 향후 배송 일정 규칙·호차 결정 결과에 연결한다. 차량은 거래처 권한 기준으로 사용하지 않는다.

## 2. 다음 구현 묶음: 표준 품목 수동 관리

`/revenue/products`의 **표준 품목** 탭에서 생성·수정·판매중지를 제공한다.

- 변경 불가 회사별 품목코드: `P-000001` 형식, DB 함수/RPC에서 원자적으로 채번
- 필드: 이름, 브랜드, 원산지, 규격 값·단위, 판매 단위, 대표 매입 단위, 환산비율, 과세/면세, 분류, 사진, 활성 상태
- 판매가 변경은 현재값 수정과 동시에 `product_sales_price_history`에 이전값·새값·변경자를 append-only로 기록
- 삭제 대신 `is_active=false`; 이미 견적·주문에 사용된 품목 ID는 유지
- 유통사 상품을 표준 품목으로 승격할 때도 동일 채번 RPC를 사용

## 3. 단위 환산

- 표준 품목의 `sales_unit`은 매장 주문 단위, 유통사 상품의 `purchase_unit`은 매입 단위다.
- `supplier_product_matches.purchase_to_sales_ratio`는 매입 단위 1개가 판매 단위 몇 개인지를 뜻한다. 예: 1박스=10봉이면 `10`.
- `b/10`, `*10개` 등 파서 결과는 **추천값**일 뿐, 사람이 확인하기 전 `conversion_confirmed=false`이며 자동 견적 원가에서 제외한다.
- 판매단위 원가 = 매입단위 원가 ÷ 환산비율. 환산비율은 0보다 커야 한다.
- 발행된 견적·주문에는 계산 당시 매입단위, 판매단위, 환산비율, 원가를 스냅샷으로 남겨 이후 환산 변경의 영향을 받지 않게 한다.

## 4. 거래처 계약 단가

`customer_price_agreements`는 거래처·표준 품목·적용기간별 판매 단가를 보관한다. 동일 날짜에 유효한 계약은 하나만 허용한다. 견적 `accepted` 전환은 계약 단가 초안을 만들되 기존 계약을 자동 종료하지 않고 충돌을 운영자에게 보여준다.

가격 우선순위는 `거래처 계약 단가 > 브랜드 우대가 > 업종 템플릿 > 표준 기준가`다. 매장 주문 API는 계약 단가만 반환하고 원가·마진·공급처 필드는 select 단계부터 제외한다.

## 5. 과세·면세와 반올림

- `product_catalog.tax_type`: `taxable | exempt`; `supplier_products.parsed_tax_type`은 업로드 추정값이다.
- 부가세 열이 0이면 면세, 공급가액의 약 10%면 과세 후보로 제시한다. 사람이 표준 품목에서 수정할 수 있다.
- 금액은 원 단위 정수로 저장한다.
- **권장 반올림 규칙**: 라인별 공급가액을 먼저 원 단위 반올림하고, 과세 라인의 부가세를 `round(공급가액 × 10%)`로 계산한다. 문서 합계는 라인 스냅샷 합계다. 견적·주문·원장·세금계산서가 같은 결과를 재현하기 쉽기 때문이다.
- 견적·주문 라인은 `tax_type_snapshot`, `supply_amount`, `tax_amount`, `total_amount`를 저장하며 과세/면세 합계를 분리 표시한다.

## 6. 거래처 원장과 결제

`partner_ledger_entries`는 append-only다. 수정·삭제하지 않고 취소/조정 전표로 정정한다. 매출처 미수금과 매입처 미지급금을 같은 구조에서 partner type으로 구분한다. 수동 입금부터 시작하고, 향후 PG 웹훅은 고유 `idempotency_key`로 중복 입금을 막는다. 잔액은 합계 뷰로 계산한다.

## 7. 세금계산서

- 거래처 세금 정보: 사업자번호, 상호, 대표자, 업태, 종목, 수신 이메일
- 과세분은 세금계산서, 면세분은 계산서로 문서를 분리한다.
- 발행 상태: `pending | issued | sent | failed | cancelled`; 국세청 승인번호는 발행 성공 후 기록한다.
- 홈택스 직접 결합 대신 `TaxInvoiceProvider` 어댑터(`issue`, `cancel`, `getStatus`)를 두고 대행사 선정 후 구현한다.

## 8. 매장 주문 웹 인증·보안

- 직원 로그인과 분리된 `customer_portal_users` 인증을 사용한다.
- 모든 조회는 `company_id + customer_id`로 제한하고, 사용자가 속하지 않은 거래처 ID는 404로 처리한다.
- 매장 응답 DTO에는 원가, 마진율, 공급처, 매입 단위가 존재하지 않아야 한다.
- 주문 품목은 계약 단가·품목명·규격·단위·과세를 스냅샷으로 저장한다.

## 9. 현재 구조에서 주문 웹을 막는 요소

1. 사람 식별용 불변 품목코드와 원자적 채번이 없다.
2. 매입 단위와 판매 단위의 확정 환산비율이 없다.
3. 거래처별 유효 계약 단가 원장이 없다.
4. 견적 수락이 계약 단가로 이어지지 않는다.
5. 견적 라인에 과세/면세·공급가액·부가세 스냅샷이 없다.
6. 매장 전용 인증과 `customer_id` 범위 모델이 없다.
7. 주문·발주·입고·원장·세금계산서 문서가 없다.
8. 견적 품목 교체가 아직 RPC 트랜잭션이 아니어서 공개 링크가 순간적으로 빈 품목을 볼 수 있다.

## 10. 권장 구현 순서

1. 표준 품목 수동 관리: 품목코드·과세구분·단위 환산·판매가 이력
2. 거래처 계약 단가 + 견적 수락 전환
3. 업종 단가표 → 자동 견적 → 브랜드 우대가
4. 매장 인증·상품조회·주문
5. 주문 집계·발주·입고
6. 매출처 미수/매입처 미지급 원장과 입금·지급
7. 세금계산서 어댑터 및 발행 대행 연동
