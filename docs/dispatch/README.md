# MAJU 개발 분배 운영 방식 (2026-11-10 대표 결정)

**설계·분배·문서는 Claude(컨트롤타워), 개발은 Codex와 Claude Code가 나눠서 병렬로, 모든 코드는 Ponytail 점검을 거쳐 병합한다.**

## 역할

| 누구 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| **Claude 컨트롤타워** (claude.ai 프로젝트 세션) | 설계·우선순위·작업 분배 md 작성, 차수별 현황판 갱신, 중앙 체크리스트·블루프린트·승인표 정리, 완료 판정 검토 | 기능 코드 작성(긴급 핫픽스 제외) |
| **Claude Code** (대표 PC) | 분배된 `CC-*` 작업 구현·테스트·PR | 남의 작업 파일 수정, 대표 승인 없는 운영 DB 쓰기·배포·플래그 변경 (승인 있으면 아래 "배포 담당"·승인 경계 절차로 직접 함 — 11/11 대표 결정) |
| **Codex 총괄방** | 이 폴더의 Codex 지시서(`*-codex.md`)를 받아 CX 작업을 작업방에 배분하고 현황판을 갱신 | 지시서에 없는 작업 생성(필요하면 현황판 "후속"에 적고 컨트롤타워가 다음 차수에 반영) |
| **Codex 작업방 01~09** | 분배된 `CX-*` 작업 구현·테스트·PR (Ponytail 사용) | 위와 같음 |
| **Codex Ponytail 검토방** | Claude Code PR을 Ponytail로 점검·보완 커밋 | 기능 범위 변경·재기획 |
| **대표** | 우선순위 결정, 운영 DB·플래그·배포 승인, 실사용 검증 | — |

## 한 작업의 흐름

```
컨트롤타워: docs/dispatch/<차수>-claude-code.md / -codex.md 에 작업지시(WO) 작성
   ↓
개발자: 지시서의 작업 ID로 브랜치 생성 (Claude Code: claude/<id>-<요약>, Codex: codex/<id>-<요약>)
   ↓ 구현 + 로컬 검증 (tsc · lint · test · build · auth-boundaries, 화면이면 PC/390 e2e)
PR 생성 — 제목 앞에 [CC-01] / [CX-01], 본문에 지시서 링크
   ↓
Ponytail 점검 (필수)
   · Codex 작업: 작성한 Codex가 Ponytail 사용 → 본문 `Ponytail: 사용함`
   · Claude Code 작업: Claude Code가 설치된 Ponytail(ponytail-review)로 직접 점검·보완 → 본문 `Ponytail: 사용함 (Claude Code ponytail-review)`
     (2026-11-11부터. Codex Ponytail 검토방 CX-00은 추가 검토가 필요할 때만)
   ↓
CI 전체 초록 → Ready for review → 병합 (병합은 작성자가 함)
   ↓
현황판(<차수>-board.md)에 PR 번호·상태 기록 → 컨트롤타워가 완료 판정
   ↓
운영 배포: 대표 지시 때만, 하루 1회 묶음. 운영 DB·플래그는 각각 별도 승인.
```

`Ponytail:` 줄이 `사용함`이 아닌 PR은 병합하지 않는다(문서만 바꾼 PR은 `해당 없음(문서)`).

## 충돌 방지

1. **작업마다 파일 소유가 지시서에 적혀 있다.** 지시서의 `Files` 밖을 고쳐야 하면 고치지 말고 현황판 "막힘"에 적는다.
2. 공유 파일(`lib/store.ts`, `lib/customer-navigation.ts` 메뉴, `docs/backend/*`, 중앙 체크리스트, 승인표)은 지시서에 **명시된 한 작업만** 고친다.
3. 작업 시작 전·PR 전 `git fetch && git rebase origin/main`. 충돌이 나면 먼저 병합된 쪽을 기준으로 맞춘다.
4. 같은 화면을 두 작업이 동시에 맡지 않는다. 한 작업이 끝나기 전 같은 화면 후속 작업은 다음 차수로 넘긴다.

## "다음 진행해"를 받았을 때 (Claude Code · Codex 총괄방 공통)

1. 최신 차수 현황판에서 **내 담당 줄**을 본다.
2. 손볼 것부터: CI 실패 PR → Ponytail 검토에서 돌아온 지적 → 대표가 허락한 보완.
3. 그다음 지시서 순서대로 `대기` 작업 하나를 시작한다.
4. 내 담당이 모두 `병합` 이상이거나 막혀 있으면 **새 작업을 만들지 말고** "R? 내 작업 완료(또는 막힘: 이유) — 컨트롤타워 다음 차수 대기"라고 보고하고 멈춘다.

**Codex 총괄방은 직접 구현하지 않고 작업방에 나눠 준다.** "다음 진행해"를 받으면:
1. 현황판의 모든 `CX-*` 줄을 작업방별(00 검토방 · 01 · 03 · 04 · 06 · 07 · 09)로 본다.
2. 각 작업방마다 위 1~3번 기준으로 **다음 할 일 1개**를 골라 그 작업방 채팅에 지시서 ID와 함께 보낸다(예: "09방: CX-08 진행. 지시서 docs/dispatch/2026-11-10-R1-codex.md"). 한 작업방에 동시에 2개를 주지 않는다.
3. 할 일이 없는 작업방은 쉬게 둔다. 지시서에 없는 일을 새로 만들지 않는다.
4. 현황판 `CX-*` 줄의 담당 작업방·상태를 갱신하고, 대표에게 "작업방별 배정 표 + 전부 끝났으면 다음 차수 대기"를 보고한다.
작업방은 대표가 아닌 총괄방에서만 지시를 받는다(대표가 직접 작업방에 보낼 때는 같은 지시서 ID를 쓴다).

## 배포 담당 (2026-11-10 대표 결정)

Claude와 Codex는 사용량 한도가 달라서 **둘 중 남아 있는 쪽이 배포한다.** 대신 동시에 두 번 배포하지 않도록 현황판으로 잠근다.

| 순서 | 담당 | 할 일 |
| --- | --- | --- |
| 기본 | **Claude 컨트롤타워** | 대표 "배포해" → 확인 → 배포 → 스모크 → 기록 |
| 대신 | **Claude Code** | 대표가 Claude Code에 "배포해"를 직접 지시했을 때 같은 순서로(11/11 대표 결정) |
| 대신 | **Codex 총괄방** | 컨트롤타워가 한도로 멈췄거나 대표가 Codex에 지시했을 때만 같은 순서로 |
| 안 함 | Codex 작업방 | 배포·롤백 하지 않음. 필요하면 현황판 "배포 요청" |

**배포 순서(누가 하든 같음)**
1. 현황판 "배포 기록"에 `진행 중 — 담당 · 시각 · main SHA` 한 줄을 먼저 적고 main에 반영(잠금). 이미 `진행 중` 줄이 있으면 배포하지 않는다.
2. main 최신 SHA의 CI 전체 초록, 병합 금지 PR(현황판 "병합 금지") 미포함, 이번 배포로 켜지는 기능 스위치 없음 확인.
3. Vercel Production 배포 → READY → 스모크(`/login` `/dashboard` `/leads` `/revenue/pricing/*` `/revenue/products` `/store` `/orders`) → 30분 런타임 오류 확인. 문제면 직전 READY로 롤백.
4. "배포 기록" 줄을 `완료 — 배포 ID · 포함 PR · 스모크 결과`로 바꾼다.

하루 1회 원칙. 운영 DB·기능 스위치는 배포와 별개로 대표 승인 문구가 필요하다.

## 중간 점검 (진행 확인)

- **정기 점검**: 컨트롤타워가 하루 여러 번(예약 작업) 현황판·열린 PR·CI·막힘을 읽고 짧게 보고한다. 확인 항목: ① 상태가 오래 안 바뀐 작업 ② CI 실패 PR ③ Ponytail 대기 쌓임 ④ 지시서와 다른 구현(Files 밖 수정, 지시서 범위 누락) ⑤ 대표 결정 대기 ⑥ 운영 READY와 main 차이.
- 컨트롤타워가 한도로 멈추면 Codex 총괄방이 같은 항목을 점검하고 현황판 "점검 기록"에 남긴다.
- 점검은 읽기만 한다. 고칠 것은 다음 차수 지시서나 현황판 "후속"으로 넘긴다.

## 승인 경계 (모두 공통 · 변경 없음)

- 운영 DB(`fcmdvveqmcgtioelzqun`) 스키마·데이터 변경: SQL 초안 + down + PG17 → 대표 명시 승인 문구 → 적용 → 읽기 검증 → `docs/work-orders/db-approval/` 기록. 적용은 승인 문구를 받은 쪽(컨트롤타워 또는 Claude Code)이 한다(11/11 대표 결정). 같은 함수·테이블을 두 쪽이 동시에 적용하지 않도록 현황판 해당 줄에 `적용 중`을 먼저 적는다.
- 새 기능은 기본 OFF + 회사 allowlist. 대표 회사 외 활성화·돈 관련 활성화는 대표 승인.
- 비밀값은 출력 금지, 이름만 `docs/work-orders/owner-change-later.md`.
- 금지: 단체 문자·카톡 매크로, 스크래핑, 비밀번호 대리 입력, 개인정보 파일 커밋, hold 모듈 노출.

## 완료 보고 (PR 본문 + 현황판 한 줄)
