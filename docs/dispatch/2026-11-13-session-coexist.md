## 고칠 것

1. 로그인·가입: **자기 쿠키만 설정**, 다른 사이트 쿠키 삭제 제거(위 3곳).
2. 로그아웃: **자기 쿠키만 삭제**(운영 → 운영만, 관리자 → 관리자만). 매장은 지금처럼 매장만.
3. 공용 PC 대비: 각 로그아웃 메뉴 아래 작은 링크 **"이 브라우저의 모든 MAJU 로그인 해제"** → 새 `POST /api/auth/logout-all`(셋 다 삭제).
4. 그대로 둘 것: 비밀번호 변경 시 관리자·운영 세션 삭제(`change-password`, 보안상 유지) · 세션 버전 검사.
5. 같은 사람이 관리자·운영 둘 다일 때 화면 위에 지금 어느 사이트인지 이미 표시되는지 확인(없으면 머리 줄에 `관리자`/`운영`/`매장` 작은 배지).

## ⚠️ 선결 조건 (18:10 컨트롤타워 코드 검사에서 발견 — 이것 없이 쿠키 삭제만 빼면 안 됨)

`lib/auth.ts` `getRequestAuthScope`(API 287곳이 사용)는 **운영 세션이 있으면 관리자 세션보다 먼저 씀**(321~330줄). 지금은 로그인할 때 서로 지워서 둘이 함께 있을 일이 없었는데, 이번 수정으로 둘이 함께 있으면:

- 관리자 화면에서 `?companyId=고객사X`로 부른 API가 **대표 회사(운영 세션의 회사)** 데이터로 처리됨 → 관리자가 고객사 X를 고친다고 생각하고 대표 회사 데이터를 바꾸는 **P1 데이터 오류**.

그래서 같은 PR에서:

1. **요청이 어느 사이트에서 왔는지 명시**: 관리자 화면(`/admin/**`)의 브라우저 요청은 헤더 `x-maju-site: admin`, 운영 화면은 `company`, 매장은 `store`. 공용 fetch 도우미(또는 각 셸의 fetch 래퍼) 한 곳에서 붙임.
2. `getRequestAuthScope`: `x-maju-site: admin`이고 관리자 세션이 있으면 **관리자 범위**, `company`면 운영 범위. 헤더가 없을 때만 지금 규칙(운영 우선).
3. **안전장치**: 두 세션이 다 있고 헤더가 없는데 요청 `companyId`가 운영 세션 회사와 다르면 **409 "어느 화면에서 요청했는지 확인할 수 없습니다. 새로고침해 주세요."** — 조용히 다른 회사로 처리하지 않음.
4. 단위 테스트: (관리자+운영 세션, admin 헤더, companyId=X) → X · (같은 세션, company 헤더) → 운영 회사 · (헤더 없음, companyId≠운영 회사) → 409 · 세션 하나일 때 동작 변화 없음.
5. e2e Done에 추가: 두 사이트 동시 로그인 상태에서 관리자 화면의 고객사 X 설정 저장 → X에만 저장되고 대표 회사는 그대로.

순서: **이 선결 조건 → 쿠키 삭제 제거**(같은 PR이어도 됨). 선결 조건 없이 병합 금지.
