# ARC-10 통계 읽기 모델 감사

- 감사일: 2026-11-01
- 기준: GitHub `main` `41bcc7b` (로컬 fetch 장애로 GitHub 비교 API에서 최신 상태 확인)
- 작업지시서: PR #106 `docs/specs/modular-monolith-reorganization-work-orders-2026-11-01.md` (미병합)
- 범위: 영업 활동, 확정 전표/원장, 배송 완료, 레거시 `sales_transactions`, 회사 격리
- 변경 성격: 문서 감사만 수행. 운영 DB, 기능 플래그, AI 영업, 회사 간 원가 비교 화면은 변경하지 않음.

## 결론

현재 `/insights`는 영업 활동과 배송 활동을 보여 주는 운영 대시보드다. 확정 전표와 거래처 원장을 기준으로 한 재무 통계 읽기 모델은 아직 없다. 특히 화면의 `계약`은 확정 매출 전표가 아니라 `sales_quotes.status = accepted`를 세며, 따라서 확정 매출이나 원장 금액으로 해석하면 안 된다.

`sales_transactions`는 확정 전표·원장과 다른 레거시 업로드 자료다. 자동 합산하거나 정합성의 기준 원장으로 사용하지 않고, 화면과 문서에서 항상 **레거시 매출 자료**로 별도 표시해야 한다.

검토한 조회 경로에는 모두 `company_id` 제한이 있다. 다만 운영사의 실제 금액을 회사별로 집계하는 검증은 민감한 영업·원장 데이터 접근 승인이 없어 수행하지 않았다. 따라서 회사별 숫자 일치 여부는 **코드상 격리 확인**, **실데이터 숫자 일치 미확인**으로 구분한다.

## 지표 원천 계약

| 지표 | 기준 원천 | 식별자·기준일 | 현재 구현 | 판정 |
| --- | --- | --- | --- | --- |
| 신규 리드 | `business_permit_leads` | `id`, `created_at`(KST) | `/insights`가 기간 내 생성 건수를 계산 | 확인 |
| 접촉 리드 | `lead_actions` | 고유 `lead_id`, 활동 시각 | 보류·외부 정보 보강·인스타 정보 수정 등을 제외한 뒤 고유 리드를 계산 | 조건 정의를 공통 계약으로 고정 필요 |
| 견적 | `sales_quotes` | `id`, 견적의 업무 기준일 | 초안·취소를 제외하지만 `created_at`을 사용 | 발송일 기준 여부 결정 필요 |
| 계약 | 확정된 영업 문서 또는 명시적 계약 원천 | 원천 문서 ID, 확정일 | 현재는 `sales_quotes.status = accepted` | 충돌: 확정 전표와 동일하지 않음 |
| 확정 순매출 | `business_documents` | `id`, `document_date`, `status = confirmed` | `/insights`에 없음 | 읽기 모델 필요. 매출은 양수, 매출반품은 음수로 재계산 가능해야 함 |
| 거래처 원장 증감·잔액 | `partner_ledger_entries` | `id`, `entry_date`, `source_document_id`, `source_type` | `/insights`에 없음 | 읽기 모델 필요. 매출액과 원장 잔액은 서로 다른 지표로 표시 |
| 배송 완료 | `customer_notes`의 `note_type = delivery` | 노트 `id`, `created_at`(KST) | `/insights`와 배송 이력이 같은 계열의 원천을 사용 | 확인. 조회 상한 차이 해소 필요 |
| 배송 알림 공유 | `customer_message_logs`와 배송 노트 메모 | 배송 노트 ID, 발송 결과 | 성공 로그 또는 카카오 공유 메모를 계산 | 확인. 실패 시 0으로 숨기는 동작 개선 필요 |
| 레거시 매출 | `sales_transactions` | 레거시 행 ID, `sales_date` | `/revenue/transactions`가 현재 “매출 원장”으로 표현 | 충돌: “레거시 매출 자료”로 분리 표기 필요 |

확정 전표 통계는 `business_documents`와 `business_document_lines`에서 다시 계산할 수 있어야 하고, 원장 통계는 `partner_ledger_entries`의 원천 문서와 취소·역분개 연결을 추적할 수 있어야 한다. 읽기 결과에는 최소한 `company_id`, 원천 종류, 원천 ID, 업무 기준일을 보존해야 한다.

## 현재 화면 간 숫자 일치 감사

| 비교 | 결과 | 이유 |
| --- | --- | --- |
| `/insights` 계약 ↔ 확정 매출 전표 | 불일치 가능 | 전자는 수락 견적, 후자는 확정 업무 문서이며 원천과 상태 전이가 다름 |
| `/insights` 배송 ↔ 배송 이력 | 제한적으로 일치 | 모두 배송 노트를 사용하지만 조회 기간·상한이 다름 |
| `/insights` 매출 ↔ 거래처 원장 | 비교 불가 | 현재 `/insights`는 확정 전표와 원장을 조회하지 않음 |
| `/revenue/transactions` ↔ 확정 매출 전표 | 합산 금지 | `sales_transactions`는 레거시 업로드 자료이며 확정 전표와 별도 데이터셋 |
| 데이터 정합성 API ↔ 신규 문서/원장 | 미지원 | 현재 검사는 주로 레거시 `sales_transactions`를 대상으로 함 |

숫자 차이를 오류로 판단하기 전에 원천, 상태, 업무 기준일, 시간대, 페이지 상한을 먼저 맞춰야 한다. 서로 다른 원천의 숫자를 맞추기 위해 보정값을 넣거나 자동 병합하면 안 된다.

## 회사 격리 감사

정적 코드와 스키마 메타데이터에서 다음을 확인했다.

- 리드, 영업 활동, 견적, 배송 노트, 메시지 로그, 확정 문서, 문서 라인, 거래처 원장, 레거시 매출 조회는 회사 범위를 전달하거나 `company_id` 조건을 사용한다.
- 업무 문서 API는 서버 인증 범위에서 회사를 결정하고 저장소 함수에 `companyId`를 전달한다.
- 업무 문서와 원장 테이블에는 회사 식별 컬럼과 회사 단위 제약·인덱스가 있다.
- 운영 스키마에 감사 대상 테이블과 `company_id` 컬럼이 존재함을 메타데이터 수준에서 확인했다.

실제 회사별 합계의 동일성 검증은 미수행이다. 승인된 운영 절차에서 다음 순서로 재검증해야 한다.

1. 한 회사씩 `company_id`를 고정한다.
2. 동일한 KST 업무 기간과 확정 상태를 적용한다.
3. 확정 매출·반품 문서 ID 목록과 문서 합계를 산출한다.
4. 같은 원천 문서 ID를 가진 원장 항목과 취소·역분개를 대조한다.
5. 배송 완료는 배송 노트 ID 목록으로 화면별 집합을 비교한다.
6. `sales_transactions`는 별도 결과 집합으로만 출력하고 차이를 자동 조정하지 않는다.
7. 원천 ID 누락, 중복, 다른 회사 참조, 조회 상한 도달을 각각 실패로 기록한다.

## 정확도를 해치는 현재 제약

- 영업 활동은 최대 5,000건을 읽어 고유 리드를 계산하므로 활동이 많은 기간에는 과소 집계될 수 있다.
- 견적 조회는 화면 호출에서 최대 500건이며 기간 집계 전에 잘릴 수 있다.
- 배송 노트와 메시지 로그는 최대 5,000건이고, 다른 배송 조회는 1,000건 또는 5,000건으로 상한이 서로 다르다.
- 배송 조회 오류를 빈 배열로 바꾸는 경로가 있어 데이터 장애가 0건처럼 보일 수 있다.
- 견적의 업무 기준일 대신 생성일을 사용하므로 재발송·수락 시점 통계와 어긋날 수 있다.

정식 읽기 모델은 전체 원천을 서버에서 집계하거나 안정적인 커서 페이지 순회를 사용하고, 조회 실패와 실제 0건을 구분해야 한다. 향후 SQL 뷰를 추가한다면 호출자 권한을 적용하는 `security_invoker` 설정과 회사별 RLS를 함께 검증해야 한다. 머티리얼라이즈드 뷰를 사용할 경우 갱신 지연을 지표에 명시해야 한다.

## 작업지시서와의 충돌

- PR #106은 아직 `main`에 병합되지 않았다. 이 문서는 해당 지시를 선반영한 감사 결과이며, 병합 과정에서 정의가 바뀌면 재검토가 필요하다.
- `docs/02_DOMAIN_MAP.md`는 `sales_transactions`와 `ai_reports`를 영업 소유로 남겨 두고 있으며, 통계 읽기 모델의 원천 소유 관계를 아직 표현하지 않는다. ARC-01 소유권 문서 작업과 조율해야 한다.
- `docs/03_DATABASE.md`와 `/revenue/transactions`는 `sales_transactions`를 “매출 거래 원장” 또는 “매출 원장”으로 표현한다. PR #106의 레거시 별도 표시 원칙과 충돌한다.
- 현재 수락 견적을 `계약`으로 세는 정의와 확정 전표 기반 매출 정의가 공존한다. `계약`을 운영 퍼널 지표로 유지하되 재무 지표와 이름·영역을 분리해야 한다.
